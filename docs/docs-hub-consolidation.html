3줄 요약
① 지금 문제 — 문서 작성 규칙이 지침 파일 여러 곳에 겹쳐 있고 문서 담당 창구는 한 프로젝트에 묶여 있다.
② 그래서 — 규칙을 지침 파일 하나로 모으고 창구를 개인 설정 저장소로 옮기는 안을 만들었다.
③ 그러면 — 아래 결정 5개에 답하면 되고 이전은 진행 작업이 끝난 뒤에 한다.

📖 용어 풀이

  • 스킬 = Claude 에게 작업 방법을 알려 주는 지침 파일. 폴더 하나가 스킬 하나다.
  • 메모리 = Claude 가 프로젝트별로 기억해 두는 규칙 메모. 프로젝트 폴더마다 따로 있다.
  • 허브(문서 코디네이터) = 문서 작업을 받아 워커에게 나눠 주는 담당 창구. 터미널 세션 하나다.
  • 워크스페이스 = 저장소를 복사해 작업하는 별도 폴더(git 워크트리).
  • sparse 워크트리 = 저장소 일부 폴더만 꺼내 둔 워크스페이스.
  • HANDOFF.md = 허브가 다음 세션에 일을 넘기는 인계 문서.
  • decisions.tsv = 허브가 스스로 내린 판단을 한 줄씩 남기는 기록 파일.
  • 개인-* = 허브 밑에 만든 개인 업무용 하위 워크스페이스.
  • 3차 검수 = 1차 다른 Claude, 2차 교차 모델, 3차 사용자가 보는 마지막 확인.
  • 구조안 = 구조 변경 제안 문서 유형. 해설·기록·보고서도 문서 유형 이름이다.
  • detached HEAD = 브랜치 없이 특정 커밋에 붙은 상태. 여기서 만든 커밋은 이력에 안 남는다.
  • 전달 규칙 = 문서 양식이 아니라 누구에게 어떻게 보내는지 정한 규칙.
  • doc-kit = 이 안에서 새로 만들자는 통합 문서 스킬의 임시 이름.
  • 🟢 추가·유지 · 🟡 변경 · 🔴 삭제 · 🔵 테스트 · ⚠️ 위험 · 파랑 도식 칸 = 그대로.

결정2. 문서 메모리 16개 중 양식 규칙 9개만 정리할까?

안 정하면 멈추는 것: 삭제 범위가 정해지지 않아 doc-kit 내용을 확정하지 못한다.

결정5. 개인 HTML 보고를 허브 전용 브랜치의 docs/out/ 한 곳에 모을까?

지금 문제: 개인 보고 HTML 이 90_정리기록과 허브 out/ 에 나뉜다. 새 허브는 detached HEAD 라서 커밋해도 이력에 안 남는다.

안 정하면 멈추는 것: doc-kit 의 저장 위치·브랜치 규칙을 쓰지 못한다.

범위: 개인 HTML 보고만. 저장소에 커밋하는 기술 문서(데이터 명세·기술 기록·해설 md)는 각 저장소 docs/ 관례를 따른다.

선택지고르면되돌리기
A. 허브 전용 브랜치 + docs/out/ ✅ 추천
HTML 만 추적, main 직접 커밋 금지		이력이 남고 찾는 곳이 하나다. 브랜치 이름은 전역 규칙 확인이 필요하다.쉬움
B. 현행 유지

추천 이유: 이력이 안 남는 곳에 산출물을 두면 사라지므로 브랜치 위에서 한 곳에 모은다. 감수하는 단점: 90_정리기록 에 두던 습관을 바꿔야 한다.
