확정: 추천 A 로 진행.

선택지결과되돌리기

B. 처음부터 전 허브 실전달가장 빠르지만 임계값이 추정치라 첫 밤 메모리·한도 사고를 막지 못한다.보통
C. dry-run 일주일 → 실전달판정 품질을 충분히 보지만 기능이 일주일 늦게 쓰인다.쉬움

추천 이유: 상한 숫자들이 아직 추정이라서 실제 부하 기록 없이 보내면 첫 밤에 틀릴 수 있다. 그래서 A 는 하룻밤 기록으로 숫자를 정한 뒤 범위를 좁혀 시작한다. 감수하는 단점: 실전달이 이틀 늦다.

답하는 법: 결정7 A

용어: dry-run — 전달하지 않고 '보냈다면 어디로 갔을지'만 기록하는 시험 운전.

상태(state)는 새로 만들지 않는다. 야간 대기는 배정, 전달 뒤는 진행, 사람 답을 기다리면 막힘(사용자답), 끝나면 완료를 그대로 쓴다. 완료는 지금처럼 증거(PR 번호·커밋 해시) 없이는 못 바꾼다.

장부 한 줄

before (지금, 일부 칸)
{"id":"T9001","text":"...",
 "hub":"docs","state":"배정",
 "needs":["T9000"],
 "done_when":"PR 초안 게시",
 "blocked_reason":null}
after (제안, 새 칸만 굵게 추가)
{"id":"T9001", ... 위와 같음,
 "after":[{"kind":"pr","ref":"#999"}],
 "gate":"auto",
 "questions":[{"q":"파일 이름?","rec":"A",
   "revert":"쉬움","answer":null}],
 "goal":"문서 이름 규칙 반영",
 "night":{"tries":0,"sent_at":""},
 "uses":["unity"]}

왜: 디스패처가 판정에 쓰는 값을 장부 한 줄에 모아 두면 파일 하나만 읽고 보낼지 말지 정할 수 있다.

after 의 형식은 허브 상태 파일이 이미 쓰는 근거 표기(pr:Owner/Repo#N·decision:D-ID·task:T0123, hub_status.py REF_ID)를 그대로 쓴다. 풀림 판정은 ledger_merged.py 의 병합 PR 조회와 answer_store.py 의 결정 답 기록(slack-inbox.jsonl·answer-delivery.jsonl)을 읽는다.

gate 값은 세 가지다. auto(야간 진행 가능), morning(아침 결재함으로), user(사람이 직접. 병합·강제 push 등). 허브가 등록할 때 적지만, 디스패처도 night_policy.tsv 의 금지 키워드(병합·ready·라이브·결정)를 본문에서 찾아 걸리면 morning 으로 올린다. 허브 판단이 틀려도 밤에 새지 않게 하는 이중 검사다.

2. 사전 질문 단계(낮)

  1. 뽑기 — 지시가 큐에 들어오면(머리말 '야간:') 담당 허브가 밤에 막힐 질문을 뽑아 장부 questions 에 적는다. 각 질문에 추천안과 되돌리기 라벨(쉬움·보통·어려움)이 붙는다.
  2. 묶어 묻기 — 매일 15:00(확정 결정2)에 '야간:' 표시 항목 중 미승인 건의 초안(목표·완료 기준·담당 허브·선행 조건·질문과 추천안)을 결정 카드로 보낸다. 카드 1장은 지시 1건이고 선택지는 「오늘 밤 진행 승인」·「보류」다. 첨부 문서는 첫 카드 하나에만 붙는 초안 묶음 html 이다. 전송은 hub_report.py add --kind decide 이고 양식 A(배경·용어 줄, 선택지마다 결과, 추천안)를 그대로 따른다.
  3. 분류 — 카드 답을 읽어 승인한 항목만 장부 night.approved_at 에 기록한다. 안 본 항목은 다음 날 15시 묶음에 다시 간다.

3. 야간 디스패처

launchd 가 30분마다 night_dispatch.py 를 실행한다. 한 회차는 위 판정 순서도대로 항목을 훑고 전달한다. 전달 경로는 허브 코디네이터 터미널로의 terminal send 뿐이다. 메인 터미널은 훅이 막으므로 메인에는 main_inbox.py append 만 쓴다.

허브가 한가한지 — 실제 근거

신호출처쓰는 법
연결·프로세스 생존patrol.sh 의 connected, resume_all.sh 의 claude 프로세스 확인둘 다 참이어야 후보

전달 뒤 무반응 판정(실패 집계)은 stall_watch.py 의 '관찰 갱신 없음(SILENCE_MIN)' 기준을 그대로 쓴다. 허브→터미널 탐색·전송은 intake.py deliver 가 이미 한다(하달 최대 1회, 전송 직전 'sending' 저장, 실패는 장부 보류+메인 알림). 접수 단위 함수라서 항목 단위로 쓸 수 있게 탐색·전송 부분만 떼어 공용화한다.

8. 위험과 막는 법

위험막는 법
허브가 밤에 Slack 알림을 울린다(공통 규칙은 즉시 보고)하달문에 야간 규칙을 붙인다. 2단계 이후 report_sender.py 가 야간 창에 보류하게 고친다.
사용량 한도로 낮 작업까지 막힌다야간 창·전달 상한·신호 감지로 정지. 한도를 직접 읽는 수단은 없어 신호 기반이다.
밤에 Mac 이 잠자면 회차가 멈춘다scrum_run.sh 선례대로 caffeinate -i 아래 실행. 덮개를 닫은 경우는 미확인이라 첫 밤 dry-run 에서 회차 로그로 확인한다.
Orca 재시작으로 허브 핸들이 바뀐다재시작 이어받기는 사용자 승인 카드라 밤에는 못 한다. 터미널을 못 찾으면 전달하지 않고 아침 보고 '허브 응답 없음'에 올린다.
디스크·메모리 가득(11-16 디스크 100% 실제 발생)전달 조건에 디스크·메모리·부하를 넣는다. 빌드·녹화는 야간 허용 범위 밖이다.
허브가 gate 를 잘못 적는다night_policy.tsv 금지 키워드 이중 검사, 의심은 morning.
