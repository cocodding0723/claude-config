결정1. 페이지에서 누른 답을 허브 코디네이터에 직접 전달할까?

배경: 문서 페이지 버튼으로 결정에 답하게 하는 작업 중이다. Slack 버튼 답은 메인 터미널까지만 자동이고 허브로는 메인 세션이 옮긴다.

지금 문제: 메인이 바쁘거나 멈추면 답이 허브에 가지 않는다. 그래서 "누르면 코디네이터가 이어서 작업" 이 메인 상태에 달려 있다.

안 정하면 멈추는 것: 페이지 버튼의 전달 지점을 정하지 못해 3번째 커밋부터 시작하지 못한다.

선택지고르면되돌리기
A. 허브 직접 전달 + 메인에 참고 한 줄 ✅ 추천허브가 바로 받으므로 메인이 멈춰도 이어진다. 실패하면 메인에 대리 전달한다.쉬움
B. 메인 경유 유지Slack 과 같은 길이라 코드가 적다. 메인이 멈추면 답이 허브에 못 간다.쉬움

추천 이유: 메인이 중계 고리라서 멈추면 답이 묻힌다. A 는 기존 허브 전송 함수를 재사용하므로 새 전송 코드가 없다. 감수하는 단점: 메인이 허브 답을 직접 못 보므로 참고 한 줄을 받는다.

답: 결정1 A

용어: 허브 — 작업 묶음별 상주 코디네이터 세션. 메인 — 허브를 총괄하는 세션. 사용자 원문 — 사용자가 한 말을 고치지 않고 허브에 붙이는 전달 형식.

결정2. PR 승인 버튼은 승인 기록만 남기고 병합은 하지 않을까?

배경: PR 승인 버튼을 넣는 중이다. 병합은 사용자 승인이 필요하고, 실행 주체는 기존 규칙대로다(dev/main 병합은 사용자가 직접).

지금 문제: 버튼이 병합까지 하면 충돌 검사를 건너뛴다. 그래서 클릭 하나로 라이브가 깨질 수 있다.

안 정하면 멈추는 것: 7번째 커밋의 버튼 동작을 정하지 못한다.

선택지고르면되돌리기
A. 승인 기록만 ✅ 추천기록과 허브 전달만 하므로 병합 실행은 기존 규칙대로다. 병합은 한 박자 늦다.쉬움
B. 기록 + 병합 실행클릭 하나로 끝나므로 빠르다. 충돌 검사를 건너뛰고 병합이 되돌리기 어렵다.어려움
C. 버튼 없이 PR 링크만위험이 늘지 않는다. 승인은 계속 터미널이나 Slack 에서 말해야 한다.쉬움

추천 이유: 클릭이 실행까지 가면 충돌 검사가 없어진다. A 는 승인과 병합을 나눠 검사를 지킨다. 감수하는 단점: 병합이 코디네이터 차례를 기다린다.

답: 결정2 A

용어: 충돌 검사 — main 에 합칠 때 겹치는 변경이 있는지 먼저 보는 확인. 주 체크아웃 — 라이브가 링크로 읽는 main 작업 폴더.

결정3. 페이지 쓰기 버튼에 확인 단계를 더할까?

배경: 페이지가 읽기 전용에서 허브 터미널로 글을 넣는 도구가 되는 중이다.

지금 문제: 기존 검사는 다른 웹사이트의 요청만 막는다. 같은 권한의 로컬 프로세스는 토큰을 받아 헤더를 직접 만들 수 있다.

안 정하면 멈추는 것: 3번째 커밋의 요청 흐름을 확정하지 못한다.

선택지고르면되돌리기
A. 선택 뒤 "이 답으로 전달" 확인 + 출처 표기·감사 로그오클릭이 줄고 허브 글에 출처가 남는다. 클릭이 한 번 늘어난다.쉬움
B. A + PR 승인만 macOS 확인 창 추가 ✅ 추천병합 승인은 되돌리기 어려우므로 화면 밖 확인을 한 번 더 받는다.쉬움
C. 기존 검사만구현이 가장 작다. 위조 요청이 허브 입력까지 간다.쉬움

추천 이유: 가짜 병합 승인이 가면 되돌릴 수 없는 병합이 시작된다. B 는 그 한 곳만 화면 밖 확인을 둔다. 감수하는 단점: 일반 결정은 A 수준까지만 막는다.

답: 결정3 B

용어: Origin·Sec-Fetch-Site — 브라우저가 요청 출처를 알리는 헤더. CSRF 토큰 — 페이지를 연 사람만 아는 일회성 값. 감사 로그 — 누가 언제 눌렀는지 남기는 기록.

결정4. 자동 판정이 안 되는 항목에 "했음" 버튼을 둘까?

배경: 첫 화면에 사용자 확인 목록을 만드는 중이다. 결정과 PR 은 기록으로 함·안 함을 알지만, 직접 실행 명령·시트 작업·검수는 기록이 없다.

지금 문제: 근거가 없으면 해도 계속 "안 함" 으로 남는다. 그래서 목록이 커지고 진짜 남은 일이 묻힌다.

안 정하면 멈추는 것: 4번째 커밋의 상태 판정 규칙을 정하지 못한다.

선택지고르면되돌리기
A. 했음 버튼 + 허브에 한 줄 전달 ✅ 추천누르면 확인 기록이 남아 "함" 이 되고 허브도 안다. 거짓으로 눌러도 막지 못한다.쉬움
B. 허브가 완료를 보고해야 "함"근거가 허브 보고라 정확하다. 허브가 보고하기 전까지 목록에 남는다.쉬움

추천 이유: 사용자가 직접 한 일은 사용자만 알아서 허브 보고를 기다리면 목록이 안 줄어든다. A 는 그 사실을 한 번 눌러 기록한다. 감수하는 단점: 안 하고 누른 경우를 시스템이 가려내지 못한다.

답: 결정4 A

용어: 확인 기록 — 사용자가 "했음" 을 누른 일을 적는 새 파일. 허브 보고 — 허브가 작업 결과를 올리는 기존 기록.

합계 약 15.5시간, 작업일로 2일 안팎. 추정이며 실측이 아니다. 1~3 을 먼저 병합하면 결정 버튼만 먼저 쓸 수 있고, 4~6 은 그 뒤에 이어진다. 커밋마다 파일 3~10개·400줄 이하를 목표로 한다.

페이지 클릭이 Slack 과 겹치면: 먼저 기록된 답만 유효하다. 늦은 쪽은 "이미 Slack 에서 답함" 또는 "이미 문서 사이트에서 답함" 을 보고 아무것도 실행하지 않는다.
