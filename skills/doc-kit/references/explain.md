# 해설 — 변경 이해 문서

**설계·작업 의도가 중심이고 도식·촬영 이미지는 그 근거다.** 짧게 쓰더라도 왜 이 선택을 했는지는 생략하지 않는다. 산출은 자체 완결 HTML 이다. 레이아웃은 [html-spec.md](html-spec.md), 문체·머리말은 [style.md](style.md).

## 기본 — 3절

상세 해설을 요청했을 때만 «확장 구조» 와 퀴즈를 적용한다. 프로젝트가 별도로 요구한 문서·영상·검증 항목은 유지하되 긴 근거와 로그는 부록이나 접힌 영역으로 뺀다.

1. **의도와 선택** — 해결할 문제 → 왜 이 설계인가 → 왜 이 순서·범위로 작업했는가를 짧게 연결한다. 중요한 대안·절충이 있으면 채택·기각 이유를 한 줄로 붙인다. 기준 커밋·범위·검증 상태는 짧은 한 줄이다.
2. **동작 흐름** — 선택한 설계가 의도를 실현하는 핵심 흐름 하나를 PUML 로 그려 SVG 로 렌더한다. 구조는 component, 순서는 sequence 또는 activity. 시작 조건·핵심 처리·결과만 남기고 중요한 화살표에 동작이나 예시 값을 적는다. 도식 아래 핵심 단계 3~5개와 책임·경계를 그렇게 나눈 이유를 쓴다.
3. **실제 화면·검증** — 의도한 변화가 드러나는 촬영 이미지 2~4장을 고른다. 같은 상태의 중복 샷은 뺀다. 각 이미지에 무엇을 확인하는 화면인지 한 줄을 붙인다. 검증은 `명령 — 결과` 이고, 어떤 위험을 확인했는지와 남은 제한만 적는다.

- `.puml` 원본을 보존하고 문서에는 렌더된 SVG 를 넣는다. PUML 원문·클래스 전체 목록·파일별 diff 를 본문에 나열하지 않는다.
- UI 가 없는 변경은 촬영 이미지를 억지로 만들지 않는다. 캡처가 없으면 미촬영으로 표시한다. 목업·생성 이미지를 실제 검증 화면처럼 쓰지 않는다.
- 촬영 이미지·영상·테스트 결과는 기준 커밋과 실행 시각·토큰 등 출처를 확인한다. 이전 실행 자료는 참고라고 구분하고 이번 검증 근거에 섞지 않는다. 이미지를 직접 열어 설명과 화면이 맞는지 확인한다.
- 의도는 사용자 요구·설계 기록·PR·커밋·실제 제약에서 찾는다. 코드에서 추론한 이유는 추론으로 구분한다. 검토하지 않은 대안이나 작업 이유를 만들지 않는다. "유지보수성 향상" 대신 피하려던 오류·비용·제약을 적는다.
- 작업 설명은 시간순 수행 일지가 아니다. 결과에 영향을 준 판단만 남긴다.
- 긴 배경·튜토리얼·중복 요약·퀴즈는 기본 문서에 넣지 않는다.

## 목적 — 검증이 아니라 참여

이 문서는 코드가 맞는지 확인하려고 만드는 게 아니다. 사람이 이해해야 하는 이유는 **다음 아이디어를 낼 수 있는 상태로 남는 것**이다.

- 결함 지적은 목적이 아니다. 읽다 발견한 문제는 문서 최하단 **번외** 에 분리한다.
- "무엇이 바뀌었나" 가 아니라 "이 시스템이 이제 어떻게 동작하나" 를 쓴다. 디프 나열은 `git diff` 가 한다.
- 파일 단위로 쓰지 않는다. 개념 단위로 묶고 서사 순서로 배열한다.

## 대상 결정

인자가 없으면 현재 브랜치 대 병합 기준이 기본이다. 기준은 설정 `base_branch`, 없으면 저장소 기본 브랜치(`git symbolic-ref refs/remotes/origin/HEAD`, 실패하면 `main`·`master` 순)다.

| 요청 | 명령 |
|---|---|
| 기본 (현재 브랜치 전체) | `git diff $(git merge-base HEAD <기준>)...HEAD` |
| 스테이징된 변경 | `git diff --staged` |
| 워킹트리 | `git diff` |
| 커밋 범위 | `git diff <A>...<B>` |
| 특정 커밋 | `git show <해시>` |
| GitHub PR | `gh pr diff <번호>` |
| GitLab MR | `glab mr diff <번호>` |

## 규모 판정 — 먼저 잰다

`git diff --shortstat` 과 `--name-only` 로 규모를 먼저 잰다.

| 규모 | 방식 |
|---|---|
| 파일 15개 미만 & 1000줄 미만 | 직접 정독 |
| 그 이상 | 먼저 축(theme)으로 분해한다. `--name-only` 와 커밋 메시지로 3~6개 축을 잡고 축마다 조사 에이전트를 한 번에 띄워 병렬 조사한다. 결과를 종합해 메인이 쓴다 |
| 파일 100개 이상 | 축 분해 결과를 먼저 보여 주고 문서를 축별로 나눌지 하나로 갈지 묻는다 |

축은 디렉터리가 아니라 **바뀐 개념**으로 잡는다. 자동 생성물(lock·스냅샷·`.meta`·번역 리소스)은 축에서 빼고 "N개 생성물 제외" 만 적는다.

## 조사

디프만 읽고 쓰면 배경을 못 쓴다. 변경된 코드의 주변(호출부·변경 전 동작·관련 자료구조)을 넓게 읽는다. 함께 읽을 근거는 사용자 요구·설계 기록·PR·커밋의 판단이다. 기록이 없으면 코드상 제약과 추론을 구분하고 의도를 단정하지 않는다. 프로젝트 전용 조사 스킬이 있으면 그 절차를 먼저 따른다.

## 확장 구조 — 상세 해설을 요청했을 때만

0. **머리말** — style.md «머리말». 큰 변경은 독자별 읽는 순서·커밋 순서 표.
1. **Background** — 넓은 배경(초심자용, "아는 분은 건너뛰세요" 명시) → 좁은 배경(변경 전 동작) → (선택) 빈칸 한 문장.
2. **Intuition** — 본질만. 장난감 데이터로 된 구체 예시 하나를 끝까지 따라간다. 동작이 바뀌면 `상황 | 이전 | 이후` 표.
3. **Code** — 변경의 높은 수준 walkthrough. 시점·데이터 흐름 순으로 개념 절을 배열한다. 파일 알파벳순 금지.
4. **못 하는 것·새 계약** — 의도된 한계 표, 이번 변경이 만든 새 규칙 번호 목록, 채택하지 않은 대안. 번외와 다르다. 설계의 일부다.
5. **번외** — 있을 때만. 이해와 무관하게 발견한 결함·의문. 의도된 한계를 번외에 넣지 않는다.
6. **이해도 퀴즈** — 요청했을 때만. 서술형이고 문서 맨 끝이다. 정답은 문항별 접힌 `<details>` 에 둔다. 문항 수·유형·실시간 질의 방식은 [quiz-protocol.md](quiz-protocol.md).

검증은 머리말 한 줄에 둔다. 본문을 고치면 그 절을 근거로 삼은 퀴즈·정답·요약 표를 같이 고친다.

### 퀴즈 문항 수 — 퀴즈를 요청한 경우에만

사용자가 문항 수를 지정하면 그 수를 따른다. 최소 5문항이고 변화량에 비례해 늘린다. 기준은 본문 3장(Code)의 개념 절이고 절 하나당 최소 1문항이 대응돼야 한다.

| 규모 | 문항 수 |
|---|---|
| 파일 15개 미만 & 1000줄 미만 | 5~8 |
| 그 이상 | 개념 절 수만큼, 최소 5 |
| 문서를 여럿으로 쪼갠 경우 | 문서마다 각각 적용 |

### 실시간 질의 테스트 — 요청했을 때만

사용자가 명시적으로 요청했을 때만 한다. 먼저 제안하지 않는다. 문항은 문서 퀴즈 절의 것을 그대로 쓴다. 6문항 이하는 한 번에 전부, 7문항 이상은 5개씩 끊어 묶음으로 낸다. 번호로 답을 받고, 묶음의 답을 다 받은 뒤 문항별로 `✅ 이해 / ◐ 부분 / ❌ 못함` 과 구체 피드백을 준다. ◐ 는 결과는 맞지만 메커니즘·비교 대상이 빠진 답이다. 관대하게 매기지 않고, 끝나면 약한 문항이 다룬 절을 지목한다.

## 저장

설정 `out_dir` 아래 날짜 접두 파일(`name_rule`)이다. 날짜 접두는 생략하지 않는다. PR 에 동봉할 해설이 필요하면 해설을 HTML 로 만들고 PR 본문(create-pr)에서 링크한다.

## 실패 모드

- 디프만 읽고 쓴다 → "코드를 한국어로 옮긴 문서" 가 된다. 주변 코드를 넓게 읽는다.
- 파일 순서대로 쓴다 → `git diff` 와 같아진다. 개념 순서로 재배열한다.
- 리뷰 코멘트가 본문에 섞인다 → 번외로 분리한다.
- 퀴즈 정답을 토글 밖에 노출한다 → 정답은 반드시 접힌 `<details>` 안에 둔다.
- 규모를 안 재고 시작한다 → `--shortstat` 을 먼저 본다.
- 퀴즈가 암기 문제다 → 인과·조건·설계 의도를 묻는다.
- 요청도 없는데 퀴즈·채점을 넣거나 제안한다 → 기본은 핵심 3절이다.
- 코드가 흑백이거나 JSON 이 한 줄로 뭉친다 → html-spec 의 구문 강조·JSON 정렬을 따른다.
- 줄임말·비유로 압축한다 → 풀어 쓴 문장과 예시 하나로 쓴다. 저장 전에 본문 텍스트를 뽑아 훑는다.
- 기준 커밋 없이 규모·실측을 적는다 → 숫자의 출처를 알 수 없다.
