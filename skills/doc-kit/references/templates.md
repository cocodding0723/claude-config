# 문서 유형별 골격

절 제목은 내용에 맞게 바꿔도 되지만 **순서와 역할은 유지**한다. 원형 문서는 설정 `precedent` 가 가리키는 선례 폴더에서 연다. 설정이 없으면 골격만 따른다.

## 1. 설계 기록 — `<주제> (설계 기록).md`

끝난 계획·조사를 근거 보존용으로 굳힐 때.

```markdown
# <주제> — <한 줄 부제>

> [!note] 상태: <확정 / 일부 폐기 / 진행 중>. <이 문서를 언제 읽는가>.

## 0. 정보원과 신뢰도
| 정보원 | 무엇 | 신뢰도 |
### 실측 기준 SHA          ← 어느 커밋 기준으로 읽었나. 움직인 기준이면 귀속이 뒤집힌다

## 1. <대조 — 기획·코드·문서가 어긋나는 지점>
### 확정이 필요한 것 (기획 판단)

## 2. <정정 — 앞 문서가 틀린 곳>

## 3. 내부 설계
### 3.1 …                   ← 후보 (A)/(B) 장단 표 → 결정 근거 번호 → "대안: B 를 골랐다면" + 뒤집는 조건
### 3.N 가져오지 않는 것

## 남은 질문
```

## 2. 계획 — `<주제> 계획.md`

두 모양이 있다. 개정 표기는 짧은 개정이면 제목에 `(v2)`, 여러 차례면 제목은 두고 부록에 vN 이력 표.

### 2-A. cross-build 입력용

구현 전 한 PR 분량 계획. `/plan-review`·`/cross-build` 입력.

```markdown
# <주제> 계획 (v2)

> 기준 HEAD `<sha>`. v1 → v2: <리뷰 반영 요지 한 줄>.

## 0. 작업 경계            ← 건드리는 곳 / 안 건드리는 곳
## 1. 무엇을 고치려는 것인가
### 1-A. <문제를 주장 문장으로>   ← "회차 핀이 네 곳에 흩어져 있다"
## 2. 설계
### 2-A. <결정을 주장 문장으로>
### 2-N. 테스트
## 3. 파일별 변경 목록     ← | 파일 | 변경 |
## 4. 커밋                 ← 제목 초안까지. "사용자 지시 후"
## 5. 하지 않는 것
## 6. 리스크
## 검증                    ← 기계로 판정할 수 있는 번호 문장. "diff 에 X 가 없다", "호출은 이 한 곳뿐이다"
```

- 절 제목을 **주장 문장**으로 쓴다. "회차 핀" ✗ → "회차 핀이 네 곳에 흩어져 있다" ✓
- 머리말에 리뷰 반영 요지를 적는다: "v1 계획검토(NEEDS-REVISION)의 지적을 반영했다".
- 지적은 대개 두 종류다 — **사실 대조 오류**(줄 번호·동작·신규 여부)와 **기계 판정이 안 되는 검증 조건**. 쓰기 전에 둘 다 스스로 대조한다.

### 2-B. 장기 계획용

여러 주 걸리는 작업의 단일 계획.

```markdown
# <작업명> 계획

## 1. 결론 요약
## …                       ← 문제·설계·단계
## N. 수용하는 한계
## N. 결정 기록            ← | 번호 | 주제 | 결정 |
## N. 커밋 단위
## N. 완료 조건
## 부록 A. 설계 검토 이력   ← | 버전 | 지적 | 판정(WRONG 등) | 조치 |  v11 → v25
```

폴더 안에 있는 계획은 `이관 결과 → 등록 지점 → 테스트 → 깨지기 쉬운 곳 → 남은 문제 → 게이트를 지울 때` 순이다.

## 3. 계약 — `<주제> — 서버 계약` / `저작 인터페이스 계약` / `문법 계약`

다른 팀·다른 레포·데이터 저작자에게 넘기는 명세.

```markdown
# <주제> 계약 (`<callable·파일·문법 이름>`)

> 이 문서가 정본이다. <코드·다른 문서와 어긋나면 어느 쪽을 고치나>.

## 0. <받는 쪽> 요약 — 무엇을 해야 하는가   ← 한 장 표. 🆕 신규 / ♻️ 기존 구분
## 1. 왜
## 2. 명세                 ← 요청·응답·필드 전수: | 필드 | 타입 | null 의미 | 매핑 |
### <필드> — <결정을 주장 문장으로>        ← "왜 X 가 아니라 Y 인가" 소절
## N. 결정                 ← D1, D2 … 번호. 폐기한 것도 "걷어낸 이유 / 살아남은 것"
## N. 계약 ↔ 테스트        ← | 계약 | 테스트 |
## N. 하지 않는 것 (비-목표)
```

- 0절 요약·D 번호를 둔다. 🆕/♻️ 구분·계약↔테스트 표는 있으면 넣는다.
- null·빈 값·필드 없음의 뜻을 각각 적는다.
- 상태 표식: 🔴 위험·주의, ✅ 확정.

## 4. 규약 — `<주제> 규약.md`

두 트랙이 갈라진 지점에서 합의한 규칙.

```markdown
# <주제> 규약

> 작성 <날짜>. <합의 경위 한 줄 — 누가, 어떤 충돌 때문에>.

## 왜 이 문서인가
## 현행 <대상>             ← 지금 있는 것 표
## 규약
### 1. <규칙 이름> (<우선순위·예외 여부>)   ← 규칙 → 근거 → 실사례(파일:줄)
### N. 계약 테스트 필수 항목
## 부착 위치               ← 이 규약을 코드·CLAUDE.md 어디에 걸었나
```

## 5. 폴더형 — `<작업명>/00 개요.md` ~ `0N …`

여러 주에 걸친 리팩토링·이관.

두 모양이 있다.

- **질문 단위** (번호형): 지금 어떤가(실측·이관 전 구조) / 어떻게 바꾸나(설계) / 어떤 순서로(진행 계획) / 찾아보는 표(참조표).
- **역할 단위** (역할 단위): `계획` / `변경 해설·이해도 퀴즈` / `CS 런북` — 독자가 다르면 파일을 나눈다.
- `00 개요`는 본문 없이 인덱스만 둔다:

```markdown
# <작업명> — 개요

## 무엇을 하나            ← 두 문단. 문제의 규모(숫자) → 이 작업이 하는 일
## 문서 목록              ← | 문서 | 내용 |
## 코드 지도              ← 핵심 폴더·클래스 (있으면)
## 게이트                 ← RC·patch 게이트 (있으면)
## 정한 것                ← | 번호 | 주제 | 결정 | — 결정 요약 표 하나
```

- 파일당 40~200줄. 넘치면 쪼갠다.

## 6. 데이터 명세 — `<데이터 명세 폴더>/<파일>.json.md`

데이터 JSON 을 추가·변경하면 **같은 PR 에서** 쓴다. 파일이 아니라 개념 단위 명세(`<개념>.md`)도 같은 폴더에 둔다.

```markdown
# <파일> 명세

| 위치 | 로드 주소 | 파서 | 모델 |

> JSON 파일에는 주석을 쓸 수 없다. 필드 뜻은 이 문서가 정본이다.

## 최상위 구조
## 필드                   ← | 필드 | 타입 | 필수 | 뜻 | 예 |
## id 규칙
## 새 항목 추가 절차       ← 번호 단계
## 값 출처                ← 기획 시트·스토리 등
```

## 7. 런북·지시서

- **런북**: CS·운영이 혼자 쓸 수 있게. `0 알아야 할 것 → 1 대상 특정(uid 등) → 2 판정 → 3 조치 절차 → 4 부분 실패 → 5 유저가 본 문구별 대응 → 6 긴급 스위치 → 7 서버 규칙`.
- **지시서**: 다른 사람·도구가 그대로 실행할 단계. `반영 대상 ID → 복사할 문자열 그대로 → 표시 예시 → 수치 위치 → 진실의 원천과 반영 순서 → 테스트 방법`. 외부 저작자 대상이면 `~합니다` 체를 쓸 수 있다.
