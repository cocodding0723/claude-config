# 문체·머리말·장치

모든 유형이 함께 쓰는 기준이다. 선례 저작자가 설정 `precedent` 에 있으면 그 선례 문서를 하나 열어 장치를 맞춘다. 설정이 없으면 이 파일만 따른다.

## 문체

- **평서 `~다`로 쓴다.** `~합니다`·`~입니다`는 쓰지 않는다. 제목·표·목록·배지 줄은 명사형 압축이다(SKILL.md «문장 규칙과 충돌 해결»).
  - 예외: 외부 저작자에게 넘기는 지시서는 `~합니다`를 쓸 수 있다. 커밋 제목은 저장소 규칙, 코드 주석은 `comment-lint` 기준이다.
- **첫 문장은 결과를 단정한다.** 변경 해설 본문만 배경부터 시작한다.
- **굵은 주장 + 근거.** 단락·불릿의 첫 구절을 굵게 쓰고 근거를 뒤에 붙인다. 훑어 읽는 독자는 굵은 줄만 따라간다.
- **용어는 처음 나올 때 굵게 + 한 줄 풀이.** 뜻이 여럿인 말은 표로 갈라 둔다.
- **사내 축약어·숫자 ID 는 첫 등장에 풀어 쓴다.**
- **모르는 것은 먼저 인정한다. 이유가 없으면 없다고 쓴다.**
- 메타 서술("본 문서에서는 ~을 다룬다")은 쓰지 않는다.
- 같은 대상은 같은 이름으로 끝까지 쓴다. 처음 쓰는 개념은 풀어 쓴 문장 + 예시 하나로 설명하고 비유·줄임말로 압축하지 않는다.

## 머리말

문서 첫머리 인용 블록에 읽기 전에 알아야 할 것만 둔다. 두 형이 있다.

**① 규모형 — 단독 변경 해설.**

```markdown
> <이 문서가 무엇이고 언제 읽는가 한 줄>. 말미에 퀴즈 N문항이 있고 정답은 접어 두었다.
>
> `17 커밋 · 23 파일 · +2682 / -46` (`.meta` 제외, vs <기준 브랜치> `b04604e69d`, 2026-10-08 실측)
> **검증**: EditMode 458/458 통과. 수동 QA 미실시.
```

**② 읽는 법·범위형 — 문서망의 세부 문서.**

```markdown
> **읽는 법**: 1장 배경 → 2장 직관 → 3장 코드. 개요는 [00 개요](00%20개요.md).
> **범위**: <이 문서가 다루는 것 / 다루지 않는 것>
```

- 규모 줄은 필수이고 기준 커밋·실측 날짜는 권장한다. 기준이 움직이면 원인 귀속이 뒤집힌다.
- 생성물 비중이 크면 밝힌다.
- 문서가 크면 목차, 독자별 읽는 순서, 커밋(리뷰) 순서 표를 붙인다. 동작을 바꾸는 커밋은 굵게 쓴다.
- 상태·정정은 `> [!NOTE]`·`> [!IMPORTANT]` 콜아웃으로 쓴다.
- 계약·규약·폴더형 같은 비해설 문서는 머리말을 생략해도 된다.

## 정정

**본문을 지우지 않고 덧쓴다.**

- 대전제가 바뀌면 머리말 콜아웃에 쓴다. "본문은 당시 판단의 기록으로 남긴다." 또는 이전/지금 표.
- 부분 정정은 본문 안에 `정정(YYYY-MM-DD)` 표식을 쓴다.
- 틀린 수치도 지우지 않고 정정 이력으로 남겨 재사용을 막는다.
- 실행이 끝난 계획은 설계 기록으로 개명하고 실행 단계 절을 걷어낸다. 남겨 두면 다음 사람이 따라간다.
- 본문을 고치면 그 절을 근거로 쓰는 퀴즈·요약 표·다른 문서를 같이 고친다.

## 반복 장치

**핵심** — 해당하면 쓴다.

| 장치 | 형태 |
|---|---|
| 번외 | 우연히 발견한 결함. 큰 문서는 「고친 것 / 남겨 둔 것」으로 나눔 |
| 못 하는 것·하지 않는 것·비-목표 | 의도된 한계. 번외와 섞지 않음. PR 에서는 `범위 밖 / 후속` |
| 상태 표식 | 🔴 위험 · ✅ 확정 · ⚠️ 주의 |
| 리뷰 반영 이력 | v1→v2 무엇을 바꿨나, 지적 판정 |
| 기각안 | `다른 안` 절: "안 → 기각 이유" |
| 뒤집는 조건 | "**뒤집는 조건**: ~가 되면 B 로 간다" |
| 부재와 빈 값 구분 | "빈 배열은 운영의 의도고, 목록 없음은 못 읽은 것이다" |
| 임의값 | 근거 없이 정한 숫자는 임의값이라고 밝힘 |
| 묶음 판단 기준 | "같은 코드가 이미 3벌 이상 있고, 넷째가 오고 있는가?" |
| 결정 번호표 "정한 것" | `번호 \| 주제 \| 결정` |
| 변화 표 | `상황 \| 이전 \| 이후` — "의도한 동작 변화는 아래 표가 전부다" |
| 실기 미검증 | 굵게 따로, 확인할 화면 목록 |
| 기본값·게이트 | 기본값, 끄면 일어나는 일, 그렇게 둔 이유 |
| 다른 브랜치·운영 영향 | 컴파일은 그대로 되지만 의미가 바뀌는 곳 |
| 배포·머지 뒤 할 일 | 실행할 명령까지 |

**선택** — 맞는 자리에서만 쓴다.

- 빈칸 한 문장 — "이 변경이 채우는 빈칸은 하나다: …"
- 실패 분기 표 — `단계 | 하는 일 | 실패하면 | 탐지?`
- 한계 표의 빈도 별점(★)
- 이번 변경이 만든 새 계약 번호 목록
- 계약↔테스트 표
- 회귀 테스트의 수정 전 실패 증명
- 폐기 결정 보존 — "걷어낸 이유 / 살아남은 것"
- 우선순위 + 장난감 집합 — "겹치면 **C > B > A**"

## 근거·인용

- 숫자로 쓴다. "많다" 대신 "약 1,060개(약 6%)", "영향 uid 78".
- 코드는 `File.cs:48`, 이어지면 `:131-133`. 커밋 해시 9자리 이상, 절 참조는 `§3.5`.
- 문서 링크: 같은 폴더 안은 퍼센트 인코딩 상대경로. PR 본문에서는 상대경로를 쓰지 않고 blob 절대 URL 을 쓴다. 경로는 퍼센트 인코딩하고 괄호도 `%28 %29` 로 바꾼다.
- 저장소 내 선례는 표로, 외부 선례(라이브러리·언어)는 이름과 링크로 적는다.

## 그림

- md 문서: 코드블록 안 ASCII 흐름도·박스와 표가 기본이다. mermaid 는 GitHub·Obsidian 둘 다 렌더될 때만 쓴다.
- 흐름이나 구조가 바뀌는 문서에는 표나 그림을 하나 이상 넣는다.
- HTML 산출물은 [html-spec.md](html-spec.md) 를 따른다. ASCII 도식은 쓰지 않는다.

## 하지 않는 것

- 같은 글을 PR 본문과 커밋 메시지에 두 번 쓰기.
- AI 흔적 줄(`🤖 Generated with`, `Co-Authored-By`)을 PR·문서에 넣기. 사용자 규칙이 우선한다.
- PR 요약 문단을 400자 넘기기. 길어지면 표나 해설 문서로 위임한다.
