# 읽기 쉬운 XML 문서 주석

문서 주석은 **이 대화도, PR 도, 설계 문서도 볼 수 없는 사람**이 IDE 툴팁으로 읽는다.
그 사람은 C# 은 알지만 이 모듈의 용어는 모른다. 그 사람이 구현을 열지 않고 호출할 수 있으면 성공이다.

## 전역 규칙과의 관계

전역 CLAUDE.md 의 "명사형 압축"은 `//` 인라인 주석 규칙이다. `///` 는 다르게 쓴다.

- `<summary>` 만 짧게 쓴다. 한 문장.
- `<remarks>`, `<param>`, `<returns>`, `<exception>` 은 완전한 문장으로 쓴다. 정보를 줄이지 않는다.
- 프로젝트가 "요청 없는 주석 금지"여도, 사용자가 문서 주석을 요청했으면 이 스킬이 우선한다.

## 태그별 역할

| 태그 | 담는 것 | 형식 |
| --- | --- | --- |
| `<summary>` | 이것이 무엇인지, 또는 무엇을 하는지 | 한 문장. 툴팁 첫 줄에 나온다 |
| `<remarks>` | 언제 쓰는지, 주의할 점, 낯선 용어의 뜻 | 완전한 문장. 문단이 둘 이상이면 `<para>` |
| `<param>` | 넣을 값과 허용 범위 | 예시 값을 함께 적는다 |
| `<returns>` | 돌려주는 값. 실패했을 때의 값 포함 | null, 빈 목록, false 가 나오는 조건을 적는다 |
| `<exception>` | 호출자가 구분해서 처리해야 하는 예외 | 던지는 조건 |
| `<example>` | 시그니처만으로 안 보이는 사용 순서 | 코드 앞에 무엇을 보여 주는지 한 문장 |

구현 방법은 문서 주석에 쓰지 않는다. 호출자가 안전하게 쓰는 데 필요한 것만 쓴다.
구현 설명이 필요하면 본문 안 `//` 주석으로 옮긴다.

## 문장 규칙

1. **한 문장에 생각 하나.** 쉼표로 세 가지를 이어 붙였으면 문장을 나눈다.
2. **기호로 단어를 대신하지 않는다.**

   | 쓰지 않는다 | 대신 |
   | --- | --- |
   | `A · B · C` | "A, B, C" 또는 "A 와 B" |
   | `설명 — 부연` | 마침표로 끊고 새 문장 |
   | `A → B` | "A 를 B 로 바꾼다", "A 다음에 B" |
   | `A ∧ B`, `A ⇔ B`, `x = y` | "A 이고 B 일 때", "A 이면 B 이고 그 반대도 같다", "x 는 y 다" |
   | `Reached / NotReached` 같은 빗금 나열 | "A 또는 B" |

3. **내부 용어는 풀어 쓴다.** 호출자가 몰라도 되면 뺀다. 꼭 필요하면 같은 주석 안에서 뜻을 적는다.
   - 나쁨: `outbox 에 보관, 다음 진입에서 ops 로 확인`
   - 좋음: `기기에 요청을 저장해 두고, 다음에 패스를 열 때 서버에 반영됐는지 확인한다`
4. **용어는 한 곳에서 정의하고 같은 말로 쓴다.** 모듈의 핵심 용어는 대표 타입의 `<remarks>` 에 정의한다.
   다른 주석은 그 용어를 그대로 쓴다. 같은 것을 "게이트", "잠금", "락" 으로 바꿔 부르지 않는다.
5. **예시 값을 든다.** id, 키, 종류 문자열에는 실제로 쓰이는 값을 적는다. 예시는 저장소의 샘플 데이터에서 가져온다.
6. **호출자가 놀랄 동작을 적는다.** 예외를 던지지 않고 삼키는 경우, null 을 돌려주는 조건, 호출 순서 제약, 부수 효과.
7. **코드와 대조하고 쓴다.** 이름만 보고 뜻을 짐작해 쓰지 않는다. 그 값을 읽는 구현을 열어 확인한다.
   확인하지 못한 내용은 쓰지 않는다.

## 달지 않는 곳

- 이름과 타입이 전부 말하는 멤버(`public int Count { get; }` 에 "개수").
- `private` 멤버, 생성자, `Equals`/`GetHashCode`/`ToString`.
- 인터페이스 구현 멤버는 `/// <inheritdoc />` 한 줄.

## 절차

1. 대상을 정한다. 공개 타입과 공개 멤버만.
2. 모듈의 낯선 용어를 뽑는다. 호출자에게 필요한 용어만 남기고, 정의를 둘 대표 타입을 고른다.
3. 각 멤버의 구현을 읽고 계약을 확인한다(반환 조건, 예외, 부수 효과).
4. 작성한다. 기존 `///` 는 고쳐 쓰고, `//` 근거 주석은 건드리지 않는다.
5. 아래 점검표로 훑는다.
6. 보고한다. 파일별 건수, before/after 예 3개 이내, 코드와 대조하다 발견한 불일치.

## 점검표

- [ ] `<summary>` 가 한 문장인가
- [ ] `·`, `—`, `→`, `∧`, `⇔`, `/` 나열이 남아 있지 않은가
- [ ] 설명 없이 쓴 내부 용어·약어가 없는가
- [ ] 같은 개념을 다른 말로 부른 곳이 없는가
- [ ] null, 빈 값, 실패 시 동작을 적었는가
- [ ] 예시 값이 실제 데이터에 있는 값인가
- [ ] 구현을 열어 확인한 내용만 썼는가

## 예

```csharp
// 나쁨: 기호 나열, 설명 없는 내부 용어, 한 줄에 생각 셋
/// <summary>15초 안에 응답 없음 — 반영 여부 불명. outbox 에 보관하고 다음 진입에서 ops 로 확인.</summary>
Timeout,

// 좋음
/// <summary>서버가 15초 안에 응답하지 않았다.</summary>
/// <remarks>
///     요청이 서버에 반영됐는지 알 수 없다. 요청을 기기에 저장해 두고,
///     다음에 패스를 열 때 반영 여부를 확인한다. 그때까지 새 수령과 구매는 실패한다.
/// </remarks>
Timeout,
```
