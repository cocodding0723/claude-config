# 한국어 기술 문서 작성 기준

적용: 한국어 기술 문서·QA 절차·도식 설명. 사용자가 지정한 독자·양식·최신 문체 요청 우선.

## 문장과 용어

- 이 사용자의 기술 문서는 짧고 직접적인 표현 우선. 제목·표·PUML 라벨은 핵심 어구 중심. `~이다`, `~하다` 반복 생략.
- 설명에 필요한 주체·조건·시점·결과는 유지. 짧은 명사 나열만으로 관계가 모호해지면 연결 표현 추가.
- 슬래시(`/`)·화살표·괄호를 한 문장에 과도하게 겹치지 않기. 비교는 표, 실행 순서는 번호, 인과관계는 문장으로 표현.
- 독자의 작업에 필요한 전문 용어는 유지하고 첫 등장에 의미 설명. 익숙하지 않은 약어·임의로 만든 역할명은 최소화.
- 같은 대상을 같은 이름으로 표현. 서버 환경, Git 브랜치, SDK 기본값, 앱 선언값을 서로 다른 개념으로 구분.
- enum·클래스·서버 키 등 식별자는 실제 철자 유지. 표시 이름을 쉽게 바꾸더라도 원래 식별자와 대응 가능하게 구성.
- 불확실성은 해당 주장 가까이에 표시. 확인한 사실까지 막연한 가능성 표현으로 약화하지 않기.
- 이미 알고 있는 맥락을 다시 묻거나 문단마다 검수 요청 반복 금지. 꼭 필요한 질문만 묶어서 제시.

## 짧지만 해석 가능한 표현

아래는 표현 예시. 다른 프로젝트의 사실이나 기본 정책으로 재사용 금지.

| 모호한 표현 | 개선 방향 |
| --- | --- |
| 개발 Key 없음 | 개발 서버 RTDB의 `/emergencyFlag`에 해당 키 없음 |
| 기본값 적용 | Flutter enum의 `defaultValue` 적용 / SDK 기본값과 구분 |
| Flag ON | 해당 enum 값 `true` / 기능 효과는 사용처 기준으로 별도 설명 |
| 실패 시 유지 | Fetch 실패 시 현재 사용값 유지 / 오류 입력으로 덮어쓰기 없음 |
| 정상 동작 확인 | 변경한 입력·확인할 화면 또는 값·기대 결과 명시 |

개선 표현에 필요한 근거가 없으면 원문을 명확히 고치거나 미확인으로 표시. 예시의 기술 조건을 추정해서 채우지 않기.

## 문서 유형별 핵심

| 유형 | 독자가 찾아야 할 내용 |
| --- | --- |
| 설계·마이그레이션 | 목적, 현재 동작, 변경 동작, 의도한 차이, 실패 처리, 미결정 사항 |
| 값·설정 목록 | 정확한 식별자, 출처별 값, 누락의 의미, 기능 영향, 반영 시점 |
| QA 가이드 | 준비 조건, 변경할 입력, 실행 순서, 관찰 가능한 예상 결과, 결과 기록 |
| 동작 도식 | 시작 조건, 역할, 정상 경로, 분기 조건, 실패 후 상태, 종료 범위 |

필요한 항목만 선택. 템플릿을 채우기 위한 빈 섹션·중복 표 생성 금지.

## QA 절차

- 기본 순서: 준비 → 조작 → 예상 결과. 계정·플랫폼·언어·기간 등 결과를 바꾸는 조건은 해당 케이스 가까이에 배치.
- 서버에 입력한 값, 앱이 현재 사용하는 값, 화면·기능 결과를 구분. 서버 저장 성공만으로 앱 반영 성공 판정 금지.
- 코드 선언값과 런타임 값 구분. Flutter 문서라면 해당 enum의 `defaultValue`와 `value`처럼 실제 API로 명시.
- 토글 검사에서는 두 값의 기능 의미 확인. `true`가 차단이나 일시 중지를 뜻할 수도 있으므로 ON/OFF만으로 설명하지 않기.
- 즉시 화면 갱신, 다음 행동에서 검사, 화면 재진입·초기화 때 검사하는 기능 구분.
- 기능이 없거나 현재 빌드에서 진입 불가하면 근거와 재현에 필요한 조건 명시. 실제 존재하지 않는 테스트 버튼·주입 도구를 준비 완료로 표현하지 않기.
- 예상 결과와 실행 결과를 분리. 미실행·재현 불가 상태는 통과로 표시하지 않기.

## PUML·기타 동작 도식

- 제목에 다루는 흐름과 현재 구현·변경 설계 여부 표시. 처음 등장하는 약어·역할은 독자가 이해할 수 있게 설명.
- 정상 경로부터 읽히도록 구성. 예외가 본 흐름을 가리면 별도 도식으로 분리하고 참조 연결.
- 분기에는 조건과 결과 표시. 끝 표시는 앱 종료·해당 요청 종료·구독 종료 중 의미 명확화.
- 시간 순서가 아닌 독립 사례를 한 도식에 넣을 때는 별도 예시임을 표시.
- 값 수신, 검증, 저장, 기능 소비가 다른 시점이면 단계 구분. UI·캐시 갱신 범위를 실제 소비 코드와 대조.
- 문법 검사와 렌더링 결과 확인. 도식 렌더링 성공을 앱 동작 검증으로 표현하지 않기.
