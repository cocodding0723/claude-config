# 퀴즈 출제 기준

퀴즈나 실시간 질의 테스트를 요청한 경우에만 읽는다. 기본 시각 설명에는 퀴즈를 넣지 않는다. 문항 수 기준은 `SKILL.md` «퀴즈 문항 수»이며 사용자 지정이 우선한다.

## 유형

한 문서에 **최소 세 유형**을 섞는다. 암기형("이 함수 이름은?")은 쓰지 않는다. 문항에 붙이는 라벨은 유형명 또는 근거 절 이름(최신 「GameComplete」: 배경·확정·판정)이고, 없어도 된다(선례 21/26 무라벨).

| 유형 | 묻는 것 | 예 |
|---|---|---|
| 인과 | A 가 일어나면 왜 B 가 되나 | "카탈로그 해시가 하나 틀리면 부팅이 왜 멈추지 않나" |
| 반사실 | 이 설계가 아니었다면 무엇이 깨지나 | "서버 필드가 단수이고 `set()`으로 덮어썼다면 무엇이 사라지나" |
| 설계 의도 | 왜 이 방법인가, 다른 안은 왜 기각됐나 | "왜 RemoteConfig 기본값을 false 가 아니라 true 로 두었나" |
| 경계 | 어디서 동작이 갈리나, 빈 값·부재·동시성 | "빈 배열과 목록 없음은 화면에서 각각 어떻게 다른가" |
| 시나리오 | 주어진 상황을 끝까지 따라가기 | "7일차에 앱을 강제 종료하면 언제 걸리고, 화면에 무슨 일이 생기나" |
| 계산 | 장난감 데이터로 값 산출 | "효율 +30%, ×1.2, 덮어쓰기 50 이 겹치면 최종값은" |
| 확장 | 새 X 를 붙이려면 어디를 고치나 | "새 속보를 추가하려면 손댈 곳은 몇 군데이고 어디인가" |
| 부작용 | 이 변경이 다른 곳에 미치는 영향 | "다른 브랜치에서 `HasTag` 를 쓰던 코드는 어떻게 되나" |

## 형식

```markdown
## 6. 이해도 퀴즈

> 자기 답을 먼저 적거나 소리 내 말한 뒤 토글을 연다.

**Q1. (인과)** <질문>

<details><summary>정답 보기</summary>

<핵심 요소 2~4개 — 메커니즘까지>. 근거: `File.cs:48`, §3.2

</details>
```

- 문항 머리는 `**Q1.**` 굵은 줄(선례 16)이 기본, `### Q1`(8)도 쓴다. 한 문서 안에서는 하나로.
- 토글 문구는 `정답 보기`(선례 22/26).
- 정답에는 **메커니즘**을 쓰고, **근거 위치**(`파일:줄` 또는 `§절`)를 붙인다(선례 18/26). 결과만 적은 정답은 독자가 대조할 수 없다.
- (선택) 퀴즈 머리에 문항↔절 대응 한 줄: "Q1·Q4 원 리팩터링 / Q2 버전 게이트 / Q3 phase".
- 문항은 본문 Code 절 순서를 따른다. 문항마다 근거 절을 하나 이상 가리킨다.
- 시나리오·계산 문항은 장난감 데이터를 Intuition 절과 같은 것으로 쓴다.

## 본문과의 일치

- 퀴즈를 쓴 뒤 **정답마다 근거 절을 다시 열어** 같은 말을 하는지 대조한다.
- 본문을 고치면 그 절을 근거로 삼은 문항을 찾아 같이 고친다(`grep -n "§3.5"`). 양성 사례 「신규 속보 21종」(정답 안에 `정정(날짜)`), 반례 「메타 보상 계층」 Q3.

## 실시간 질의 테스트

`SKILL.md` 4장을 따른다. 문항은 문서에 실린 것을 그대로 쓰고, 채점은 `✅ 이해 / ◐ 부분 / ❌ 못함`. ◐ 는 결과는 맞지만 메커니즘·비교 대상이 빠진 답이다.
