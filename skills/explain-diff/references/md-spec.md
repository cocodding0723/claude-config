## 파일명

기본은 `<주제> (변경 해설).md`. 퀴즈를 요청한 경우에만 `(변경 해설·이해도 퀴즈)`를 쓴다. 기존 저장소 네이밍 규칙이 있으면 따른다.

## 기본 골격

**의도와 선택 → PUML 동작 흐름 → 실제 화면·검증** 3절로 쓴다. 해결할 문제, 왜 이 설계와 작업 순서·범위를 택했는지부터 설명한다. 중요한 대안·절충은 한 줄로 적는다. 렌더된 도식으로 선택이 구현되는 흐름을, 대표 촬영 이미지 2~4장과 검사로 의도한 결과를 보여 준다. 기준 SHA·검증 상태는 짧게 붙인다. 긴 배경·파일별 나열·퀴즈는 기본으로 넣지 않는다. 간결함을 이유로 설계·작업 의도를 빼지 않는다.

## 확장 골격 — 상세 해설 요청 시

아래 구조는 상세 요청 시에만 적용한다. 퀴즈 절과 문항 안내는 퀴즈를 요청했을 때만 넣는다.

```markdown

> 말미에 이해도 퀴즈 N문항이 있고 정답은 접어 두었다.
>
> `17 커밋 · 23 파일 · +2682 / -46` (`.meta` 제외, vs dev `<sha>`, <날짜> 실측)
> **검증**: <명령·결과 숫자>. <수동 QA·실기 미실시면 그렇게>

<큰 변경이면: 목차 / 독자별 읽는 순서 / | 커밋(리뷰 순서) | 절 | — 동작을 바꾸는 커밋 굵게>
<문서망의 세부 문서면 머리말을 "읽는 법·범위형"으로 — house-style.md «머리말»>
```

## 그림

흐름·구조는 PUML로 작성해 SVG로 렌더하고 `.puml` 원본과 함께 보존한다. 문서에는 상대경로 이미지 링크로 SVG를 넣고, 실제 촬영 이미지도 관련 설명 옆에 붙인다. 대상 뷰어가 SVG를 지원하지 않으면 같은 PUML에서 렌더한 PNG를 사용한다. PUML 코드블록이나 ASCII 그림으로 렌더 결과를 대신하지 않는다. 캡처에는 출처·기준 SHA/실행 시각과 관찰할 변화 한 줄을 적는다.
