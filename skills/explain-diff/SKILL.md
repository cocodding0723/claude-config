# explain-diff — 변경 이해 문서

## 기본 — PUML과 실제 화면으로 핵심만

**설계·작업 의도가 중심이고 도식·촬영 이미지는 그 근거다.** 짧게 쓰더라도 왜 이 선택을 했는지는 생략하지 않는다. 아래 3절만으로 의도와 변경 후 동작을 이해하게 만든다. 상세 해설을 요청했을 때만 뒤의 확장 구조와 퀴즈를 적용한다. 프로젝트가 별도로 요구한 문서·영상·검증 항목은 유지하되 긴 근거와 로그는 부록이나 접힌 영역으로 뺀다.

1. **의도와 선택** — 해결할 문제 → 왜 이 설계인가 → 왜 이 순서·범위로 작업했는가를 짧게 연결한다. 중요한 대안·절충이 있으면 채택·기각 이유를 한 줄로 붙인다. 기준 SHA·범위·검증 상태는 짧은 한 줄로 적는다.
2. **동작 흐름** — 선택한 설계가 의도를 어떻게 실현하는지 핵심 흐름 하나를 PUML로 그려 SVG로 렌더한다. 구조는 component, 순서는 sequence 또는 activity 중 맞는 것을 고른다. 시작 조건·핵심 처리·결과만 남기고 중요한 화살표에 동작이나 예시 값을 적는다. 도식 아래 핵심 단계 3~5개와 중요한 책임·경계를 그렇게 나눈 이유를 설명한다.
3. **실제 화면·검증** — 의도한 변화가 드러나는 촬영 이미지 2~4장을 고른다. 같은 상태의 중복 샷은 빼고, 각 이미지에 무엇을 확인하는 화면인지 한 줄로 붙인다. 검증은 `명령 — 결과`, 선택한 검사로 어떤 위험을 확인했는지와 남은 제한만 적는다.

- `.puml` 원본을 보존하고 문서에는 렌더된 SVG를 넣는다. PUML 원문·클래스 전체 목록·파일별 diff를 본문에 나열하지 않는다. 세부 코드는 이해에 꼭 필요할 때만 넣는다.
- UI가 없는 변경은 촬영 이미지를 억지로 만들지 않는다. UI 캡처가 없으면 미촬영으로 표시하고, 필요할 때 관련 흐름만 촬영한다. 목업·생성 이미지를 실제 검증 화면처럼 쓰지 않는다.
- 촬영 이미지·영상·테스트 결과는 기준 SHA와 실행 시각·토큰 등 출처를 확인한다. 이전 실행 자료는 참고라고 구분하고 이번 검증 통과 근거에 섞지 않는다. 직접 이미지를 열어 설명과 화면이 맞는지 확인한다.
- 의도는 사용자 요구·설계 기록·PR·커밋·실제 제약에서 찾는다. 코드에서 추론한 이유는 추론으로 구분하고, 검토하지 않은 대안이나 작업 이유를 만들어 내지 않는다. "유지보수성 향상" 같은 추상적인 말 대신 피하려던 오류·비용·제약을 적는다.
- 작업 설명은 시간순 수행 일지가 아니다. 왜 먼저 분리·수정·검증했고 무엇을 이번 범위에서 남겼는지, 결과에 영향을 준 판단만 남긴다.
- 긴 배경·튜토리얼·중복 요약·퀴즈는 기본 문서에 넣지 않는다. 핵심 동작이 아니라면 생략하거나 부록으로 보낸다.
- 저장 전 **왜 이 설계·작업 방식을 택했는지**, **도식이 그 선택을 어떻게 구현하는지**, **실제 화면·검사가 의도한 결과를 뒷받침하는지** 확인한다.

Geoffrey Litt(Notion), ["Understanding is the new bottleneck"](https://www.geoffreylitt.com/2026/07/02/understanding-is-the-new-bottleneck)의 기법을 이 환경에 맞춘 것. 실제 산출물 기준은 **machamy 의 JobMaker `docs/Tech Records/*(변경 해설·이해도 퀴즈).md` 26편**이다(2026-10-08 분석).

읽을 파일 — 해당 단계 진입 전에:

| 파일 | 언제 |
|---|---|
| `~/.claude/skills/tech-record/references/house-style.md` | **항상.** 문체(`~다`)·머리말·반복 장치 |
| `references/md-spec.md` | B(마크다운) 산출 |
| `references/html-spec.md` | A(HTML) 산출 |
| `references/quiz-protocol.md` | 퀴즈·실시간 질의 테스트를 요청했을 때만 |
| `~/.claude/skills/tech-record/references/sources.md` | 선례를 열어 볼 때 |

## 목적 — 검증이 아니라 참여

**이 문서는 "코드가 맞는지" 확인하려고 만드는 게 아니다.** 맞는지는 에이전트가 점점 잘한다. 사람이 이해해야 하는 진짜 이유는 **다음 아이디어를 낼 수 있는 상태로 남는 것**이다. 이번 바퀴에서 얻은 이해가 다음 바퀴의 재료다. 그 자리는 위임이 안 된다.

이 전제가 산출물의 모든 선택을 지배한다:

- **결함 지적은 목적이 아니다.** 읽다 발견한 문제는 본문에 섞지 말고 문서 최하단 **번외** 섹션에 분리한다. 섞이면 독자가 문서를 리뷰 코멘트로 읽고, 이해는 뒷전이 된다
- **"무엇이 바뀌었나"가 아니라 "이 시스템이 이제 어떻게 동작하나"를 쓴다.** 디프 나열은 이미 `git diff`가 한다
- **파일 단위로 쓰지 않는다.** 개념 단위로 묶고 서사 순서로 배열한다

## 대상 결정

인자가 없으면 **현재 브랜치 vs 병합 기준**이 기본이다.

| 요청 | 명령 |
|---|---|
| 기본 (현재 브랜치 전체) | `git diff $(git merge-base HEAD <기본브랜치>)...HEAD` |
| 스테이징된 변경 | `git diff --staged` |
| 워킹트리 | `git diff` |
| 커밋 범위 | `git diff <A>...<B>` |
| 특정 커밋 | `git show <해시>` |
| GitHub PR | `gh pr diff <번호>` |
| GitLab MR | `glab mr diff <번호>` |

기본 브랜치는 `git remote show origin` 대신 `git symbolic-ref refs/remotes/origin/HEAD` 로 싸게 확인하고, 실패하면 `main`/`master` 순으로 시도한다. 어느 쪽인지 끝내 애매하면 묻는다.

## 규모 판정 — 먼저 잰다

`git diff --shortstat`과 `--name-only`로 규모를 먼저 잰다. 이 스킬이 필요한 상황은 대개 큰 변경이고, 재지 않고 뛰어들면 컨텍스트가 터진다.

| 규모 | 방식 |
|---|---|
| 파일 15개 미만 & 1000줄 미만 | 직접 정독 |
| 그 이상 | **먼저 축(theme)으로 분해**한다. `--name-only`와 커밋 메시지로 3~6개 축을 잡고, 축마다 `Explore` 서브에이전트를 **한 번에** 띄워 병렬 조사(그 축의 기존 시스템 + 변경의 요지 + 핵심 파일:줄). 결과를 종합해 메인이 문서를 쓴다 |
| 파일 100개+ | 축 분해 결과를 먼저 보여주고 **문서를 축별로 나눌지 하나로 갈지 묻는다**. 5만 줄짜리를 한 문서에 밀어넣으면 아무도 안 읽는다 |

축은 파일 디렉터리가 아니라 **바뀐 개념**으로 잡는다. 자동 생성물(lock 파일, 스냅샷, `.meta`, 번역 리소스)은 축에서 빼고 문서에 "N개 생성물 제외"만 적는다.

## 워크플로우

### 1. 조사

디프만 읽고 쓰면 **배경**을 못 쓴다. 변경된 코드의 **주변 코드를 넓게 읽는다** — 호출부, 이 변경 전의 동작, 관련 자료구조. 배경이 부실한 설명 문서는 "코드에 있는 말을 다시 쓴 것"이 되고 이해에 기여하지 않는다.

함께 읽을 근거는 사용자 요구·설계 기록·PR·커밋의 판단이다. 기존 문제, 선택 이유, 중요한 대안과 절충, 작업 순서·범위·검증 선택의 이유를 찾는다. 기록이 없으면 코드상 제약과 추론을 구분하고 의도를 단정하지 않는다.

프로젝트 전용 스킬이 있으면(예: `jobmaker-onboarding-qa`) 그 조사 절차를 먼저 따른다.

### 2. 문서 작성

먼저 아래 **2-1에서 산출 형식을 정한다.** HTML이면 `references/html-spec.md`, 마크다운이면 `references/md-spec.md`를 읽고 위의 **기본 3절**로 작성한다.

**아래 확장 구조는 상세 해설을 요청했을 때만 적용한다.** 퀴즈는 상세형에서도 별도 요청이 있을 때만 붙인다:

0. **머리말** — 인용 블록. 단독 해설은 규모형(읽는 법 한 줄, 규모 줄 + 기준 SHA·실측 날짜, **검증 한 줄**, 퀴즈 N문항·정답 접힘 안내), 문서망의 세부 문서는 읽는 법·범위형(`house-style.md` «머리말»). 큰 변경은 독자별 읽는 순서·커밋 순서(리뷰 순서) 표
1. **Background** — 넓은 배경(초심자용, "아는 분은 건너뛰세요" 명시) → 좁은 배경("이미 있던 것", 변경 전 동작) → (선택) **빈칸 한 문장**("이 PR 이 채우는 빈칸은 하나다: …")
2. **Intuition** — 본질만. 장난감 데이터로 된 구체 예시 하나를 끝까지, 그림 적극 사용. 동작이 바뀌면 `상황 | 이전 | 이후` 표
3. **Code** — 변경의 높은 수준 walkthrough. **시점·데이터 흐름 순**으로 개념 절을 배열. 단계마다 실패 경로가 갈리면 (선택) `실패하면 / 탐지?` 열이 있는 표
4. **못 하는 것·새 계약** — (해당할 때) 의도된 한계 표, 이번 변경이 만든 새 규칙 번호 목록, 검토했지만 채택하지 않은 대안. **번외와 다르다** — 이건 설계의 일부다
5. **번외** — (있을 때만) 이해와 무관하게 발견한 결함·의문. 큰 문서는 「고친 것 / 남겨 둔 것」으로 나눈다
6. **이해도 퀴즈** (`자가 점검 퀴즈`도 씀) — 서술형, 문서 맨 끝. **정답은 문항별 접힌 `<details>` 토글로 숨긴다.** 읽는 사람이 혼자 자기 이해를 재는 장치다 — 채점자는 없다. 문항 수는 아래 기준, 유형·형식은 `references/quiz-protocol.md`

검증 결과는 머리말 한 줄에 둔다("**검증**: EditMode 458/458 통과. 수동 QA 미실시"). 기본형의 마지막 절에서는 필요한 명령·결과만 적고, 상세 표는 검증 항목이 여럿이고 일부가 실패·미실시일 때만 쓴다.

사실이 바뀌면 본문을 지우지 않고 정정 머리말·`정정(날짜)` 표식으로 덧쓴다(`house-style.md` «정정»).

변경이 여러 하위 시스템에 걸쳐 문서가 600줄을 넘을 것 같으면 **개요 1개 + 세부 문서 N개**로 쪼갤지 검토한다(선례: 「이벤트 프레임워크」. 600줄 넘는 단일 문서도 5편 있다). 새 기능을 붙이는 사람이 볼 문서면 **실전 장**("이 장만 읽어도 새 X 를 붙일 수 있게", 복사용 체크리스트)을 Code 뒤에 둔다.

#### 퀴즈 문항 수 — 최소 5, 변화량에 비례해 늘린다

**퀴즈를 요청한 경우에만 아래 기준을 적용한다.** 사용자가 문항 수를 지정하면 그 수를 따른다.

**5는 하한이지 정원이 아니다.** 작은 변경도 5문항은 채우고, 변경이 클수록 늘린다. 선례 26편은 5~8문항이 69%, 10문항 이상 6편(큰 변경)이다. 예외는 2파일 +8/−1 변경에 3문항 1건뿐이다.

기준은 **본문 3장(Code)의 개념 절**이다. **절 하나당 최소 1문항**이 대응돼야 한다 — 그 절을
읽고도 못 푸는 문항이 없으면 그 절은 설명이 덜 된 것이고, 아무 문항도 안 걸리는 절이 있으면
독자가 그 부분을 건너뛰어도 자기가 뭘 놓쳤는지 모른다.

| 규모 | 문항 수 |
|---|---|
| 파일 15개 미만 & 1000줄 미만 | 5~8 |
| 그 이상 | 개념 절 수만큼, 최소 5 |
| 축을 나눠 문서를 여럿으로 쪼갠 경우 | **문서마다** 위 기준을 각각 적용 |

상한은 두지 않는다. 다만 **실시간 질의 테스트(4장)로 넘어갈 때만** 5개씩 끊어 낸다 —
문서에 15문항이 실려 있어도 한 번에 15개를 들이밀지 않는다.

### 2-1. 산출 형식 — 혼자 볼 것인가, 리뷰어에게 넘길 것인가

경로가 둘이고 **기본은 A**다. 사용자가 "PR에 넣을 것", "팀에 공유", "리뷰어가 읽을 것"이라고 하면 B로 간다.

| | **A. 개인 이해용 (기본)** | **B. 리뷰 동봉용** |
|---|---|---|
| 형식 | 자체 완결 HTML | 마크다운 |
| 위치 | `<scratchpad>/explain-diff/YYYY-MM-DD-<slug>.html` | 레포의 문서 디렉터리 (JobMaker `docs/Tech Records/`, LoveRevolutionMaker `docs/`). 큰 작업은 하위 폴더로 묶는다 |
| 파일명 | **날짜 접두 필수** | 그 레포의 문서 네이밍을 따르고, `(변경 해설)` 접미로 표시. 퀴즈를 넣을 때만 `(변경 해설·이해도 퀴즈)` |
| git | 레포 밖이라 무관 | **PR에 동봉한다** — 단 커밋은 사용자 승인 후 |

- A를 레포에 안 넣는 이유는 그대로다: 버전 관리를 오염시키고, 날짜 접두 없이 쌓이면 시간순으로 안 보인다
- B는 그 오염이 **의도된 것**이다. 리뷰어는 PR에서 바로 읽어야 하므로 문서가 변경과 같은 브랜치에 있어야 값이 있다. 전례: JobMaker PR #2307 `docs/Tech Records/안티치트 Track B 애셋 무결성 (변경 해설·이해도 퀴즈).md`
- B도 기본 3절을 따른다. 퀴즈를 요청했을 때만 A와 같은 `<details>` 정답 토글을 넣는다. 빠지는 건 `references/html-spec.md`의 레이아웃·색 규칙뿐이다
- B의 머리말에는 범위·기준 SHA·실측 날짜를 한 줄로 적는다. 퀴즈가 있을 때만 문항 수와 접힌 정답 안내를 붙인다. 골격은 `references/md-spec.md`
- PR 본문에는 이 문서 링크 옆에 **담긴 내용**을 적는다("타임라인·규모 표·퀴즈 6문항, 정답은 접어 두었다"). 리뷰 전에 읽어야 하면 본문 맨 앞 인용 블록에, 아니면 말미 `## 문서` 절에 둔다
- **PR 본문에서 이 문서로 거는 링크는 상대경로 금지.** `[…](docs/Tech Records/….md)` 는 GitHub 이 PR URL 기준으로 풀어 diff 뷰로 튄다(#2438 에 상대경로가 남아 있다). 반드시 head 브랜치의 blob 절대 URL 로: `https://github.com/<owner>/<repo>/blob/<head-branch>/<경로>` — 경로는 `urllib.parse.quote(path, safe="/")` 로 전부 퍼센트 인코딩하고 괄호 `()` 도 `%28 %29` 로 바꾼다(마크다운 링크가 `)` 에서 끊긴다). 사설 레포는 curl 이 404 를 내므로 `gh api repos/<owner>/<repo>/contents/<인코딩 경로>?ref=<head-branch> --jq .html_url` 로 검증한다
- 어느 쪽인지 애매하면 **묻는다.** 짐작으로 B를 고르면 승인 안 받은 파일이 레포에 생기고, 짐작으로 A를 고르면 리뷰어가 못 읽는다

### 3. 읽기 안내

문서 경로와 핵심 변화 한 줄을 주고 끝낸다. 요청한 퀴즈가 있을 때만 문서 말미의 접힌 정답을 안내한다.

**기본은 여기서 끝난다.** 채점을 **먼저 제안하지 않는다** — 문서의 퀴즈는 독자가 혼자 쓰는 자가 점검이다.
사용자가 **실시간 질의 테스트를 명시적으로 요청했을 때만** 아래 4장으로 간다.

A(HTML)는 Orca 환경이면 내장 브라우저로 열어주고(`orca-cli` 스킬 참조), 아니면 `open <경로>`(macOS)를 안내한다. B(마크다운)는 레포 경로를 주고 에디터나 GitHub 프리뷰로 읽으라고 안내한다 — 정답 토글이 접힌 채 보여야 정상이다.

### 4. 실시간 질의 테스트 — **요청이 있을 때만**

사용자가 직접 요청했을 때만 한다. "퀴즈 내줘", "실시간으로 물어봐줘", "이해했는지 확인해줘" 같은 명시적 요청이 없으면 **하지 않고, 제안하지도 않는다.**

문항은 문서 퀴즈 섹션에 실린 것을 그대로 쓴다. 정답도 그 토글 안에 있으니 별도 답안 키 파일을 만들지 않는다.

#### 묶어서 낸다

**한 문항씩 끊어 내지 않는다.** 사용자가 자기 속도로 답하게 한 번에 묶어 제시한다.

| 문항 수 | 방식 |
|---|---|
| 6개 이하 | 한 번에 전부 |
| 7개 이상 | **5개씩 끊어서.** 앞 묶음 채점이 끝나면 다음 묶음 (예: 12문항 → 5 + 5 + 2) |

번호를 붙여 내고, 답도 번호로 받는다. 일부만 답해도 답한 것만 채점하고 나머지를 다시 묻는다.

#### 채점

- 묶음의 답을 다 받은 뒤 **문항별로** `✅ 이해` / `◐ 부분` / `❌ 못함` 과 구체 피드백
- **◐ 는 "결과는 맞는데 메커니즘·비교 대상이 빠진 답"** 이다. 완답 기준을 알려 준다
- 아직 안 낸 묶음의 답을 피드백에서 흘리지 않는다
- 관대하게 매기지 않는다 — "비슷하게 말했으니 ✅"는 ◐다
- 채점이 끝나면 약한 문항이 다룬 **문서 섹션을 지목**한다. 재독 후 그 문항만 다시 묻는 것은 사용자가 원할 때만

## 실패 모드

- **형식을 안 정하고 씀** → 리뷰어에게 넘길 문서를 스크래치패드 HTML로 내면 PR에서 아무도 못 읽고, 개인용을 레포 md로 내면 승인 안 받은 파일이 레포에 남는다. 2-1을 먼저 정한다
- **디프만 읽고 씀** → 배경이 비고 "코드를 한국어로 옮긴 문서"가 된다. 주변 코드를 넓게 읽는 게 이 스킬 비용의 대부분이다
- **파일 순서대로 씀** → `git diff`와 같아진다. 개념 순서로 재배열
- **리뷰 코멘트가 본문에 섞임** → 독자가 이해 대신 판정 모드로 읽는다. 번외로 분리
- **퀴즈 정답을 토글 밖에 노출** → 답 찾기 읽기가 된다. 퀴즈는 문서 맨 끝에, 정답은 반드시 접힌 `<details>` 안에
- **규모를 안 재고 시작** → 5만 줄에서 컨텍스트가 터지거나 문서가 얕아진다. `--shortstat` 먼저
- **퀴즈가 암기 문제** → "저 함수 이름이 뭐죠?"는 이해를 안 잰다. 인과·조건·설계 의도를 묻는다
- **기본 설명에 퀴즈를 강제로 추가함** → 기본은 핵심 3절이다. 퀴즈를 요청한 경우에만 문항 수 기준을 적용한다
- **요청도 없는데 채점을 제안함** → 문서를 넘기고 끝내야 할 자리에서 시험을 들이민다. 4장은 요청이 있을 때만
- **문항을 하나씩 끊어 냄** → 사용자가 대화를 열 번 왕복해야 한다. 묶어서 내고, 7개 이상이면 5개씩
- **본문을 고치고 퀴즈는 그대로 둠** → 정답이 본문과 어긋난다(실사례: 「메타 보상 계층」 Q3 "수령 전체 거절" ↔ §3.5 "그 조각만 빼고 지급"). 절을 고치면 그 절을 근거로 삼은 문항·정답을 같이 고친다
- **의도된 한계를 번외에 넣음** → 독자가 설계상 선택을 결함으로 읽는다. 한계는 4절 「못 하는 것」, 우연히 발견한 결함만 번외
- **코드가 흑백이거나 JSON 이 한 줄로 뭉침** → 키워드·문자열·주석이 안 갈라져 읽기 힘들다(2026-10-08 피드백). HTML 은 `references/highlight.html` + 언어 클래스, 마크다운은 펜스 언어 태그. JSON 은 정렬해서 쓴다
- **줄임말·비유로 압축함** → "무엇이 열려 있나", "퍼진다", "문지기", "기록 존중" 같은 말은 쓴 사람만 안다(2026-10-08 피드백). 처음 쓰는 개념은 풀어 쓴 문장 + 예시 하나로, 상태·용어 이름은 표로 한 번 정의하고 문서 끝까지 같은 말을 쓴다(장/페이지/챕터, 깸/클리어 혼용 금지). 저장 전에 본문 텍스트만 뽑아 이런 표현을 훑는다
- **기준 SHA 없이 규모·실측을 적음** → 브랜치가 움직이면 숫자가 어디서 왔는지 모른다
- **문체가 섞임** → `~다` 평서로 통일. `~습니다`·`~함` 금지(`house-style.md`)
