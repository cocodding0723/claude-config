# orca-feature — 기능 코디네이터 열기·끝내기

사용자가 터미널 명령 대신 이 스킬로 코디네이터를 만든다. **사용자가 직접 부른 때에만 실행한다.** 세션이 스스로 판단해 코디네이터를 만들거나 끝내지 않는다(만든 뒤 지시·보고도 옮기지 않는다. 사용자가 코디네이터 창이나 그 Slack 스레드에 직접 지시한다).

스크립트: `~/orca/claude-config/hubs/scripts/feature_open.sh`, `feature_close.sh`. 옵션은 각 `--help` 가 기준이다.

## 인자

| 부르는 법 | 하는 일 |
|---|---|
| `/orca-feature` 또는 `list` | 열려 있는 기능 코디네이터 목록 |
| `open <기능 이름> [기준 브랜치]` | 티켓을 먼저 발급하고 이어서 코디네이터 열기 |
| `open <티켓> <기능 이름> [기준 브랜치] [영문 작업명]` | 이미 있는 티켓으로 코디네이터 열기 |
| `close <slug>` | 코디네이터 끝내기 |
| `sprint [YYYYMMDD]` | 이 스프린트의 시작일 보기·바꾸기(브랜치의 스프린트 폴더 이름에 씀) |

## 목록

```
cd ~/orca/board && bd list --type epic --status open,in_progress --label-pattern 'feature:*' --limit 0 --json \
  | jq -r '.[] | [.id, ((.labels // [])[] | select(startswith("feature:")) | sub("feature:"; "")), .title] | @tsv'
```

출력은 카드 번호, slug, 기능 이름 순이다. 표로 보여 준다. 그 밖의 조사는 하지 않는다.

## 열기

1. 인자를 맞춘다. 첫 낱말이 `LRM-숫자` 꼴이면 그 티켓을 쓴다. 아니면 티켓이 없는 것이므로 아래 「티켓이 없을 때」를 먼저 한다. 기능 이름은 필수다. 기준 브랜치를 안 줬으면 `dev` 로 하고 그렇게 했다고 말한다.
2. 브랜치 이름에 들어갈 것을 정한다. 게임 저장소 규칙(`CLAUDE.md` Branch Convention)은 `sprint-<스프린트 시작일>/<타입>-<티켓>-<작업명>` 이다.
   - **스프린트 시작일**: 오늘 날짜가 아니다. `~/.config/lrm-hubs/sprint-start`(한 줄 `YYYYMMDD`)에 정해 둔 값을 스크립트가 읽는다. 파일이 없으면 아래 「스프린트 시작일」대로 사용자에게 한 번 묻고 적어 둔다. 날짜를 지어내지 않는다.
   - **영문 작업명**(`--slug`): 사용자가 안 줬으면 기능 이름을 영문 소문자 2~4낱말로 옮긴다(우편함 → `mailbox`, 미션 카드 게이지 → `mission-card-gauge`). 허브 이름과 `/orca-feature close` 에 쓰는 이름이 된다.
   - **타입**(`--type`): 티켓이 버그면 `fix`, 그 밖은 `feat`. 설정·빌드는 `chore`, 구조만 바꾸면 `refactor`.
   - **여러 스프린트에 걸치는 모듈**이라고 사용자가 말했을 때만 `--long` 을 붙인다(`feature/<작업명>`).
3. 미리 보기: `feature_open.sh --ticket <티켓> --name "<이름>" --base <기준> --slug <작업명> --type <타입> --dry-run`. 사용자가 목표와 확인 방법을 말했으면 `--goal`·`--verify` 로 원문 그대로 함께 넘긴다(티켓이 이미 있어도 같다). 만들 것(브랜치·작업 공간·작업판 카드·코디네이터·Slack 스레드)을 그대로 보여 준다. 브랜치 이름과 작업명은 한 줄로 따로 짚어 준다.
4. 실행: 같은 명령에서 `--dry-run` 을 빼고 `--json` 을 붙인다. 사용자가 `open` 을 부른 것이 실행 승인이다. 훅이 확인 창을 띄우면 사용자가 누른다.
5. 결과 보고(3줄 이내): 코디네이터 작업 공간 경로, 기능 브랜치, 작업명. 그리고 "이제 코디네이터 창이나 그 기능의 Slack 스레드에 직접 지시"라고 알린다.

종료 코드가 0 이 아니면 스크립트가 낸 원인 줄을 그대로 전하고 멈춘다.

## 스프린트 시작일

브랜치의 스프린트 폴더(`sprint-YYYYMMDD/`)는 스프린트마다 하나다. 날짜는 그 스프린트의 시작일이고 사용자가 정한다.

- 보기: `cat ~/.config/lrm-hubs/sprint-start`. 없으면 "정해지지 않음"이라고 답한다.
- 바꾸기(`sprint 20261125` 또는 사용자가 날짜를 말했을 때): 여덟 자리 숫자인지 확인하고 그 한 줄만 파일에 쓴다. 이미 연 기능의 브랜치 이름은 바뀌지 않는다(기능 카드에 적힌 이름을 계속 씀).
- 파일이 없는데 `open` 을 불렀으면: 사용자에게 이번 스프린트 시작일을 묻는다. 참고로 Jira 의 진행 중인 스프린트 시작일을 함께 보여 줄 수 있다(`project = LRM AND sprint in openSprints()` 의 스프린트 칸). Jira 날짜와 팀이 쓰는 폴더 날짜가 다를 수 있으니 Jira 값을 그대로 쓰지 말고 확인받는다.
- Jira 의 진행 중인 스프린트가 파일의 날짜보다 뒤에 시작했으면(새 스프린트로 넘어간 것) 열기 전에 한 줄로 알리고 새 날짜를 확인받는다.

## 티켓이 없을 때 (11-18 사용자: 열 때 티켓도 같이)

게임 작업 티켓 발급은 승인 없이 한다(11-17). 여기서는 발급과 열기를 한 번에 잇는다.

1. **목표와 확인 방법을 한 번 묻는다.** 사용자가 이미 말했으면 묻지 않는다. 두 문장이다: 만들 것 한 문장, 끝났는지 확인할 방법 한 문장. 이 둘은 7단계의 접수(0단계)에 그대로 쓰인다. 사용자 원문을 고쳐 쓰지 않는다.
2. **`jira-issue` 스킬로 발급한다.** 그 스킬의 절차(중복 검사, 상위 결정, 초안 보여주기, 발급 전후 검사)를 그대로 따른다. 완료 기준 칸에 확인 방법을 넣는다. 비슷한 티켓이 이미 있으면 새로 만들지 말고 그 번호로 열지 묻는다.
3. 받은 티켓 번호로 「열기」 2번(브랜치 이름 정하기)부터 이어 간다.
4. 열 때 접수 내용을 함께 넘긴다: `feature_open.sh … --goal "<목표 원문>" --verify "<확인 방법 원문>"` (범위 밖을 말했으면 `--out`). 기능 카드 설명의 접수 칸에 적히고, 코디네이터는 거기서 읽어 7단계의 0단계를 시작한다.

개인·설정 작업(Jira 발급 금지 대상)이면 티켓을 만들지 않고 `orca-hub-create` 로 안내한다.

## 끝내기

보통은 부를 일이 없다. 카드가 모두 닫히고 코디네이터가 완료 검사(`board-done --epic`)를 통과하면 그 검사가 `feature_close.sh --yes` 를 이어서 실행해 스스로 정리된다. `close` 는 중간에 그만두거나 검사를 통과하지 못한 채 접을 때 쓴다.

1. 점검: `feature_close.sh --slug <slug>`. 아무것도 바꾸지 않는다. 종료 0 은 남은 것이 없다는 뜻, 4 는 남은 것이 있다는 뜻이다.
2. 점검 결과(진행 중 카드, 기능 브랜치에 합쳐지지 않은 워커 브랜치)를 보여 주고 **실행 여부를 묻는다.** 남은 것이 있으면 무엇이 버려지지 않고 남는지(브랜치·코드 변경이 있는 작업 공간은 지우지 않음)도 함께 말한다.
3. 사용자가 그러라고 하면 `feature_close.sh --slug <slug> --yes --json`. 워커 반납, 하위 작업 공간 정리, 코디네이터 창 닫기, 스레드 마무리 보고, 기능 카드 닫기가 한 번에 된다.
4. 결과 보고: 끝낸 것과 남긴 것(브랜치, 코디네이터 폴더).

`close` 는 되돌리기 어렵다(코디네이터 세션이 닫힌다). 점검 없이 `--yes` 부터 실행하지 않는다.

## 하지 않는 것

- 코디네이터에게 줄 지시문을 대신 보내지 않는다. 사용자가 원하면 맡길 문장(목표 + 확인 방법) 초안만 준다.
- 이미 살아 있는 코디네이터를 다시 띄우지 않는다(`feature_open.sh` 가 재사용한다).
- 티켓 없는 개인·설정 작업용 허브는 만들지 않는다. `orca-hub-create` 로 안내한다.
