## 절차

검사기: `python3 ~/.claude/skills/jira-issue/scripts/issue_check.py pre|post <json>` (입력 칸·점검 표 형식은 파일 머리말). MCP 호출은 에이전트가 하고 전후 검사는 스크립트가 맡는다.

1. **자료 모으기.** 대화·로그·스크린샷·녹화·커밋·PR·기획 문서·시트 행에서 템플릿 칸을 채울 근거를 찾는다. 코드 위치는 직접 grep 해서 파일:줄로 확인한다. 끝내 모르는 칸은 지우지 말고 `미확인`(무엇을 보면 알 수 있는지 한 줄).
2. **중복 검사:** `searchJiraIssuesUsingJql` 로 `project = LRM AND text ~ "핵심어"` 조회(핵심어 2~3개로 각각). 비슷한 게 있으면 링크를 보여주고 멈춘다.
3. **상위 결정(필수, 상위 없이 발급 금지).** 아래 「상위 결정」을 따른다.
4. **실제 단계 확인.** 아래 「실제 상태」를 따른다.
5. **초안 보여주기.** 템플릿으로 쓴 초안에 상위·상태·기한·담당을 함께 보여준다. 게임 작업 티켓 발급(생성·이슈 링크·에픽·상위 지정)은 승인 없이 바로 한다(사용자 11-17 "jira 티켓 발급 그냥 자동화하자"). 개인 업무(허브·워크스페이스 이름이 `[개인]`)는 Jira 발급 금지. 상태 변경은 여전히 승인 기록(결정 카드 `D-JST<이슈 키>` 의 1번 답 또는 계획 승인)이 있어야 하고, 없으면 `jira-approval-guard` 훅이 거부하며 정확한 번호를 알려 준다.
6. **발급 전 검사:** 입력을 JSON 으로 쓰고 `issue_check.py pre` 실행. 오류(종료 1)는 고친 뒤 다시. 경고(상태 불일치)도 발급 전에 해소한다.
7. **생성:** `createJiraIssue`(상위는 `parent` 필드). 첨부(스크린샷·녹화·로그)는 `uploadAttachmentToJiraIssue` 2단계(filePath → 받은 curl 실행). 관련 티켓은 이슈 링크로도 건다. 단계가 착수 전이 아니면 `getTransitionsForJiraIssue` → `transitionJiraIssue` 로 바로 전환.
8. **발급 뒤 자기 점검:** `getJiraIssue` 로 다시 읽은 값(키·상위·상태·기한·담당·근거, 에픽은 설명·하위 수)을 JSON 으로 쓰고 `issue_check.py post` 의 표를 그대로 보고한다. 하나라도 `비어 있음`·`고칠 것`이면 바로 `editJiraIssue`·전환으로 고치고 다시 점검한다. 응답이 끊겼으면 재생성 전에 같은 제목부터 검색.
9. **여러 개 몰아 발급:** 한 개씩 7~8 을 통과한 뒤 다음 티켓으로 간다. 먼저 전부 만들고 나중에 보지 않는다.

## 상위 결정

1. 같은 기능·키워드로 기존 에픽 후보를 검색한다(핵심어 2~3개 각각).
   - `project = LRM AND issuetype = 에픽 AND text ~ "매점" ORDER BY updated DESC`
   - `project = LRM AND issuetype = 에픽 AND statusCategory != Done AND labels = "라벨"`
   - 후보의 하위 확인: `project = LRM AND parent = LRM-숫자`
2. 제목·라벨·기존 하위를 보고 **한 줄 근거**로 고른다(예: "하위 3건이 같은 매점 새로고침 흐름"). 이름이 비슷한 것만으로 붙이지 않는다. 엉뚱한 에픽에 붙이는 것도 상위 없음과 같은 결함이다.
3. 맞는 에픽이 없으면 새 에픽을 만든다. 에픽 본문에 목표·범위·완료 기준을 쓰고, 하위 티켓 목록을 같이 만든다. 설명 없는 빈 에픽 금지.
4. 입력 JSON 에는 `parent: {key, reason}` 또는 `new_epic: {description, children}` 중 하나가 반드시 있어야 한다. 없으면 검사기가 거부한다.

## 실제 상태

기본값 `해야 할 일` 은 **착수 전 작업만**. 발급 시점에 아래 근거를 확인해 그 단계로 바로 전환한다.

| 근거 | 상태 |
|---|---|
| 브랜치·커밋 없음 | 해야 할 일 |
| 작업 브랜치·커밋 있음, PR 열림 | 진행 중 |
| dev 병합됨 | 확인 대기 |
| 사람이 확인 | 완료 (사람만 전환, 에이전트 금지) |

게임 저장소 `.github/workflows/jira-pr-status.yml` 자동화와 같은 규칙이다. **PR 열림은 진행 중**이며 확인 대기가 아니다.

- 확인: `git branch --list '*티켓키*'`, `git log --oneline 기준브랜치..HEAD`, `gh pr list --head 브랜치 --state all`.
- 입력 JSON `evidence` 에 `branch`·`commits`·`pr`·`merged` 를 넣는다. 브랜치 없는 조사·설계 작업은 `comment`(티켓의 작업 진행 댓글) 또는 `workspace`(이름에 티켓 번호가 든 Orca 작업 공간) 도 진행 근거로 인정한다. 근거와 상태가 다르면 검사기가 경고한다.
- **에픽은 하위 티켓 상태로 판정**: 하위 중 진행 중이 있거나 일부만 끝났으면 진행 중, 전부 확인 대기 이상이면 확인 대기, 전부 해야 할 일이면 해야 할 일. 하위가 0개면 판정 보류로 지적한다(하위 먼저 만든다). 점검 입력 `children` 에 하위 상태를 넣는다.
- LRM 상태 이름: `해야 할 일`·`진행 중`·`확인 대기`·`보류`(분류는 완료)·`완료`. `리뷰 중` 은 없다. `보류` 는 사람이 정하며 단계 검사에서 제외한다.
- **`완료` 는 사람만 전환한다.** 입력 상태가 `완료` 이거나, 병합 전인데 `확인 대기` 면 검사기가 오류로 거부한다. 이름이 바뀌면 `getTransitionsForJiraIssue` 로 확인하고 `issue_check.py` 의 `STAGE_STATUS` 를 고친다.

## 작업 댓글 (회사 원칙)

보고·결정·승인 요청·검수는 전부 Slack, 진행 기록은 Jira 와 Slack 둘 다 남긴다(사용자 11-25). 댓글을 달았다고 Slack 보고를 생략하지 않는다. Slack 쪽은 기능 허브면 작업판 카드 기록(전송기가 옮김), 그 밖의 허브면 `hub_report.py add --kind info|done` 을 쓴다.
모든 작업(수정·리뷰·충돌 해결·단계 진행·PR 게시)의 진행 상황을 단계마다 그 티켓에 댓글로 남긴다. 별도 승인 불필요.
순서: 무엇을 했나 → 왜 → 결과(바뀐 동작·검증) → 남은 일. 커밋 해시·PR 번호는 맨 아래.
로컬 작업 용어(허브·워커·코디네이터·작업 묶음 번호·결정 번호·내부 별명)는 풀어 쓴다. 팀원 누구나 이해하는 말로.

누가 읽나: QA·기획·아트가 티켓을 열었을 때 **댓글 하나로 원인·바뀐 것·확인 방법**을 알아야 한다(팀 선례 댓글 21건 분석, 11-25).

**마무리 댓글**(dev 병합·해결 때 1개. 앞선 댓글을 안 읽어도 되게 스스로 완결):

```
**원인**: 사용자가 본 증상 → 왜 그랬는지 1~2문장

**수정**: 바뀐 동작 1~3문장. 예외·그대로인 것은 괄호로

**PR**: [#번호](링크) (dev 머지)

**확인 방법**: 어느 화면에서 무엇을 하면 무엇이 보여야 하는지. 고친 경우와 원래대로여야 하는 경우를 함께. 몇 번 빌드부터인지

**남은 일**: 있을 때만. 후속 티켓 링크
```

- 새 기능은 `원인` 대신 `구현`. 화면이 여럿이면 `수정` 아래 화면별 불릿.
- `주의`(다른 화면에 영향)·`재발 방지` 는 있을 때만 덧붙인다.
- `확인 방법` 은 생략 금지. "검수 통과", "컴파일 통과" 는 확인 방법이 아니다. 못 정하면 `미확인` 과 이유.
- 400~700자. 넘으면 과정 설명부터 뺀다.
- 자료는 아래 「자료」 를 따른다.
- 커밋 해시는 PR 이 없을 때만 맨 아래.

**중간 댓글**(단계 진행): 첫 줄 굵게 `상태 · 바뀐 것`, 아래 무엇·왜·결과·남은 일 중 있는 것만 5줄 이내. 앞 댓글을 되풀이하지 않는다.
쓰지 않는 것: 작업 브랜치·워크트리·반입, 검수 횟수·모델 이름, 검사 항목 나열, "최종 확인 대기" 같은 우리끼리의 절차.

- 코드 변경 없이 닫는 경우(기획 반영·중복·재현 안 됨)도 이유를 댓글로 남긴다.
- 범위 밖으로 남긴 것은 "범위 밖, 별도 티켓 필요"로 한 줄 덧붙인다.
- 실제 화면 확인을 못 했으면 그렇다고 적는다.

## 자료 (화면·영상·도식·문서)

자료는 Slack 으로 보낸다(사용자 11-25). 허브는 `hub_report.py` 를 쓴다. 시안·구조안·도식·설명 문서는 티켓에 올리지 않는다.

티켓 첨부는 **마무리 댓글의 전후 화면·영상만, 선택**이다. QA 는 사용자 Slack 을 못 보므로 글만으로 확인 방법을 알기 어려울 때 붙인다.

- 올리는 법: `uploadAttachmentToJiraIssue` 로 올리고 `inlineFileId` 로 본문에 넣는다.
- 설명 한 줄: `시연 영상(17초, 에디터 녹화): 매점의 '라이벌 보기'로 라이벌 화면에 돌아옴`. 찍으려고 바꾼 값이 있으면 적는다.
- 파일 이름은 `LRM-번호-내용-전|후.확장자`.
- 올리기 전에 파일을 열어 본다. 계정·토큰·개인 대화·로컬 경로가 보이면 올리지 않는다.
- 컨플루언스 쓰기는 사용자 확인 뒤.
- 버그 발급 때 재현용 화면·로그 첨부는 「본문 템플릿」 의 근거 칸을 따른다.
