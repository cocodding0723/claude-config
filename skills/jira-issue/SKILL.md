# Jira 이슈 등록

원칙: **티켓만 읽고 일할 수 있게.** 받는 사람이 대화·로그를 다시 뒤지지 않고 재현하고, 착수하고, 끝났는지 확인할 수 있어야 한다.
길게 쓰되 문단으로 쓰지 않는다. 한 줄에 사실 하나, 섹션마다 불릿.

## 절차

검사기: `python3 ~/.claude/skills/jira-issue/scripts/issue_check.py pre|post <json>` (입력 칸·점검 표 형식은 파일 머리말). MCP 호출은 에이전트가 하고 전후 검사는 스크립트가 맡는다.

1. **자료 모으기.** 대화·로그·스크린샷·녹화·커밋·PR·기획 문서·시트 행에서 템플릿 칸을 채울 근거를 찾는다. 코드 위치는 직접 grep 해서 파일:줄로 확인한다. 끝내 모르는 칸은 지우지 말고 `미확인`(무엇을 보면 알 수 있는지 한 줄).
2. **중복 검사:** `searchJiraIssuesUsingJql` 로 `project = LRM AND text ~ "핵심어"` 조회(핵심어 2~3개로 각각). 비슷한 게 있으면 링크를 보여주고 멈춘다.
3. **상위 결정(필수, 상위 없이 발급 금지).** 아래 「상위 결정」을 따른다.
4. **실제 단계 확인.** 아래 「실제 상태」를 따른다.
5. **초안 보여주기.** 템플릿으로 쓴 초안에 상위·상태·기한·담당을 함께 보여준다. 등록 승인 전 생성 금지(요청에 "바로 올려"가 있거나 허브 선발급 규칙이 있으면 생략).
6. **발급 전 검사:** 입력을 JSON 으로 쓰고 `issue_check.py pre` 실행. 오류(종료 1)는 고친 뒤 다시. 경고(상태 불일치)도 발급 전에 해소한다.
7. **생성:** `createJiraIssue`(상위는 `parent` 필드). 첨부(스크린샷·녹화·로그)는 `uploadAttachmentToJiraIssue` 2단계(filePath → 받은 curl 실행). 관련 티켓은 이슈 링크로도 건다. 단계가 착수 전이 아니면 `getTransitionsForJiraIssue` → `transitionJiraIssue` 로 바로 전환.
8. **발급 뒤 자기 점검:** `getJiraIssue` 로 다시 읽은 값(키·상위·상태·기한·담당·근거, 에픽은 설명·하위 수)을 JSON 으로 쓰고 `issue_check.py post` 의 표를 그대로 보고한다. 하나라도 `비어 있음`·`고칠 것`이면 바로 `editJiraIssue`·전환으로 고치고 다시 점검한다. 응답이 끊겼으면 재생성 전에 같은 제목부터 검색.
9. **여러 개 몰아 발급:** 한 개씩 7~8 을 통과한 뒤 다음 티켓으로 간다. 먼저 전부 만들고 나중에 보지 않는다.

## 상위 결정

1. 같은 기능·키워드로 기존 에픽 후보를 검색한다(핵심어 2~3개 각각).
   - `project = LRM AND issuetype = 에픽 AND text ~ "매점" ORDER BY updated DESC`
   - `project = LRM AND issuetype = 에픽 AND statusCategory != Done AND labels = "라벨"`
   - 후보의 하위 확인: `project = LRM AND parent = LRM-숫자`
2. 제목·라벨·기존 하위를 보고 **한 줄 근거**로 고른다(예: "하위 3건이 같은 매점 새로고침 흐름"). 이름이 비슷한 것만으로 붙이지 않는다. 엉뚱한 에픽에 붙이는 것도 상위 없음과 같은 결함이다.
3. 맞는 에픽이 없으면 새 에픽을 만든다. 에픽 본문에 목표·범위·완료 기준을 쓰고, 하위 티켓 목록을 같이 만든다. 설명 없는 빈 에픽 금지.
4. 입력 JSON 에는 `parent: {key, reason}` 또는 `new_epic: {description, children}` 중 하나가 반드시 있어야 한다. 없으면 검사기가 거부한다.

## 실제 상태

기본값 `해야 할 일` 은 **착수 전 작업만**. 발급 시점에 아래 근거를 확인해 그 단계로 바로 전환한다.

| 근거 | 단계 | 상태 |
|---|---|---|
| 브랜치·커밋 없음 | 착수 전 | 해야 할 일 |
| 작업 브랜치 또는 커밋 있음 | 진행 | 진행 중 |
| PR 게시됨 | 리뷰 | 리뷰 중 |
| PR 병합됨 | 완료 | 완료 |

- 확인: `git branch --list '*티켓키*'`, `git log --oneline 기준브랜치..HEAD`, `gh pr list --head 브랜치 --state all`.
- 입력 JSON `evidence` 에 `branch`·`commits`·`pr`·`merged` 를 넣는다. 근거와 상태가 다르면 검사기가 경고한다.
- 상태 이름은 사이트 워크플로 값이다. 이름이 다르면 `getTransitionsForJiraIssue` 로 실제 이름을 확인하고 `issue_check.py` 의 `STAGE_STATUS` 를 고친다.

## 작업 댓글 (회사 원칙)

모든 작업(수정·리뷰·충돌 해결·단계 진행·PR 게시)은 그 티켓에 진행 단계마다 댓글로 자세히 남긴다. 별도 승인 불필요.
순서: 무엇을 했나 → 왜 → 결과(바뀐 동작·검증) → 남은 일. 커밋 해시·PR 번호는 맨 아래.
로컬 작업 용어(허브·워커·코디네이터·작업 묶음 번호·결정 번호·내부 별명)는 풀어 쓴다. 팀원 누구나 이해하는 말로.

수정을 마친 댓글의 최소 형식:

```
원인: 한 줄
수정: 한 줄
커밋: 브랜치 · 해시 (PR 있으면 #번호)
확인: QA 가 확인하는 방법 한 줄
```

- 코드 변경 없이 닫는 경우(기획 반영·중복·재현 안 됨)도 이유를 댓글로 남긴다.
- 범위 밖으로 남긴 것은 "범위 밖, 별도 티켓 필요"로 한 줄 덧붙인다.
- 실제 화면 확인을 못 했으면 그렇다고 적는다.

- 점검 표 없이 "발급 완료" 보고
- 섹션 삭제. 빈 칸은 `미확인` 또는 `해당 없음`

- 토큰·uid·이메일 같은 계정 정보 포함
