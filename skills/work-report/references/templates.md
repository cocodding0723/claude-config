# work-report 템플릿

골격 A·B는 실제 승인된 보고서에서 추출했고, 골격 C는 A의 파생이다. 섹션 제목은 작업 내용에 맞게 바꾸되 **순서와 역할은 유지**한다.

## 골격 A — 항목 카탈로그형

독립 항목 N개를 독자가 골라 적용하는 작업 (최적화 모음, 개선 항목 정리). 원형: 「인게임 GC 최적화 — 항목별 정리」.

```markdown
# [실행 기록] <작업명> — 항목별 정리

> [!success] <한 줄 결론 — 무엇이 문제였고 무엇이 가장 컸는지>
> <대표 수치 before → after, bold>

<대표 이미지 1~2장 + 캡션 (노션용만)>

<이 문서의 위상 — 선행 문서가 있으면 관계 한 줄>

## 0. 이 문서를 읽는 법
전부 적용하지 않을 수 있다는 전제. 독립 적용 절 안내. 상세는 효과순 배치 안내.
시간 없는 독자를 위한 최단 경로 (§1.3 추천 조합만 봐도 된다).

---

## 1. 요약
### 1.1 무엇이 문제였나   ← 원인 순위표: | 순위 | 원인 | 항목 | 실측 근거 |
### 1.2 항목 일람          ← 아래 "일람표 템플릿"
### 1.3 추천 조합          ← 조합 + 각 항목을 넣은/뺀 사유

---

## 2. 적용 전 확인사항     ← 독자가 잘못 적용하게 만들 함정만 (환경 분기, 빌드 타입 차이 등)

---

## 3. 항목 상세            ← 효과 큰 순. 아래 "항목 상세 템플릿"
   > [!info] 도입부 내비게이션 — 효과순 배치·제목 클릭 시 표 복귀·해시 클릭 시 커밋 이동 안내
   ...
   ---
   > [!note] 이 밑으로는 중요하지 않은 항목입니다 — 적용하지 않아도 무방합니다
   ...

---

## 4. 하지 않기로 한 것    ← 기각·미착수 + 사유 표

---

## 5. 부록 (TMI)           ← 결정에 불필요한 참고 정보 전부: 계측 인프라, 패턴 관찰,
                              탐색 서사, 측정 환경 상세. 본문에 두지 않는다
```

## 골격 B — 트랙 종합형

작업 축(Track A/B/C 등) 단위로 종합 보고하는 작업. 원형: 「안티치트 작업 보고서」. 사용자가 직접 지정한 구조: **배경 → 커밋 표 → 각 항목별/그룹별 설명**.

⚠️ 이 골격은 **요약 문서다**. 원형은 섹션 구성은 승인받았지만 장황하다는 지적을 받았다 — 섹션은 유지하되 각 섹션은 표·요점 판단 근거까지만 쓰고, 깊이는 트랙별 상세 문서로 위임한다 (SKILL.md 두 층 설계).

```markdown
# <작업명> 보고서

브랜치 `<브랜치명>` · base `<베이스 해시>` · <YYYY-MM-DD>      ← 제목 직하 메타 라인

# 1. 배경
## 왜 하는가
## <위협/문제> 등급과 담당 트랙     ← 아래 "등급 정의표". 여기 선언한 축은 이후 전 섹션에서 유지
## 지금 되는 것과 안 되는 것
## 검증 상태                        ← 무엇으로 어디까지 검증했고 무엇이 미검증인지

---

# 2. 커밋
## Track A — <이름> (N건)           ← 트랙별 커밋 표: | 커밋 | 요약 | 규모 | 영향성 | 리스크 |
## Track B — <이름> (0건이어도 유지)
## Track C — <이름>
## 문서 등 부수 커밋                ← 축약형: | 커밋 | 요약 | 규모 | (영향성·리스크 컬럼 생략)
## 미착수 / 기각                    ← | 항목 | 상태 | 사유 | — 상태에 `실질 불가` 허용

---

# 3. 트랙별 설명                    ← 선언한 축 순서 그대로. 요점 판단 근거만 — 깊이는 위임
## Track A / Track B / Track C      ← 트랙당 몇 문단 이내, 말미에 `→ 상세: [트랙 문서](경로)` 링크

---

# 4. 동작이 달라지는 지점 — 전량    ← 아래 "변경점 표". 끝에 "확인했으나 변경하지 않은 것" 문단

---

# 5. 번외 — 범위 밖 발견            ← 본문과 절대 섞지 않는다

---

# 6. 남은 작업                      ← 머지 전 / 배포·운영 / 후속 / 결정 필요로 구분

---

**관련 문서** — [문서A](경로) · [문서B](경로)                   ← 최하단 푸터
```

골격 B 전용 표 3종 (원형에서 추출 — 컬럼 유지):

```markdown
<!-- 등급 정의표 (§1). 등급 문자와 트랙 문자가 별개 체계면 그 사실을 표 옆에 명시 -->
| 등급 | 위협 | 담당 | 상태 |
```

## 골격 C — PR 본문형

PR/MR 본문에 넣는 **한 페이지** 요약. **골격 A의 축약형이다** — 효과순 배치, 실측 수치, 무결성 규칙은 A를 그대로 상속하고, 분량 상한이 최우선 규율로 추가된다. GitHub 전용이 아니다 — GitLab 등 다른 프로바이더 MR에도 같은 형식을 쓴다.

**분량 상한**: 렌더링 기준 스크롤 한두 번 안. 넘칠 것 같으면 문장을 압축하는 게 아니라 **위임한다** — 상세 보고서(골격 A/B 문서)·이슈·후속 코멘트로 빼고 링크만 남긴다. 골격 A의 2층(더보기)이 여기서는 전부 **링크**다.

```markdown
## 요약
<무엇이 문제였고 무엇을 했는지 2~4줄. 대표 수치 before → after **bold**>

## 변경 목록
| # | 대상 | 변경 | 효과 | 리스크 |
|---|---|---|---|---|
<효과 큰 순, 상위 bold. 커밋 컬럼은 생략 — PR이 커밋 목록을 이미 보여준다.
 특정 커밋을 짚어야 할 때만 해시 표기.
 # 컬럼 셀에는 맨숫자만(3). 본문에서 그 항목을 가리킬 때도 `#3` 코드 표기나 "3번">

## 검증
<무엇으로 어디까지 검증했고 무엇이 미검증인지 — 리뷰어가 재현할 수 있게 한 단락>

## 리뷰 포인트
<리뷰어의 판단을 요청하는 지점만 2~3개. 없으면 섹션 삭제>

## 범위 밖 / 후속
<이 PR에서 안 한 것과 사유. 번외 발견은 본문에 섞지 말고 여기 한 줄 + 별도 이슈 링크>
```

- 섹션이 비면 빈 채 두지 말고 **삭제한다** — 한 페이지 예산에서 빈 섹션은 낭비다 (골격 A/B의 "0건도 섹션 유지" 규칙은 장문 보고서용이므로 여기엔 적용하지 않는다)
- `<details><summary>` 접기는 PR 본문에서 허용 — 로그·벤치마크 원문처럼 참고용 덩어리에 쓴다
- 상세 항목 번호(`#N`)는 변경 목록 표 안에서만 쓴다 — 본문이 짧아 문서 내 앵커 드릴다운은 없다
- **맨몸 `#숫자` 금지** (SKILL.md 무결성 규칙 7) — 트래커가 PR/이슈 번호로 자동 링크한다. 항목 번호는 코드 표기(`` `#3` ``)로 감싸거나 `3번`·`항목 3`으로 쓰고, 맨몸 `#숫자`는 진짜 PR·이슈를 가리킬 때만 쓴다. 표 셀의 맨숫자(`3`)와 `#` 헤더 칸은 안전하다. 골격 A/B 문서를 PR 본문으로 옮겨 붙일 때도 이 변환을 거친다
- 항목이 1~2개뿐이면 표를 생략하고 요약에 합쳐도 된다 — 표가 본문보다 큰 배보다 배꼽을 만들지 않는다

## 일람표 템플릿

```markdown
> [!info] 표의 #을 누르면 해당 문단으로, 커밋 해시를 누르면 해당 커밋으로 이동합니다.
> 효과: <판정 기준 한 줄>. 리스크: <판정 기준 한 줄>.

| # | 대상 | 상태 | 세대/단계 | 커밋 | 효과 | 리스크 | 독립 적용 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **13** | **<효과 최대 항목>** | 완료 | 6 | [`f88c2d97c`](<원격URL>/commit/f88c2d97c) | **최대** | 없음 | ✅ |
| 10 | <무효가 된 항목> | ⚠️ **무효** | 4 | [`f4768b739`](...) | **0** | — | #14로 대체 |
| 5 | <기각 항목> | **기각** | — | — | 0.05% 미만 | 중 | — |
| 4 | <미착수 항목> | 미착수 | — | — | 중 | 낮음 | ✅ |
```

- 정렬: 효과 큰 순 → 무효/실효 없음 → 기각 → 미착수. 상위 항목 bold
- `세대/단계`: 빌드 세대·작업 라운드 등 프로젝트에서 실제 쓰는 단위. 없으면 컬럼 삭제
- 커밋 링크는 **푸시 확인 후에만**. 미푸시면 `` `해시` ``만 적고 표 위에 사유 명시 (SKILL.md 무결성 규칙 1)
- 독립 적용 컬럼: ✅ / 의존 대상 표기 (`#N 선행 필요`, `#N로 대체`) — 선행 필수 커밋은 별도 강조

## 항목 상세 템플릿

```markdown
### 3.1 #13 · <항목명> — <한 줄 특징, 예: 최대 효과>

**완료** · 6세대 · `f88c2d97c`

**대상** <파일·함수>

**문제**
<코드 스니펫 + 실측 수치. "왜 이게 문제인가"를 독자가 재검증할 수 있게>

**변경**
<무엇을 어떻게 바꿨나. 표가 명확하면 표로>

**왜 <이 방법>이고 <기각한 대안>이 아닌가**   ← 대안이 자명하지 않을 때만
<기각 사유 — 수치나 구조적 근거로>

**리스크** <수준 + 깨질 수 있는 시나리오. "중" 이상이면 검증 항목 목록 필수>
**독립 적용** ✅/조건 · **#N과 시너지/의존** — <관계 설명 한 줄>
```

## 상태 어휘 (통일)

| 상태 | 의미 |
| --- | --- |
| `완료` | 적용됨, 효과 확인 |
| `⚠️ 무효` | 적용됐으나 런타임 효과 없음 (사유·대체 항목 필수) |
| `⚠️ 실효 없음` | 현재는 효과 없지만 향후 조건 충족 시 유효 |
| `기각` | 검토 후 하지 않기로 결정 (사유 필수) |
| `실질 불가` | 하려 했으나 기술적으로 불가능 (근거 필수) |
| `미착수` | 후순위로 미룸 |

등급 정의표의 ✅/📋 이모지 상태는 그 표 전용이다 — 일람표·커밋 표에는 위 어휘를 쓴다.

## 노션 이원화 체크리스트

0. 산출 폴더·파일명 관례: 보고서 폴더는 `YYYY-MM-DD <작업명>/`, 노션용 파일은 `<이름> (노션용).md` 접미
1. 노션용 작성: 이미지 `images/` 상대경로, 캡션은 이미지 아래 *이탤릭* 한 줄, callout `> [!success|info|tip|warning|danger|note]`. 핵심 수치는 callout 없는 일반 인용구 `> **...**`로도 강조 가능
2. git용 파생: 노션용에서 이미지·이미지 캡션만 제거, 본문 동일. callout은 GitHub 어휘로 매핑 (SKILL.md 산출 워크플로우 참조)
3. `.git/info/exclude`에 노션용 md와 `images/` 추가 (커밋 금지)
4. 노션 업로드용: 노션용 md + images를 zip으로 묶어 전달
5. 이후 수정은 **양쪽 동시 반영** — 어긋난 채 두지 않는다
6. 커밋·푸시는 사용자 지시가 있을 때만
