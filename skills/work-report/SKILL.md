# work-report — 작업 보고서 양식·워크플로우

> **11-04 개정 (사용자 결정, 아래 기존 규칙보다 우선)**
> 1. **산출물은 자체 완결 HTML.** 스타일·다크 모드·좁은 화면은 `~/.claude/skills/structure-change-doc/templates/doc.html` 의 `<style>` 을 그대로 쓴다. 마크다운은 저장소에 커밋되는 규약 문서일 때만.
> 2. **맨 위 순서:** 쉬운 말 3줄 요약(무엇을 했나 / 왜 / 사용자가 할 일) → 🙋 결정 카드 → 일람표 → 상세(접힘).

> 4. **쉬운 말:** 본문에 고유명사(클래스·파일·티켓·커밋·캐릭터 실명)와 AI 내부 기호(P1·fixup·ctx_ 등)를 쓰지 않는다 — 표의 "참고" 열·맨 아래 접힌 참고 칸에만. 헤더 이모지 🙋 결정 · 🛠️ 할 일 · ✅ 완료 · 🔄 진행 · ⚠️ 문제 · 📄 문서.
> 5. **화면이 바뀐 작업:** structure-change-doc 의 `image_diff.py`(바뀐 곳 상자)·`screen_flow.sh`(장면 띠·GIF)를 쓴다. 영상 원본은 HTML 에 넣지 않고 Slack 에 따로 올린다.
> 6. **검수 3단계:** 1차 다른 Claude 워커의 처음 보는 사람 독자 검수 + `python3 ~/.claude/skills/structure-change-doc/scripts/check.py --report <문서>` → 2차 Fable(사실·논리) 또는 astra(시각 렌더) → 3차 사용자. 검수 기록을 참고 칸에.
> 7. 기존의 `#N` 번호·독립 적용·선행 커밋·두 층 구조·효과 큰 순 배치 규칙은 그대로 유지한다.
> 8. **인과 규칙(11-05, 최우선):** 결정 카드·표 칸·요약은 '지금 문제 → 그래서 하는 조치 → 그러면 달라지는 것'으로 잇는다. 추천 이유는 다른 선택지와의 비교로 끝내지 않는다. 그 차이가 왜 중요한지, 즉 무엇이 막히거나 깨지는지를 쓴다.

문체(평서 `~다`)·머리말·반복 장치는 `~/.claude/skills/tech-record/references/house-style.md`를 따른다. 설계·계획·계약 문서는 `tech-record`, 변경 해설은 `explain-diff`.

여러 커밋·여러 항목에 걸친 작업 결과를 남에게 넘길 수 있는 문서로 만드는 규칙. 문서 골격과 표 템플릿은 `references/templates.md`에 있다 — 문서를 쓰기 전에 반드시 읽는다.

## 독자 전제 — 모든 규칙의 뿌리

**독자는 이 문서를 보고 "무엇을 받아들일지" 결정하는 사람이다. 전부 적용하지 않을 수 있다.**

**읽기 구조는 두 층이다 — "필요한 것만 보기 → 보고 싶은 건 더보기".** 1층(결론·표·추천 조합)만 읽어도 결정할 수 있어야 하고, 나머지 전부는 독자가 원할 때만 여는 더보기다. 섹션을 아무리 잘 나눠도 전부 본문에 눌러담으면 장황한 실패작이다.

- 모든 항목에 `#N` 번호를 붙인다. 문서 전체에서 번호로 상호 참조한다
- 항목마다 **독립 적용** 가능 여부를 명시한다. 선행 필수 커밋·항목 간 의존성·시너지는 반드시 표기한다 — 이것 없이 항목만 떼가면 의도대로 안 된다
- 시간이 없는 독자를 위해 **추천 조합**을 제시한다. 제외한 항목도 사유를 적는다 ("간단하지만 추후 휴먼 에러 우려로 제외" 같은 식)

이 절의 장치(#N 번호·독립 적용 절·추천 조합)는 **항목 카탈로그형** 골격의 것이다. **트랙 종합형**에서는 선택 단위가 항목이 아니라 커밋이므로, 같은 목적을 커밋 표의 영향성·리스크 컬럼과 선행 필수 커밋 표기로 달성한다 — 카탈로그형 장치를 억지로 이식하지 않는다.

## 문서 구조

**배경 → 일람표 → 항목별/그룹별 상세** 순서가 기본. 세 가지 골격이 있다 (상세는 templates.md):

- **항목 카탈로그형 (골격 A)** — 독립 항목 N개를 선택 적용하는 작업 (최적화, 개선 모음). **기본형** — 다른 골격 판단이 서지 않으면 이걸 쓴다
- **트랙 종합형 (골격 B)** — 작업 축(Track A/B/C 등) 단위로 종합 보고하는 작업
- **PR 본문형 (골격 C)** — PR/MR 본문에 넣는 **한 페이지** 요약. 골격 A의 축약형 — 구조·규율은 A를 상속하되 분량 상한이 최우선 규율이다. 산출물은 파일이 아니라 PR/MR 본문 텍스트다 (사용자가 파일로도 달라고 할 때만 저장). 항목 번호 표기는 무결성 규칙 7을 따른다 — PR/MR에서는 맨몸 `#숫자`가 금지다

**다룬 축은 전부 섹션을 유지한다.** 구현이 0건인 트랙도 빼지 말고 "구현 0건"과 그 이유를 적는다 — 섹션이 사라지면 독자는 "빠뜨렸나?"부터 의심한다. 순서는 전체 설명 → A → B → C처럼 선언한 축 순서 그대로.

**트랙 종합형도 두 층 규율을 따른다.** 종합 문서 본문은 표와 요점 판단 근거까지만 — 트랙별 깊이는 별도 트랙 문서로 위임하고 `→ 상세:` 링크로 잇는다. 섹션이 많다는 이유로 각 섹션을 길게 쓰지 않는다.

상세 항목은 **효과가 큰 순서로 배치**하고, 중요도가 꺾이는 지점에 `---` 수평선 + `> [!note]` callout을 함께 넣는다: "이 밑으로는 중요하지 않은 항목입니다 — 적용하지 않아도 무방합니다."

최상위 섹션(대구획) 사이에는 `---` 수평선을 넣는다.

## 일람표

**항목 카탈로그형**의 심장 (트랙 종합형의 커밋 표는 templates.md 골격 B의 별도 스펙을 따른다). 컬럼 구성 (프로젝트 맥락에 안 맞는 컬럼은 빼되, 나머지는 유지):

```
| # | 대상 | 상태 | 세대/단계 | 커밋 | 효과 | 리스크 | 독립 적용 |
```

- 효과가 큰 순으로 정렬, 상위 항목은 **bold**
- 상태 어휘: `완료` / `⚠️ 무효` / `⚠️ 실효 없음` / `기각` / `미착수` — **실패·무효 항목도 표에서 지우지 않는다.** 왜 무효인지가 독자에게 정보다
- **효과·리스크의 판정 기준을 표 근처에 명시한다** (예: 효과 = 막는 피해·절감량의 실질 크기, 리스크 = 정상 경로가 깨질 가능성). 기준 없는 "큼/작음"은 판정이 아니라 인상이다
- 표의 `#`는 해당 상세 문단으로, 상세 문단 제목은 표로 되돌아가는 앵커로 연결한다 — GitHub 렌더링 기준 헤딩 자동 앵커를 쓴다 (예: `[13](#31-13--항목명)`, 한글·특수문자는 소문자화·공백→`-` 규칙). 노션 임포트에선 페이지 내 앵커가 유지되지 않을 수 있으니 그 경우 `§3.1` 식 번호 참조만으로 대신한다

## 항목 상세

항목마다: **상태 · 세대/단계 · 커밋 해시** 한 줄 → **문제**(실측 수치·코드 스니펫 포함) → **변경** → 필요시 **왜 이 방법인가**(기각한 대안과 이유) → **리스크**(검증 항목 포함) → **독립 적용**(의존성·시너지).

## 두 층 설계 — 본문 다이어트와 더보기

**1층(본문)에는 독자의 적용·검토 결정에 필요한 정보만 딱딱 남긴다.** 나머지는 전부 2층(더보기)으로 내린다. 더보기 수단은 셋 — 문서 성격에 맞는 것을 고른다:

1. **문서 내 드릴다운** — 표의 앵커로 상세 문단 이동 (항목 카탈로그형 기본)
2. **별도 문서 위임** — 종합 문서는 요점까지만 쓰고 깊이는 트랙/주제별 문서로 빼서 `→ 상세:` 링크 (트랙 종합형 기본)
3. **부록(TMI)** — 흥미롭지만 결정을 바꾸지 않는 정보는 문서 최하단 부록으로 옮기거나 삭제

git 전용 문서라면 `<details><summary>` 접기도 더보기로 쓸 수 있다 — 단 노션 임포트에서 토글로 변환되지 않을 수 있으니 이원화 문서에는 쓰지 않는다.

부록행 후보:

- 계측·도구 인프라 상세 (마커 이름 목록, 프로파일러 설정)
- 탐색 과정 서사 ("처음엔 X를 의심했으나...")
- 측정 환경 잡설, 재현 절차의 세부
- 다음 작업을 위한 패턴 관찰·단서 모음

요약(1장)과 상세(3장)에 같은 내용을 두 번 쓰지 않는다 — 요약은 표와 추천 조합, 상세는 근거. 겹치면 상세 쪽만 남기고 요약에선 참조한다.

## 무결성 규칙

1. **죽은 링크 금지.** 미푸시 커밋에 원격(GitHub 등) URL을 달면 404다. 푸시 여부를 `git branch -r --contains <hash>` 등으로 확인하고, 미푸시면 해시만 코드 표기로 적은 뒤 표 상단에 "미푸시라 링크 없음, 푸시 후 전환" 사유를 명시한다. 링크를 달 때는 현재 레포의 실제 원격 URL(`git remote get-url origin`) 기준으로 만든다
2. **수치는 실측만.** 규모는 `git show --shortstat`, 성능은 프로파일러 캡처 등 출처가 있는 값만 적는다. 추정값이 불가피하면 추정임을 명시한다. 실측 근거는 일람표나 항목에 같이 적는다
3. **용어는 실존하는 것만.** 코드베이스·팀에 실재하지 않는 개념어를 발명하지 않는다 (예: 코드에 없는 "마스터데이터" 같은 분류어). 쓰기 전에 그 용어가 코드·문서에 실제로 존재하는지 확인한다
4. **정정은 삭제가 아니라 기록.** 이전 서술이 틀렸으면 지우고 다시 쓰는 게 아니라 callout으로 남긴다: `> [!note] 근거 정정 — 커밋 메시지의 X 주장은 이후 <해시>에서 정정됐다. 실제로는 Y다.` 커밋 메시지가 이미 틀린 채 남았다면 그 사실도 적는다
5. **레퍼런스를 단다.** 외부 사실 주장(엔진·프레임워크 동작)엔 공식 문서 링크, 코드 언급엔 `파일:줄` — 푸시된 커밋이면 커밋 고정 permalink(`<원격URL>/blob/<해시>/<파일>#L<줄>`)가 더 좋다(브랜치가 움직여도 안 깨진다). 관련 문서엔 상호 링크: 그룹 설명 말미에 `→ 상세: [문서](경로)`, 문서 최하단에 `**관련 문서** — ...` 푸터. 독자가 "정말?"을 스스로 확인할 경로를 남긴다
6. **범위 밖 발견은 섞지 않는다.** 작업 목적에서 벗어난 발견·제안은 **번외** 섹션으로 분리한다. 본문 항목과 섞이면 범위가 흐려진다
7. **PR/MR에 올리는 텍스트에서 `#숫자`를 맨몸으로 쓰지 않는다.** PR·MR 본문, 리뷰·이슈 코멘트, 커밋 메시지 — 트래커가 렌더링하는 모든 곳에서 `#12`는 **PR/이슈 번호로만** 쓴다. 항목 번호로 적으면 GitHub·GitLab이 무관한 이슈로 자동 링크하고, 그 이슈에 역참조 알림까지 남는다(취소 불가). 항목 번호는 백틱으로 감싸(`` `#3` ``) 코드 표기로 쓰거나, `3번`·`항목 3`·`No.3`처럼 다른 형태로 적는다. 표의 `#` 헤더 칸과 셀의 맨숫자(`3`)는 자동 링크되지 않으니 그대로 둬도 된다. 저장소 안 md 파일(골격 A/B)에는 적용되지 않는 규칙이지만, **그 문서를 PR 본문으로 옮겨 붙일 때는 옮기면서 변환한다**

## 커밋 재정리 선행 확인

커밋 표를 만들기 전에 히스토리가 보고 단위(문제 단위)로 읽히는지 본다. 다음이면 바로 보고서를 쓰지 말고 **사용자에게 먼저 묻는다** — 문제 단위로 커밋을 재정리(스쿼시·분할·재배열)한 뒤 쓸지, 히스토리는 그대로 두고 문서에서만 묶을지:

- **너무 복잡** — 한 문제의 수정이 여러 커밋에 흩어짐(fix-up·오타 수정 등), 무관한 문제가 한 커밋에 섞임
- **너무 적음** — 여러 문제가 커밋 하나에 뭉쳐 표의 행과 문제 단위가 안 맞음

푸시 여부를 먼저 확인하고(`git branch -r --contains <해시>`, 무결성 규칙 1과 동일) 분기한다:

- **전부 미푸시 로컬 커밋** — 재정리는 안전하다. 승인받으면 rebase로 정리한 뒤 커밋 표를 만든다
- **푸시된 커밋 포함** — **위험을 함께 고지한 뒤 묻는다**: 재정리에는 force-push가 필요하고, 같은 브랜치를 받은 사람들의 히스토리가 갈라지며, 기존 커밋 해시를 참조하는 링크(리뷰·CI·문서)가 전부 죽는다. 사용자가 위험을 알고도 지시할 때만 진행하고, 아니면 히스토리는 두고 문서 층위 묶음으로만 정리한다

## 산출 워크플로우

**기본 산출은 git용 1부** (이미지 없음). 저장 위치는 프로젝트의 보고서 관례 폴더(예: `docs/` 하위의 기존 보고서 폴더)를 먼저 찾아 따르고, 없으면 사용자에게 위치를 확인한다.

**노션 공유 요청 시 이원화한다:**

- **노션용**: 이미지 포함(`images/` 폴더 + 상대경로), callout은 `> [!success]` `> [!info]` `> [!tip]` `> [!warning]` `> [!danger]` `> [!note]` 문법 — 노션 임포트에서 callout으로 변환된다. md + images를 zip으로 묶어 업로드용으로 전달한다
- **git용**: 노션용에서 이미지·이미지 캡션만 뺀 본문 동일본. callout은 GitHub 지원 어휘로 매핑한다 — `success`/`info`→`NOTE`, `tip`→`TIP`, `warning`→`WARNING`, `danger`→`CAUTION`, `note`→`NOTE` (GitHub는 NOTE/TIP/IMPORTANT/WARNING/CAUTION만 렌더링, 나머지는 평문 인용구로 깨진다)
- **이미지와 노션용 md는 git에 커밋하지 않는다** — `.git/info/exclude`에 파일 단위로 추가 (레포 오염 없이 로컬 제외)
- 한쪽을 수정하면 반드시 다른 쪽에도 반영한다 — 두 파일이 어긋나면 어느 쪽이 진실인지 알 수 없게 된다

**커밋·푸시는 사용자가 지시할 때만 한다.** 보고서를 만들었다고 커밋까지 하지 않는다.

## 이 양식의 실패 모드 (전부 실제 발생 사례)

- 트랙 하나를 조용히 누락 → "B는 왜 빠짐??" — 0건이어도 섹션 유지
- 미푸시 커밋에 GitHub 링크 → 전부 404 — 푸시 여부 먼저 확인
- 존재하지 않는 용어로 분류 → 독자가 개념 실존부터 의심 — 용어 실사
- 추정 수치를 실측처럼 서술 → 신뢰 전체가 흔들림 — 출처 없는 숫자 금지
- 참고 정보가 본문에 산재 → 문서가 길어져 정작 결정 정보가 묻힘 — TMI 부록 격리
- 트랙 종합형이 장황해짐 → 섹션은 잘 나눴는데 전부 본문에 담아 읽기 부담 — 1층은 결론·표·요점만, 깊이는 더보기(앵커·별도 문서·부록) 뒤로
- PR 본문에 항목 번호를 `#3`으로 적음 → 무관한 이슈 #3으로 링크되고 그쪽에 역참조 알림까지 감 — `#숫자`는 PR·이슈 번호 전용, 항목 번호는 코드 표기나 `3번`
