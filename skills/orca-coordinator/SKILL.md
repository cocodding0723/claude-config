# Orca 중앙 코디네이터

중앙은 사용자 소통·범위·배정·최종 수용을 소유한다. 개발은 설계와 구현, QA는 독립 판정과 증거를 소유한다. 역할을 나누되 모든 역할을 상시 프로세스로 띄우지는 않는다.

## 시작

1. 실행 호스트의 `orca skills get orchestration`을 읽고 그 실행 파일을 계속 사용한다. 모델 선택·재사용은 `references/coordinator-loop.md`, 복구는 `references/recovery-and-cleanup.md`를 필요할 때 조회한다. Orca 대신 다른 하위 에이전트 도구로 우회하지 않는다.
2. 사용자 요청, 저장소 규칙, 기존 변경, 진행 중인 Run·작성자·공유 자원을 확인한다. 다른 세션의 Run은 인계 지시 없이 채택·종료하지 않는다.
3. [운영 계약](references/operations.md)에 따라 요구사항 버전·수정 담당·수용 조건·승인 범위를 고정한다. LoveRevolutionMaker는 [프로젝트 정책](references/loverevolutionmaker.md)을 적용한다.
4. 한 요청을 Run으로 묶고, 실제 선행 조건만 Task 의존성으로 표현한다. 설치된 CLI의 스키마를 사용하며 오래된 명령·플래그를 추측하지 않는다.

## 실행과 수용

- Task spec에 목표, 변경/금지 범위, 정확한 호스트·워크트리, 수정 소유권, 의존 방향, 관찰 가능한 완료 조건을 넣는다.
- 워커는 자연스러운 체크포인트와 완료 직전에 자기 Dispatch의 후속 메시지를 확인한다. `check`가 FIFO 배치 하나만 반환할 수 있으므로 처리·ack 뒤 다음 배치를 확인해 미처리 보완 요청이 없는지 확인한다. 다른 Run이나 중앙의 inbox를 대신 소비하지 않는다. `worker_done` 이후 수정은 새 Task/Dispatch로 배정한다.
- 새 모듈·UI·공유 계약의 경계는 구현 전에 독립 설계 리뷰한다. 기존 패턴의 작은 변경은 해당 경계의 준수 여부만 확인한다.
- 구현은 `[impl]`, 독립 구조 리뷰는 `[review]`, 관련 동작/화면 검증은 `[qa]`, 검증 내용과 커밋 일치 확인은 `[commit]` 제목으로 구분한다. 조사·기획은 `[research]`를 쓴다. 검증 가능한 완료 기준 없이 제목만 붙이지 않는다.
- `worker_done`은 해당 Task의 종료다. 기능 전체 완료는 필요한 review·QA·commit Task와 수용 조건이 충족됐을 때만 선언한다. Task가 모두 종료돼도 미해결 Gate는 결정 대기로 남긴다. 후속 기능은 impl 종료가 아니라 최종 수용에 의존한다.
- 구현 작성자와 수용 리뷰어를 분리한다. QA 반려를 중앙이 근거 없이 통과시키지 않는다. 수정 후 영향받는 리뷰·검증을 다시 한다.
- 기획·코드 충돌은 중앙이 최신 사용자 결정과 원문 근거로 조정한다. 요구사항 변경 시 작업 버전을 갱신하고 영향받는 검증을 무효화한다.

## 모델과 도구

사용자가 자동 선택을 허용한 범위에서 agent/model/effort를 배정한다. 필요한 도구·인증·실행 호스트 지원을 먼저 확인하고, 난도·위험·불확실성으로 모델을 선택한다. 모델 성능에 대한 미검증 우열을 규칙으로 굳히지 않는다.

고정 모델은 정확 ID·실제 호출을 확인한다. `launch.effective`와 가능한 런타임 증거를 기록한다. 지원 불명 모델을 기본 모델로 바꾸고 성공했다고 하지 않는다. 같은 터미널 재사용은 모델 전환이 아니다.

## 중앙 보고와 HUD

- 착수 때 목표·기능 단위·담당·모델·완료 조건을 알린다. 진행 중에는 60초 이내 상태 보고를 목표로 하고, 도구 대기는 45초 이하 관찰로 나눈다. 차단·범위 변경·반복 실패는 즉시 보고한다.
- 보고는 `완료/진행/차단 → 근거·마지막 관찰 시각 → 다음 행동` 순이다. Task 수를 기능 진척률로 오인하지 않는다. 테스트 성공, 화면 확인, QA 수용, 커밋을 구분한다.
- HUD는 읽기 전용이다. 상태를 표시할 뿐 배정·승인·메시지 소비·완료 판정을 대신하지 않는다. 오류/오래된 관찰은 확인 불가로 보이며 워커 사망으로 해석하지 않는다.
- 중앙이 활성일 때의 보고와 세션 종료 이후 상시 감시는 다르다. 별도 감시가 없으면 종료 후 보고를 보장하지 않는다.
- 마감에 작업별 결과·증거·미검증·커밋/게시 상태·잔여 자원을 보고한다. settled 워커는 수신 메시지를 처리한 뒤 재사용·사용자 요청 보존·release 중 하나를 결정하고 delivery를 ack한다.

### HUD 열기

프로젝트 전체 현황은 이 스킬 위치 기준 `scripts/project_hud.py`를 Python 3으로 실행한다. `orca project list --json`의 정확한 프로젝트 ID와 sourceRepoIds를 확인한다.

```text
python3 <skill-root>/scripts/project_hud.py --repo id:<repo-id> --project <project-id> --watch
```

프로젝트 화면은 Run을 새로 발견하며 기존 Run의 바인딩·배정·inbox를 변경하지 않는다. 전체 프로젝트를 본다는 것과 다른 중앙의 작업을 인계받는 것은 다르다. 확인한 호스트 범위, 소속 미확인·혼합 Run, 부분 오류, 마지막 성공 관찰을 표시한다. 조회 실패는 0건이 아니다. 혼합 Run의 귀속 미확인 Task를 프로젝트 진척 분모에 넣지 않는다. 읽기 전용 HUD는 상시 작업 배정·복구를 실행하는 중앙 프로세스가 아니다.

특정 Run 상세는 기존 `scripts/hud.py`를 사용한다. 실제 Run ID와 작업 경로를 사용한다.

```text
python3 <skill-root>/scripts/hud.py --run <run_id> --worktree <path> --watch
```

사용자가 HUD를 요청한 오케스트레이션에서는 시작 때 프로젝트 화면을 함께 연다. 설치된 `orca terminal create --help`로 옵션을 확인한 뒤 명령을 `--command`로 전달한다. HUD 터미널은 사용자가 보는 읽기 전용 화면이며 supervised 워커가 아니다. 다른 사용자의 HUD를 임의 종료하지 않는다. 이 요청에서 만든 HUD는 상태 확인 후 같은 터미널에서 재시작할 수 있다. 단일 Run 화면에 새 Run이 자동 반영된다고 설명하지 않는다. 한 번 출력은 `--watch`를 생략한다. 기본 화면은 터미널 크기에 맞춰 조회 시각·작업 수·현재 작업을 표시한다. Task 종료는 기능 수용이나 QA 통과가 아니다. 현재 Dispatch의 모델과 워커 관찰 나이를 표시하며, 60초를 넘긴 관찰은 오래됨으로 구분한다. 긴 항목·생략한 작업은 더보기로 표시한다. 전체 기술 증거는 `--details`로 조회한다. 색상은 TTY에서 자동 적용하며 `NO_COLOR`가 비어 있지 않으면 끈다. `--color auto|always|never`로 색상을 지정하며 `always`는 `NO_COLOR`보다 우선한다. 단일 Run `hud.py --details --worktree <path>`의 Stage 파일 목록·최근 커밋은 index/커밋 메타데이터만 조회하고 optional locks를 끈다. 기본 화면과 프로젝트 화면은 Git을 조회하지 않는다. 미추적·unstaged 파일 검사, 파일 내용·비밀 파일·전체 대화 기록 조회는 하지 않는다.

Codex 기본 상태줄은 설치된 `codex-hud` 스킬로 설정한다. Claude 전용 TSX mod를 Codex에 복사하지 않는다. 상세 파일 탐색·변경 비교는 Orca의 기존 파일·diff 화면을 사용한다. 편집 단위 Replay Theater와 Git 커밋 이력은 다르다.

## 검증

스킬 형식 검증과 HUD 테스트는 설치·구문 검증이다. 실제 모델 실행·MCP 조회·화면 노출·기능 동작 검증과 구분해 보고한다. 실패 복구·QA 이후 변경 감지·중복 작성자 방지가 입증되지 않은 상태를 운영 자동화 완료로 표시하지 않는다.
