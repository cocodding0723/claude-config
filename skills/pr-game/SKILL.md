# pr-game

`~/Downloads/pr-games-v4` 11개 파일의 엔진을 이어받았다. v4 59문항은 정답이 최장 보기인 문항이 93%였고, 코드를 안 본 에이전트가 59개를 다 맞혔다(2026-11-06). 그래서 게임 형식은 두고 측정 방식을 바꿨다.

로비에서 둘 중 하나를 골라 푼다. 문항 수는 PR 크기에 맞춘다. 화면은 데이터에 든 문항 수를 그대로 쓴다.

| 트랙 | 문항 | 대상과 목적 |
|---|---|---|
| 📘 배우며 풀기 (`level: "learn"`) | 3~10 | 배경 지식이 없는 사람. 문항마다 "먼저 알아 둘 것" 카드와 코드·도식이 같이 나오고, 그것만 읽고 풀 수 있다. 풀면서 PR 을 배운다 |
| ✅ 확인 문제 (`level: "check"`) | 4~10 | 배우기를 마친 사람이나 리뷰어. 코드를 일부러 빼서 PR 을 열어 봐야 풀린다. 제대로 읽었는지 잰다 |

| PR 크기 | 배우기 | 확인 | 예 |
|---|---|---|---|
| 작음: 파일 몇 개, 한 가지 동작 | 3~4 | 4 | 버튼 하나 고침, 설정값 변경 |
| 보통: 한 기능, 몇 군데 호출 | 5~6 | 5~6 | 창 하나 추가, 저장 방식 변경 |
| 큼: 여러 계층, 새 구조 | 8~10 | 8~10 | 새 시스템, 스택 PR 의 뼈대 층 |

물을 것이 없는데 수를 채우지 않는다. 같은 사실을 두 번 묻는 문항이 생기면 줄인다. 문서 한 줄 고친 PR 처럼 확인 4문항도 안 나오면 게임을 만들지 말고 그렇다고 말한다.

배우기 결과 화면에서 확인 문제로 바로 이어진다. `level` 을 안 쓰면 예전처럼 한 묶음(5~10문항)으로 푼다.

점수는 자가 점검이다. 정답이 파일 안에 있으므로 시험이나 승인 근거로 쓰지 않는다.

## 절차

1. **규모와 대상을 잰다.** `gh pr view`, `gh pr diff <번호> > <scratchpad>/pr.diff` 를 쓴다. head 커밋은 `headRefOid` 다. 파일 100개가 넘으면 축을 나눠 PR 묶음별로 게임을 만들지 묻는다.
2. **주변 코드를 읽는다.** 호출부와 변경 전 동작을 head 커밋에서 읽는다. diff 만 읽으면 구조 문항을 못 쓴다. 조사 범위는 `explain-diff` 의 1장과 같다. 의도는 PR 본문·커밋·코드에 근거가 있을 때만 쓴다. 근거가 없으면 동작을 묻는 문항으로 바꾼다.
3. **데이터를 쓴다.** `references/schema.md` 를 읽고 `<scratchpad>/pr-<번호>.json` 을 만든다.
4. **빌드한다.** 검증 실패는 문항을 고쳐 해결한다.
   ```sh
   python3 -I ~/.claude/skills/pr-game/scripts/build.py pr-<번호>.json --diff pr.diff --repo <저장소> \
     --out pr-<번호>-game.html --blind blind/ --key key.json
   ```
5. **변별력을 잰다.** 새 하위 에이전트 셋에게 시킨다. A는 `blind/questions.md`(확인 문항)만, B는 확인 문항에 diff 와 head 코드까지, C는 `blind/learn.md`(배우기 문항과 설명 카드)만 보고 답을 JSON 으로 낸다. 어느 쪽도 `key.json` 과 데이터 파일을 읽지 못하게 한다. `build.py pr-<번호>.json --score key.json <답안>` 으로 채점한다.
   - 확인 문항: A가 맞힌 비율이 50% 이하, B가 80% 이상이면 통과다.
   - 배우기 문항: C가 80% 이상이면 통과다. 설명 카드만으로 풀려야 배경 지식 없는 사람이 배울 수 있다. C가 틀린 문항은 카드에 답의 근거가 빠졌거나 용어 풀이가 모자란 것이다.
   - A가 맞힌 문항은 왜 글만으로 풀렸는지 보고 고친다. B가 틀린 문항은 정답 근거나 문항 모호성을 먼저 의심한다.
   - 표본 1회라 회귀 탐지일 뿐이다. 수치를 그대로 보고한다.
6. **실제로 연다.** 브라우저로 끝까지 한 번 풀고 좁은 화면에서 도식을 본다. 콘솔 오류가 없어야 한다.
7. **전달한다.** 파일 경로를 주고 Orca 내장 브라우저나 `open` 으로 연다. Slack 공유는 사용자가 한다. PR 댓글은 전역 규칙대로 문안을 보이고 허락을 받는다.

## 배우기 문항 쓰는 법

독자는 개발자가 아닐 수도 있는 팀원이다. 기획자·아티스트·새로 온 사람이 PR 을 열지 않고도 무엇이 바뀌었는지 배울 수 있어야 한다.

- `brief.background` 에 처음 보는 말을 풀어 쓴다(5~8개). 클래스 이름보다 하는 일로 설명한다. 예: "레이캐스트 — 화면의 한 점을 눌렀을 때 맨 위에 무엇이 있는지 찾는 방법".
- 문항마다 `learn` 에 2~4문장으로 그 문항을 푸는 데 필요한 사실을 쓴다. 답을 그대로 말하지 않고, 읽은 사람이 한 걸음 생각하면 고를 수 있게 쓴다. 새 용어는 `terms` 로 푼다.
- 쉬운 것부터 놓는다. 앞 문항은 "무엇을 하는 기능인가", "누가 누구를 부르나", 뒤 문항은 "이런 경우 어떻게 되나".
- 문항 글에 영어 식별자만 쓰지 않는다. 처음 나올 때 우리말 설명을 붙인다.
- 코드나 도식을 같이 보여 줘도 된다. 보여 준 코드는 짧게(10줄 이하) 자르고 `learn` 에서 어느 줄을 볼지 짚는다.
- 오답은 여전히 그럴듯해야 한다. 카드를 안 읽어도 상식으로 고를 수 있으면 배우는 것이 없다.

## 문항

축은 셋이다. 확인 문항 묶음과 배우기 문항 묶음에 각각 섞는다. 코드만 맞혀서는 "구조까지 파악"이 나오지 않는다.

| 축 | 묻는 것 | 예 |
|---|---|---|
| `code` | 값·분기 추적, 코드로 확인되는 이유 | 이 입력이면 어느 칸에 붙나 |
| `structure` | 책임 위치, 호출·데이터 방향, 다음 변경의 수정 지점 | 비슷한 창을 더하려면 어디를 고치나 |
| `impact` | 이번에 안 바뀐 것, 실패 경로, 호환 근거 | 대상을 못 찾으면 어떻게 되나 |

- 브리핑 문장을 옮겨 적으면 풀리는 문항을 내지 않는다. 브리핑은 지도이고 답은 코드에 있어야 한다.
- 오답은 실제로 있을 법한 다른 설계나 잘못 읽은 결과로 쓴다. 터무니없는 보기는 문항 수만 채운다.
- `level` 을 쓰면 문항 수는 위 PR 크기 표를 따른다(배우기 3개·확인 4개 이상, 합 24개 이하). 확인 문항의 절반 이상은 코드와 도식을 뺀다. `level` 이 없으면 5~10개이고 절반 이상 코드와 도식을 뺀다. 그 문항은 PR 을 열어 풀도록 안내된다.
- 민감한 값은 스니펫과 도식에 넣지 않는다. 받는 사람은 PR 을 볼 수 있는 사람으로 한정한다.

## 실패 모드

- **정답만 길고 자세함** → 읽지 않아도 풀린다. 오답에도 같은 밀도로 근거를 쓴다.
- **보기에 근거를 붙임** → "4 — 판정 앞 칸", "이전처럼 연다"는 답을 알려 준다. 값만 쓴다.
- **상식으로 고를 수 있는 정답** → 다른 보기가 어설프면 글만으로 풀린다. 실제로 택할 만한 다른 설계를 오답으로 쓴다.
- **문항에 코드를 다 보여 줌** → 문항만 읽고 풀린다. PR 을 읽었는지 재지 못한다.
- **전부 "왜"로 시작** → 코드 축만 남는다. 추적·수정 지점·실패 경로를 섞는다.
- **도식을 손으로 그림** → 데이터와 어긋난다. `graph` 만 쓰고 엔진이 그리게 둔다.
- **의도를 지어냄** → 근거 없는 "왜"는 작성자 생각이 아니다. 동작 문항으로 바꾼다.
- **변별력 시험 생략** → 검증기는 형식만 본다. 글만으로 풀리는지는 5단계만 잡는다.
