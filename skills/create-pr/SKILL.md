# PR 작성·등록

1. 원격 저장소, 현재 브랜치, 실제 기본 브랜치, 기존 PR을 확인한다. `main`을 고정 가정하지 않는다. `gh` 또는 연결된 GitHub 도구를 사용한다.
2. 저장소 PR 템플릿·기여 규칙, 기준 브랜치부터의 커밋·diff, 연관 Issue를 읽는다. 마지막 커밋만 보고 전체 변경을 요약하지 않는다.
2-1. 트리아지 산출물이 있으면 새로 쓰지 않는다. `~/.orca-triage/<저장소명>/reports/<브랜치 슬러그>.pr.md`가 있으면 본문으로 그대로 쓰고, diff와 어긋나는 부분만 고친다. 같은 경로의 `.meta.json`에서 `sources[].url`을 읽어 Crashlytics 링크 줄이 본문에 있는지 확인한다.

3. 아래 **본문** 형식으로 쓴다. 검증하지 않은 체크박스는 체크하지 않는다. 일부만 해결하면 `Related to #N`, 완료되는 Issue에만 `Closes #N`을 쓴다.
4. 커밋되지 않은 변경이 있으면 설치된 `review-before-commit` 스킬로 검수·승인 범위를 확인한다. PR 준비를 이유로 자동 stash·rebase·reset·squash·강제 push하지 않는다.
5. 초안 작성 요청이면 본문을 보여주고 끝낸다. 등록 요청이 이미 명시됐다면 권한을 재질문하지 않고 생성한다. 범위가 달라지거나 게시 승인이 없으면 완성된 초안을 먼저 보여준다. 리뷰어 호출·댓글·merge는 해당 지시가 있을 때만 수행한다.

## 본문

machamy 의 JobMaker PR **10월 형식**을 따른다(2026-10-08 정제 분석, 선례는 `~/.claude/skills/doc-kit/references/sources.md`). 문체·장치는 `~/.claude/skills/doc-kit/references/style.md` — 평서 `~다`. 저장소 PR 템플릿이 있으면 템플릿 구조가 우선이고 각 칸을 이 기준으로 채운다.

```markdown
> <변경 해설 문서가 있고 리뷰 전에 읽어야 하면: 링크(blob 절대 URL) + 담긴 내용 한 줄>

## 요약
<바뀐 결과를 단정하는 첫 문장>. <dev 는 ~했다 — 이전 상태 대비>. Closes #N
<해설 문서가 없으면 규모 줄: `N 커밋 · N 파일 (+x / −y)`>

## 유저·QA 가 보는 변화 (dev 대비)     ← 동작이 바뀔 때만
| 상황 | dev | 이 PR |
"의도한 동작 변화는 위 표가 전부다."

## 원인 / 어떻게                       ← fix 는 원인, feat·refactor 는 어떻게

## 왜 이 방식인가                      ← 굵은 주장 + 근거. 기각안은 `## 다른 안`

## 게이트 / 배포 전에 할 일            ← RC·patch 게이트, 선행 조건, 체크박스

## 검증
- <테스트> — N 통과 / M 실패 / K 스킵 (기준 커밋 해시). 재현 가능하면 명령까지
- **실기 미검증**: <확인 못 한 것과 확인할 화면>

## 리뷰 포인트
- **<볼 곳>** — <왜 여기를 봐야 하나, 근거의 전제>

## 범위 밖 / 남은 결정
- <손대지 않은 결함·후속 작업·기획 결정 대기 — 이름과 함께>
```

절은 해당할 때만 넣는다. 작은 PR 은 9월 형식(`요약 / 변경 목록 / 검증 / 리뷰 포인트 / 범위 밖 / 후속`)으로 줄여도 된다 — 변경 목록 표는 `| # | 대상 | 변경 | 효과 | 리스크 |`.

유형별로 더하는 것:

| 유형 | 더하는 것 |
|---|---|
| fix | 원인은 함수·발생 조건·증상을 인과 순서로, 원인이 아닌 경로도 배제(#2616) · `## 영향 범위` · `## QA 확인 절차`(번호 재현 단계) · 증거 표(버전별 건수·영향 uid, #2549) · 회귀 테스트가 수정 전에 실패했는지(있으면) |
| feat 대형 | 커밋 리뷰 순서 표(동작을 바꾸는 커밋 굵게) · `## 리뷰 가이드` · 부록은 `<details>` (#2623) |
| refactor | `## 전과 후` · `## 다른 브랜치 주의`(뜻이 바뀌는데 컴파일은 되는 API) · `## 운영 주의` · `## 기각한 것` (#2615, #2438) |
| 서버·데이터 | `## 선행 PR` · `## 배포 순서` · `## 머지 뒤 할 일`(실행할 명령까지) (fn#11, fn#16) · 저작 요청이 있으면 "이 PR 이 살아나려면 필요한 것"(#2524) |
| RC·게이트 | 기본값, 끄면 일어나는 일, 기본값을 그렇게 둔 이유 (#2629) |
| docs/chore | 짧게. 요약·변경·검증, 필요하면 근거 실측(#2625) |

- **첫 화면에서 병합 판단이 서야 한다.** 요약 문단 400자 이내 — 이 스킬의 선택이다(선례 중앙값 약 700자). 깊은 설명은 `doc-kit`(B 경로) 문서로 빼고 링크한다.
- 사내 축약어·숫자 ID 는 첫 등장에 풀어 쓴다(#2613 "국민체조 속보(60061)").
- 흐름·구조가 바뀌면 표나 ASCII 그림을 하나 이상 넣는다.
- 검증하지 않은 것을 통과로 쓰지 않는다. 체크박스는 `배포 전에 할 일`에서만.
- **AI 흔적 줄 금지** — `🤖 Generated with`, `Co-Authored-By` 를 본문에 넣지 않는다(machamy PR 25/25 에 있으나 사용자 규칙이 우선).
- PR 제목은 저장소 규칙을 따른다. LoveRevolutionMaker 는 명사 종결·타입 접두(`fix: 아트 노드명 오타 교정`). machamy 의 `~한다` 서술형 제목(8/25)은 따르지 않는다. 규칙이 없으면 50자 이내 명사형.
- 같은 글을 커밋 메시지와 PR 본문에 두 번 쓰지 않는다. 서술은 PR, 커밋은 제목 한 줄.

## 리뷰하기 쉽게 정리

PR 을 올리기 전에 리뷰어가 의도·핵심 파일·위험을 빨리 잡게 만든다. **코드 동작은 바꾸지 않는다.**

- **커밋 정리**: 한 커밋 = 한 개념(기능 단위). 순수 이동·이름 변경은 내용 변경과 분리해 rename 으로 보이게 한다. fixup 합치기·리베이스는 계획을 보여 주고 **사용자 승인 뒤**에만, 백업 태그 먼저. 재작성 전후 `git rev-parse HEAD^{tree}` 가 같은지 확인하고 다르면 push 하지 않는다.
- **리뷰어 안내**: `## 리뷰 포인트`에 읽는 순서(데이터·계약 → 핵심 로직 → 연결 → UI → 테스트)와 위험 지점을 적는다. 생성물·기계적 변경 파일은 따로 묶어 "훑어도 됨"으로 표시한다.
- **정리로 동작 변경을 숨기지 않는다.** 정리 중 결함을 찾으면 별도 커밋·PR 로 뺀다.
- 노트로 감당 안 되게 크면 다듬지 말고 PR 분할을 제안한다.

## 등록

멀티라인 본문은 임시 파일로 작성해 `gh pr create --title '제목' --body-file /절대경로/pr.md --base 실제기준브랜치 --head 현재브랜치`에 전달한다. 작업 미완료나 사용자 요청 시 `--draft` 사용. shell 문자열에 본문을 직접 끼워 넣지 않는다.

이미 같은 브랜치 PR이 있으면 중복 생성하지 않는다. 수정 요청 범위만 `gh pr edit --body-file`로 갱신한다. 생성 결과가 불명확하면 먼저 PR 목록을 조회하고 무조건 재시도하지 않는다.

최종 확인: PR URL, base/head, 제목·본문, draft 상태를 다시 읽는다. CI 실행 예정과 실제 통과를 구분해 보고한다. PR 등록 성공은 merge 성공이 아니다.

## Crashlytics 역링크

크래시에서 출발한 PR이면 등록 후 `crashlytics_create_note`로 각 이슈에 `수정 PR: <PR URL>`을 남긴다. 대상 이슈 id는 `.meta.json`의 `sources[].id`. Crashlytics 콘솔에는 GitHub 링크가 자동으로 생기지 않아 이 노트가 유일한 역방향 경로다.

이슈 상태(`crashlytics_update_issue`)는 바꾸지 않는다. 머지·배포 후 재발 여부를 보고 사용자가 판단한다.
