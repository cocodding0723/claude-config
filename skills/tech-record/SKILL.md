# tech-record — 기술 문서 (machamy 선례 기준)

문서 작성의 **기본 스킬**이다. 다른 문서 스킬(`explain-diff`·`create-pr`·`work-report`·`qa-checklist`)도 문체와 장치는 `references/house-style.md`를 따른다.

## 순서

1. **유형을 고른다** — 아래 표. 애매하면 묻는다. 유형이 없으면 가장 가까운 것을 쓰고 문서 머리말에 이유를 적는다.
2. **선례를 연다** — `references/sources.md`에서 같은 유형 선례를 최소 1개 읽는다. 골격만 보고 쓰면 장치(빈칸 문장·뒤집는 조건 등)가 빠진다.
3. **근거를 모은다** — 코드·커밋·실측. 기준 커밋 SHA 와 실측 날짜를 적어 둔다. 근거가 없는 칸은 비워 두고 "미확인"으로 쓴다.
4. **골격대로 쓴다** — `references/templates.md`. 문체·장치는 `references/house-style.md`.
5. **자기 점검** — 아래 체크리스트. 결과는 사용자에게 경로와 함께 알린다. 커밋은 승인 뒤.

## 유형

| 유형 | 언제 | 파일명 |
|---|---|---|
| 설계 기록 | 끝난 조사·계획을 근거 보존용으로 굳힐 때 | `<주제> (설계 기록).md` |
| 계획 | 구현 전. cross-build 입력용 / 장기용 두 모양 | `<주제> 계획.md` (짧은 개정은 제목 `(v2)`, 여러 차례면 부록 이력) |
| 계약 | 다른 팀·레포·저작자에게 넘기는 명세 | `<주제> — 서버 계약` / `저작 인터페이스 계약` / `문법 계약` |
| 규약 | 갈라진 트랙 사이의 합의 | `<주제> 규약.md` |
| 폴더형 | 여러 주 걸리는 리팩토링·이관 | `<작업명>/00 개요.md` ~ `0N …` (질문 단위) 또는 `<작업명>/계획`·`변경 해설`·`런북` (역할 단위) |
| 데이터 명세 | JSON·CSV 추가·변경 (같은 PR 에서) | `docs/Json Specs/<파일>.json.md` |
| 런북·지시서 | 운영·CS·다른 도구가 그대로 실행 | `<주제> 런북.md` / `… 지시서.md` |
| 변경 해설 | 코드 변경 이해 | → `explain-diff` |
| PR 본문 | | → `create-pr` |
| 결과 보고서 | 여러 커밋에 걸친 작업 정리 | → `work-report` |
| QA 체크리스트 | | → `qa-checklist` |

## 위치

- 저장소에 문서 폴더 관례가 있으면 따른다. JobMaker 는 `docs/Tech Records/`, LoveRevolutionMaker 는 `docs/`.
- 폴더형은 하위 폴더로 묶는다. 하위 폴더 안 파일 링크는 퍼센트 인코딩 상대경로.
- 개인용 메모·초안은 레포 밖(scratchpad)에 둔다. 레포 문서는 사용자 승인 뒤 커밋.

## 체크리스트

- [ ] 첫 문장이 결과·결정을 단정하는가
- [ ] 해설이면 머리말에 규모 줄이 있는가(기준 SHA·날짜 권장). 비해설 문서는 생략 가능
- [ ] 결정마다 근거와 기각안(또는 "다른 안 없음")이 있는가. 뒤집힐 수 있는 결정엔 뒤집는 조건
- [ ] 의도된 한계와 우연히 발견한 결함이 분리됐는가
- [ ] 숫자·`파일:줄`·커밋 해시로 근거를 댔는가. 추정은 추정이라고 썼는가
- [ ] 축약어·숫자 ID 를 첫 등장에 풀었는가
- [ ] 흐름·구조 설명에 그림(표·ASCII·mermaid)이 하나 이상 있는가
- [ ] 평서 `~다`로 통일됐는가(선례 다수 경향 87%. 외부 저작자용 지시서만 예외)
- [ ] 사실이 바뀐 곳을 지우지 않고 정정 표식으로 덧썼는가
- [ ] 본문을 고쳤다면 그 절을 참조하는 요약 표·퀴즈·다른 문서를 같이 고쳤는가

문장 다듬기가 더 필요하면 `writing-clearly-and-concisely`, 상투어는 `writing-humanizer`, 표현 검사는 `prose-lint`.
