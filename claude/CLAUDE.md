# 전역 작업 규칙

## 커밋·리뷰 흐름 (2026-10-26)
- **AI는 작업 브랜치에 승인 없이 커밋한다.** 리뷰 시점은 커밋 전이 아니라 PR 전이다.
- 커밋 전 필수: `comment-lint` 주석 점검, 컴파일, 관련 테스트 통과. 깨진 커밋을 만들지 않는다.
- push·리베이스·머지·PR 생성은 여전히 사용자 승인 뒤에만 한다.
- 정리 흐름: `explain-diff` 로 브랜치 범위 문서 작성 → 사용자 검토 → 백업 태그 → 리베이스 → PR.
- 리뷰 단위: 기능 3~5개 또는 하루치 작업. 넘기 전에 정리를 제안한다.
- 커밋마다 판단이 들어간 부분·확신 없는 부분을 기록하고 정리 문서에 모은다.

## 기능 단위 커밋
- 계획 단계에서 기능 목록을 번호로 제시하고 단위를 승인받음.
- 기능 1개 완료 → 관련 테스트 → 커밋 → 다음 기능 착수.
- 검토 후 수정 요청은 fixup 커밋으로 남기고 리베이스 때 합친다.
- 커밋은 작업 브랜치에만. PR 전 squash 여부는 저장소 규칙을 따름.
- 커밋 후 보고 형식: 기능 번호/전체, 커밋 해시, 검증 결과(`명령 — 결과`), 판단이 들어간 부분.
- **커밋 크기** (2026-10-07): 한 커밋 = 한 개념(동작 하나 또는 계층 하나). 코드 파일 3~10개·변경 400줄 이하 권장, 15개 초과 금지.
  - 근거: 리뷰 결함 발견율이 200~400줄을 넘으면 급감(SmartBear·Cisco 연구). 10개 안쪽이면 파일 목록만 보고 커밋 의도 파악 가능.
  - 세지 않는 파일: `.meta`, 이미지·바이너리, 자동 생성물, 순수 이동·이름 변경.
  - 제목에 `·` 로 셋 이상 나열되면 쪼갬.
  - 프리팹·에셋은 그걸 쓰는 코드와 같은 커밋. 에셋만 많으면 에셋 전용 커밋(20개 이하).
  - 테스트는 기능 커밋에 함께. 크기를 넘으면 바로 다음 커밋으로.
  - 순수 이동·이름 변경은 내용 변경과 섞지 않음(diff 에서 rename 으로 보이게).

## Unity `.meta` 커밋 규약

- **GUID 참조와 사용자 지정 임포트 설정이 없는 순수 C#의 `.cs.meta`는 커밋하지 않는다.** 클래스·구조체·인터페이스·열거형·테스트를 포함한다. 리뷰 대상 파일 수를 줄이기 위한 작업 규칙이다.
- **제외한 `.meta`는 로컬 미추적 파일로 보존한다.** 이 목적으로 `.gitignore`나 `.git/info/exclude`를 추가하지 않는다. 필요한 파일만 명시적으로 stage한다.
- **Unity 객체·에셋 참조에 필요한 `.meta`는 원본과 함께 추적한다.** MonoBehaviour·ScriptableObject의 간접 상속도 확인하고, GUID 참조 또는 사용자 지정 임포트 설정이 있으면 제외하지 않는다.
- **추적 대상 `.meta`는 원본과 같은 기능 커밋에 넣는다.** 이동·이름 변경 때 GUID를 유지한다. 동반 메타파일은 커밋 제목에 나열하거나 코드 파일 수에 세지 않으며, GUID·임포트 설정 자체가 바뀌면 영향은 설명한다.
- 순수 C# `.meta`가 이미 이력에 들어갔다면 승인된 리베이스에서 원본 커밋부터 제외한다. 게시한 이력을 재작성하거나 push할 때는 기존 사용자 승인 범위를 확인한다.

Unity의 GUID·임포트 설정 동작: [Asset metadata](https://docs.unity.com/en-us/engine/6000.3/manual/assets-and-media/import-assets/asset-metadata).

## 코드 작성 원칙 (기본값, 2026-10-07)
착수 순서: **리서치 → 설계 → 구현 → 관련 테스트 → 문서**.

- **리서치 먼저**: 새 개발·리팩토링·참고 작업은 코드 작성 전에 ① 다른 로컬 레포의 유사 코드 ② 웹의 유사 구현 ③ 적용할 디자인 패턴부터 조사함. 조사 결과(채택·기각 근거)를 설계 설명에 포함.
- **구조**: MVP(수동 View, 순수 Presenter) + DDD(도메인 순수, 포트/어댑터). 맥락 파악이 쉬운 계층·폴더 구조를 우선함.
- **재사용 코드 분리**: 기능 모듈 밖에 둘 것. 예) `PassModule`의 수식 파서가 쓰는 이진 트리·토크나이저 같은 범용 구현은 `PassModule`에 두지 않고 공용 모듈로 분리.
- **매직 값·상수 지양**: 문자열 하드코딩·흩어진 `const` 지양. 관련 값은 소유 모듈 한 곳에 모으고 노출 범위 최소화(`internal`·`private`). 설정 객체·레지스트리·주입 같은 패턴 우선. 맞는 패턴을 모르면 웹 리서치 후 결정.
- **`static`은 꼭 필요할 때만**: 상태 없는 순수 함수·확장 메서드·조립용 팩토리처럼 인스턴스가 이득 없는 경우만 허용. 바꿔 끼울 구현이 있거나 상태를 가지면 인스턴스 + 주입. 누구나 꺼내 쓰는 `public static` 전역 값은 금지.
- **네이밍**: 짧고 개발자가 흔히 쓰는 단어. 신조어·직역 금지.
- **주석**: 의도·핵심 기능만 압축. 코드를 반복하는 주석 금지.
- **문체**: 주석·커밋은 `~함`·명사형. **문서·PR 본문은 평서 `~다`**(2026-10-08, machamy 선례). 어디서든 `~합니다`·`~입니다` 금지.
- **테스트 범위**: 이번에 개발한 기능과 관련된 테스트만 실행함. 무관한 기능 테스트·전체 스모크는 돌리지 않음.
- **완료 문서**: 기능 하나 완료 시 `explain-diff`로 HTML 문서 작성(아래 「문서 작성」). 장문 대신 구현 의도 중심 + PUML 도식(가능하면 인터랙티브 그래프). 해당 기능의 스모크 녹화 영상을 문서에 포함함.

## Jira (회사 프로젝트 원칙, 2026-11-06)
- **티켓 발급은 `jira-issue` 스킬의 상세 양식으로.** 받는 사람이 티켓만 읽고 재현·착수·확인할 수 있어야 한다(요약·현상·재현·기대/실제·영향·환경·근거·추정 원인·관련·완료 기준). 빈 칸은 지우지 말고 `미확인`.
- **티켓을 고치면 커밋 직후 그 티켓에 댓글.** 원인·수정·커밋(브랜치·해시, PR)·확인 방법을 한 줄씩, 쉬운 말로. 승인 불필요.
- 코드 변경 없이 닫아도(기획 반영·중복·재현 안 됨) 이유를 댓글로 남긴다.

## Git
- 푸시/머지/리베이스는 항상 사용자 승인 후에만 실행한다 (권한 설정으로도 강제됨). 작업 브랜치 커밋은 승인 불필요(「커밋·리뷰 흐름」).
- `main`/`master`/`develop`에 직접 커밋하지 않는다. 작업 전 feature 브랜치를 만든다 (`feat/…`, `fix/…`).
- 파괴적 git 명령(강제 push, hard reset, clean, 작업 트리 전체 되돌리기, 강제 브랜치 삭제)은 `~/.claude/hooks/git-guard.sh`가 차단한다. 우회하려 하지 말고 사용자에게 직접 요청한다.
- 커밋 메시지: 한 줄 요약 + 필요 시 본문. 언어는 프로젝트 관례를 따른다.
- 병합 원칙 (git-flow 변형, https://techblog.woowahan.com/2553/ 기준):
  - 공유 브랜치 = `main`/`master`/`develop`/`release/*`. 여기서는 rebase·amend 금지 (git-guard + 전역 `pre-rebase` 훅이 차단).
  - 공유 브랜치로 병합할 때는 `git merge --no-ff` (merge commit으로 이력 보존). 갱신은 `git pull --rebase`. 둘 다 전역 git config(`merge.ff=false`, `pull.rebase=true`)로 기본값이며 git-guard가 이중 검사한다.
  - 작업 브랜치 접두사: `feat/`, `fix/`, `hotfix/`, `release/`. 다른 이름은 git-guard가 확인을 요청한다.
  - 작업 브랜치의 기능 단위 커밋은 squash하지 않고 그대로 PR(위 「커밋 크기」). 공유 브랜치 병합은 `--no-ff` 로 이력 보존. 저장소 규칙이 squash를 요구하면 그 규칙을 따름. 커밋 제목 티켓번호 검사는 저장소별 `git config hooks.ticketPattern` 설정 시에만 동작.

## 한국어 텍스트 규칙 (커밋·PR·주석·문서)
답변 문체는 i-have-adhd 플러그인(always-on)의 K1~K7이 담당한다. 아래는 코드·저장소에 남는 한국어 텍스트에 같은 기준을 적용하는 규칙이다. 공통 원칙: **짧고, 정확하고, 한눈에 읽히게.** 정보 삭제가 아니라 의미 압축. 통용되는 용어만 사용, 직역·신조 용어 금지.

- **커밋 메시지**: 제목은 동사형 압축, 50자 이내 ("~기능을 추가했습니다" → "한국어 압축 규칙 추가"). 본문은 무엇을·왜만. 어떻게는 diff가 말한다. `기본적으로`, `~하게 됩니다`, `여러 가지 수정` 같은 필러 금지.
- **PR 설명**: `create-pr` 골격(machamy 10월 형식: 요약 → 유저·QA 가 보는 변화 표 → 원인·어떻게 → 왜 이 방식인가 → 검증 → 리뷰 포인트 → 범위 밖). 첫 줄은 리뷰어의 병합 판단에 영향 주는 사실. 검증은 `명령 — 결과` 한 줄씩.
- **인라인 주석**: 명사형 압축 ("값을 가져옵니다" → "값 조회"). 단, 주석은 "왜"를 남기는 곳이다. 압축하다 근거를 지우지 않는다 ("재시도 3회 제한" ✗ → "재시도 3회 제한. 4회부터 서버가 429 반환" ✓).
- **docstring / XML doc (`///`)**: 첫 줄만 압축. 파라미터·반환·예외 설명은 정보 삭제 금지 (IDE 툴팁·문서 생성기가 읽는다).
- **README·설계 문서**: 결론 먼저, 문장 압축. 배경·근거 섹션은 유지한다. 독자는 미래의 본인. 골격은 `tech-record`.
- **에러 메시지·로그 문자열**: 원인 + 조치만.
- **공개 API 문서**: 외부 독자 기준. 팀 내부 약어 금지, 용어 정확성이 간결함보다 우선.
