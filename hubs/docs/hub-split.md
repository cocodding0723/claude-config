# 허브 분할·병합 런북

커진 허브를 하위 허브로 나누고, 한가해진 하위 허브를 부모로 다시 합치는 `hub_split.py` 의 판정 기준, 승인 흐름, 실행 순서, 되돌리기를 적는다. 작성일은 2026-11-12 이고, 결정 D-SPLIT1(네 결정 모두 추천안)을 따른다.

## 쉬운 말 3줄 요약

- 무엇이 생겼나: 스크립트가 허브마다 작업 공간 수와 최근 접수 수를 재서 분할·병합 후보를 낸다. 메인이 결정 카드로 제안하고, 사용자가 승인하면 실행 스크립트가 정해진 순서로 옮긴다.
- 왜: 허브가 커져도 나누는 절차가 없어 손으로 옮겼고, 옮기다 접수·보고가 엉뚱한 허브로 갈 위험이 있었다.
- 사용자가 할 일: 카드가 오면 승인 또는 보류만 고른다. 첫 회는 시험 실행만 하므로 실제로 바뀌는 것은 없다.

## 1. 흐름

```text
 measure (읽기 전용, --record 면 연속 횟수 기록)
   │  허브별: 정리 후 작업 공간 수 · 최근 7일 접수 · 메인의 주제 갈림 판단(--topic)
   ▼
 메인이 후보 확인 → propose --record (결정 카드 outbox 기록, 제안 저장)
   ▼
 사용자 승인(카드 1번)
   ▼
 run --decision-id D-… (기본 시험: 단계만 출력) → run … --apply (실행, 끝난 단계 기록)
   ▼
 (분할 후속) PR 이 닫힌 작업 공간만 relink --apply
```

## 2. 판정 기준

조건은 칸마다 모두 충족해야 한다. 값은 `hub_split.py` 의 `Limits` 한 곳에 있다.

| | 분할 제안 | 병합 제안 |
|---|---|---|
| 작업 공간 | 정리 후보를 뺀 하위 작업 공간 9개 이상 | 부모와 하위의 합 5개 이하 |
| 내용 | 메인이 주제가 둘로 갈렸다고 판단, 떼어 낼 작업 5건 이상(`--topic slug=N`) | 하위 허브 최근 7일 새 접수 0건 |
| 연속 | 30분 간격 점검에서 2회 연속(1시간 안) | 하루 1회 점검에서 3일 연속 |
| 냉각 | 분할·병합 뒤 7일은 제안하지 않음 | 같음 |

- 워커 상한 도달은 신호가 아니다(결정1). 상한은 기계 부하 기준이라, 나누면 상한이 늘어 부하가 더 오른다.
- 하위 허브는 다시 나누지 않는다(결정3). 하위 허브가 넘치면 부모 아래 형제 허브를 하나 더 만든다.
- 판정 결과: `split`·`merge`(제안 대상), `watch`(신호 일부만 충족), `cooldown`(냉각 중), `none`.

## 3. 명령

```sh
hub_split.py measure                               # 읽기 전용 판정(정리기 시험 실행 포함, 1~2분)
hub_split.py measure --no-gc --topic ui-layer=6    # 빠른 판정 + 메인의 주제 판단
hub_split.py propose --kind split --hub ui-layer --child ui-popup --child-name 'UI 팝업' --prefix ui팝업 \
    --decision-id D-SPLIT2 --reason '정리 후 작업 공간 11개' --file docs/split.html --record
hub_split.py run --decision-id D-SPLIT2 --move C0012           # 시험(기본)
hub_split.py run --decision-id D-SPLIT2 --move C0012 --apply   # 승인 뒤
hub_split.py relink --decision-id D-SPLIT2 --ws <작업 공간 경로> --apply
```

종료 코드: 0 성공, 1 파일 입출력 실패, 2 인자 오류, 3 Orca 응답 없음 등 환경 오류, 4 안전 조건 미충족(진행 워커 남음, 제안 기록 없음, 하위 허브 기동 실패).

## 4. 실행 순서

분할(`run`, 10단계):

1. 백업: 허브 목록 표·접수 경로 표를 `hub-split-runs/<결정 번호>/backup/` 에 복사
2. 시작 보고: Slack 한 줄(문서가 있으면 `--file` 첨부)
3. 하위 허브 생성: 허브 목록 표에 부모 칸을 채운 행 추가 → `create_hub.sh` → 터미널 확인
4. 미착수 목록: `--move` 로 받은 작업 번호 확인. 장부는 하달 즉시 `진행` 이 되어 미착수를 가르지 못하므로 부모 허브가 보고한 목록을 쓴다
5. 재하달: 접수 기록의 원문을 하위 허브 터미널로 보냄
6. 장부 담당: 넘긴 작업의 담당을 하위 허브로
7. 진행 중 작업: 그대로 부모에 둔다(결정4). 완료 보고가 시작한 허브로 가기 때문이다
8. 접수 경로: 새 머리말 한 줄을 기본 행(`*`) 앞에 추가. 기존 머리말은 부모에 둔다
9. 부모 허브에 상태 파일 재기록 요청(스크립트는 상태 파일을 직접 고치지 않음)
10. 완료 보고

병합은 역순이다: 백업 → 시작 보고 → 하위 허브 진행 워커 0 확인(상태 파일 기준, 아니면 종료 코드 4) → 장부 담당을 부모로 → 접수 경로를 부모로 → 하위 허브 아래 작업 공간 전부(열린 PR 포함) 부모로 재연결 → 허브 목록 표 행 삭제 → 하위 허브 터미널 종료 → 부모 상태 재기록 요청 → 완료 보고.

끝난 단계는 `progress.json` 에 남는다. 중간에 멈추면 같은 명령을 다시 실행해 이어서 한다.

## 5. 되돌리기

| 실패 지점 | 되돌리기 |
|---|---|
| 하위 허브 생성 실패 | 허브 목록 표만 백업으로 되돌린다 |
| 장부 이관 중 실패 | `ledger.py owner <id> --to <부모>` 로 담당을 되돌리고 하위 허브 터미널을 닫는다. 작업 공간 폴더는 지우지 않는다 |
| 접수 경로 변경 뒤 오배송 | 접수 경로 표만 백업으로 되돌린다. 하위 허브는 남긴다 |

## 6. 승인·안전

- 분할·병합은 매번 사용자 승인(결정2). `run --apply` 는 `propose --record` 로 남긴 결정 번호만 받는다.
- 부모 정보는 허브 목록 표 여섯째 칸에만 둔다. 상태 파일은 허브가 쓸 때마다 통째로 바뀌기 때문이다.
- 재기동 스크립트는 부모 칸이 빈 허브를 먼저 띄운다.
