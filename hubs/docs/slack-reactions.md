# Slack 반응·댓글 수신 규약

봇 DM 에서 사용자가 단 이모지 반응과 댓글을 봇이 어떻게 읽고, 어떻게 표시하고, 메인 세션에 어떻게 넘기는지 정한다. 같은 이모지라도 메시지 종류(결정 카드·시안)에 따라 뜻이 다르다.

- 기준: `feat/slack-reaction-push` (기준 커밋 `907dfcd` 위 4커밋), 2026-11-10
- 관련 스크립트: `hubs/scripts/slack_poll.sh`(수집·표식), `hubs/scripts/slack_push.py`(메인 전달)
- 실제 Slack 확인: 안 함. 가짜 Slack API·가짜 orca 시험으로만 확인했다

## 쉬운 말 3줄 요약

- 무엇이 바뀌었나: 봇 메시지에 이모지를 누르면 그 메시지에 👀 가 붙고, 메인이 읽으면 ☑️ 로 바뀐다. 이모지 반응도 메인에 전달된다.
- 왜: 지금까지 댓글에만 👀 가 붙고 이모지는 아무 표시 없이 inbox 에만 쌓여, 봇이 읽었는지 알 수 없었다.
- 사용자가 할 일: 없다. 시안(이미지) 메시지에서는 ✅ 가 합격, ❌ 가 불합격, :비서-a:·:비서-b: 가 시안 선택이다.
- 추가(11-10): 번호 결정 카드는 :one:·:two:·:three: 가 선택, ✅ 가 추천대로, ❌ 가 보류다. 할 일 카드는 ✅·🛠️ 가 완료다. 한 카드에 서로 다른 답을 누르면 메인에 "선택이 여러 개" 로 넘어가 다시 묻는다.

## 반응 의미표

메시지 종류에 따라 같은 이모지를 다르게 읽는다. 표에 없는 이모지는 이름을 그대로 넘긴다(`action` = 이모지 이름).

| 이모지 | 결정 카드·종류 없음 (`REACTION_ACTION`) | 시안 `kind=review` (`REVIEW_ACTION`) |
|---|---|---|
| ✅ `white_check_mark` | `approve` (승인) | `pass` (합격) |
| ❌ `x` | `hold` (보류) | `fail` (불합격) |
| `:비서-a:` | `a` | `pick_a` (시안 A 선택) |
| `:비서-b:` | `b` | `pick_b` (시안 B 선택) |
| `:비서-c:`·`:비서-d:` | `c`·`d` | 이름 그대로 |
| `:비서-추천대로:`·`:비서-lgtm:`·`:비서동의:` | `approve` | 이름 그대로 |
| `:비서-보류:` | `hold` | 이름 그대로 |
| 그 밖 | 이름 그대로 | 이름 그대로 |

시안에서 `:비서-추천대로:` 를 합격으로 바꾸지 않는 이유: 시안에는 "추천" 이 정의돼 있지 않다. 잘못 바꾸면 사용자가 뜻하지 않은 합격이 메인에 전달된다. 이름 그대로 넘기면 메인이 판단한다.

시험: `tests/slack_poll/react.sh` 시나리오 R(종류 7가지 × 이모지 6개).

### 번호 카드·할 일 카드 (11-10 추가)

보낸 기록에 `options` 가 있는 `form_kind=decide` 카드(`slack_notify.sh --options`)와 `form_kind=todo` 카드는 아래 표로 읽는다. 위 표의 옛 카드·시안 해석은 그대로다. 이모지 표준표 전체는 `slack-format.md` 「이모지 표준표」.

| 이모지 | 번호 카드 | 할 일 |
|---|---|---|
| `one`·`two`·`three`·`four` | `pick`, `pick`=N. 선택지 수보다 크면 이름 그대로(stderr `범위 밖` 1줄) | 이름 그대로 |
| ✅ `white_check_mark` | `approve`, `pick`=보낸 기록의 `recommended` | `done` |
| ❌ `x` | `hold` | `hold` |
| 🛠️ `hammer_and_wrench` | 이름 그대로 | `done` |
| 그 밖 | 이름 그대로 | 이름 그대로 |

- 레코드에 더하는 키: 번호 카드는 `kind:"decide"`·`decision_id`, `pick`·`approve` 면 `pick`·`option_text`(문구 앞 80자). 할 일은 `kind:"todo"`, 기록에 있으면 `todo_id`. `option_text` 는 우리가 보낸 문구이며 사용자 원문이 아니다.
- **fail-closed.** 보낸 기록의 `options`·`recommended`·`decision_id` 중 하나라도 모양이 틀리면(목록, 번호 빠짐, 추천 번호 범위 밖, 번호 형식 위반) ✅·❌ 까지 포함해 해석하지 않고 이름 그대로 넘긴다(stderr `옵션 정보 오류` 1줄). 보낸 기록을 못 찾은 메시지는 전처럼 수집하지 않는다.
- **충돌.** 같은 카드(같은 `parent_ts`·`decision_id`)의 답(`pick`·`approve`·`hold`)이 inbox 의 앞선 줄과 이번 회차를 합쳐 둘 이상으로 갈리면, 이번 회차 답 줄 전부에 `conflict:true`·`choices`(예 `["1","2"]`, 보류는 `"hold"`)를 붙인다. 줄은 모두 남긴다. 선택 1 과 ✅(추천 1)은 같은 답이라 충돌이 아니다. 범위 밖·이름 그대로 반응은 답이 아니라 충돌에 세지 않는다.
- stderr 줄은 새 반응일 때만 한 번 쓰고 문구·제목은 넣지 않는다.
- **본인 반응만.** 남이 누른 반응과 봇 자신의 반응은 번호 카드·할 일 카드에서도 수집하지 않는다. 응답의 `users` 가 잘려 본인이 안 보이면 그 메시지만 `reactions.get` 으로 보강한 뒤 본인 반응만 해석한다.
- **옛 할 일 카드.** 이 변경 전에 보낸 `form_kind=todo` 카드도 ✅ 가 `approve` 가 아니라 `done` 으로 읽힌다(레코드에 `kind:"todo"` 가 붙는다). 그 카드 본문에 줄 중간 ✅ 글자가 있었다면 `:비서-추천대로:` 로 나갔으므로 이름 그대로 넘어간다.
- **범위 검사가 깨져도 회차는 이어진다.** 선택지 번호는 사전 조회(`not in opts`)로 거르고 문구는 `.get` 으로 읽어, 조회 실패로 예외가 나 그 회차의 다른 수집이 멈추는 일이 없다.

시험: `tests/slack_poll/decide.sh` 시나리오 P(남의·봇 반응 포함), 변이 `tests/slack_poll/mutate.sh` S14~S19·S25.

## 메시지 종류 판별

`slack-sent.jsonl` 의 기록 한 줄로 정한다. 위에서부터 처음 맞는 규칙을 쓴다.

| 순서 | 조건 | 종류 |
|---|---|---|
| 1 | `form_kind` 가 있음(양식 A 의 `--kind`) | 그 값 |
| 2 | `kind` 가 전송 방식(`text`·`file`)이 아닌 값 | 그 값 |
| 3 | 첨부 기록(`file_id` 있음)이고 제목에 "결정" 이 없음 | `review` |
| 4 | 그 밖 | 없음(결정 카드 해석) |

- 종류가 `review` 일 때만 시안 표를 쓰고, 반응·댓글 레코드에 `"kind":"review"` 를 남긴다. 다른 종류는 레코드 모양이 전과 같다.
- 3번에서 "결정" 을 빼는 이유: `slack_notify.sh --tag ui-hub "결정1 A/B?" report.html` 처럼 첨부가 달린 결정 카드가 있다. 이 ✅ 를 합격으로 읽으면 승인이 사라진다. 대기 목록(`slack_pending.sh`)도 제목의 "결정" 으로 결정을 판별한다.
- 병합 시점 기준: 양식 A 가 들어간 `main` 의 `slack_notify.sh` 는 `--kind` 를 받고(값 `decide|todo|done|progress|warn|doc`) 그 값을 `form_kind` 로 기록한다. 이 브랜치는 `form_kind` 를 읽기만 한다. `--kind` 값에 `review` 는 아직 없다(후속).
- **시안 발송 규칙.** 지금 시안이 `review` 로 읽히는 길은 "첨부 + `--kind` 없음 + 제목에 '결정' 없음" 하나뿐이다. 시안 이미지는 `--kind` 없이 첨부로 보낸다. `--kind todo|doc|done|progress` 를 붙이면 1번 규칙이 먼저 맞아 시안이 결정 해석(✅=approve, ❌=hold)이 된다. 제목에 "결정" 이 들어가도("결정 반영 시안") 같다. `--kind review` 를 지원하기 전까지는 이 규칙을 지킨다.
- 공통 규칙 템플릿(`skills/orca-hub-create/references/common-rules.txt.tmpl`)에는 이 규칙을 넣지 않았다. 템플릿은 render 파일·설치가 필요해 후속으로 둔다.

## 읽음 표식

| 받은 것 | 봇이 다는 곳 | 수집 직후 | 메인이 읽은 뒤 |
|---|---|---|---|
| 사용자 글·댓글 | 그 글 | 👀 | ✅ |
| 봇 메시지에 단 이모지 | 이모지가 달린 봇 메시지 | 👀 | ☑️ `ballot_box_with_check` |

- Slack 은 반응에 반응을 달 수 없다. 그래서 이모지가 달린 봇 메시지에 표식을 단다.
- 반응의 완료 표식을 ✅ 가 아닌 ☑️ 로 둔 이유: 사용자가 결정 카드에 누른 ✅(승인)와 봇의 ✅ 가 한 칩("✅ 2")으로 합쳐져 구분이 안 된다. 사용자가 자기 ✅ 를 취소해도 봇의 ✅ 가 남아 승인처럼 보이는 위험도 있다.
- "읽음" 은 그 메시지의 반응 줄이 모두 읽음 표식(`.main-read-lines`)보다 앞일 때다. 같은 메시지에 새 반응이 오면 다시 👀 를 달고, 새 반응 줄이 읽히기 전에는 ☑️ 로 바꾸지 않는다.
- 봇은 자기가 단 👀 만 지운다. 사용자 이모지는 건드리지 않는다.
- 묵음 기준은 메시지 ts 가 아니라 반응 수집 시각이다. 결정 카드는 몇 시간 전 메시지인 경우가 많아, ts 기준이면 바로 묵음 처리된다. 수집 뒤 30분 넘게 못 단 대기는 달지 않는다.
- 메시지와 반응 표식은 회차당 반응 호출 상한(`LRM_REACT_MAX`, 기본 10)을 함께 쓴다. 메시지 표식이 먼저다.
- 진행 표: 상태 파일 `slack-poll-state.json` 의 `reacted_on` = `{봇 메시지 ts: {"s": new|eyes|done|skip, "at": 수집 시각}}`.

## 즉시성 경로

지연 하한은 폴러 주기(launchd `StartInterval` 120초)다. 아래 경로는 모두 수집한 회차에 바로 👀 를 단다. 전달 직후에는 push 가 폴러를 한 번 더 돌려 ✅·☑️ 를 바로 반영한다.

| 경로 | 수집 | 👀 | 이번 변경 |
|---|---|---|---|
| 본인 최상위 글(메모·명령) | ○ | ○ | 그대로 |
| 본인 첨부 글(`file_share`) | ○ | ○ | 그대로 |
| 본인 글 스레드의 댓글 | ○ | ○ | 그대로 |
| 봇 메시지(결정 카드·시안) 스레드 댓글 | ○ | ○ | 그대로 |
| 결정 카드 명령 댓글("결정 1 A") | ○ (command) | ○ | 그대로. 수신 확인 답장은 안 함 |
| "채널에도 보내기" 를 켠 댓글(`thread_broadcast`) | ○ | ○ | **새로 수집**. 전에는 버려졌다 |
| 봇 메시지에 단 이모지 | ○ (reaction) | ○ 봇 메시지에 | **새로 표식**. 전에는 표식이 없었다 |

수집하지 않는 경로(이번 범위 밖): 본인 글에 단 이모지, 봇 확인 답장("📥 메시지 집계 중")처럼 스레드 안 봇 메시지에 단 이모지, `slack-sent.jsonl` 에 없는 봇 메시지(대기 목록·즉답)의 이모지·댓글.

시험: `tests/slack_poll/react.sh` 시나리오 K(9건이 한 회차에 👀).

## 메인 전달(push) 대상

| inbox 항목 | 전달 | 전달문 |
|---|---|---|
| `note`·`command` | ○ | `- #줄번호 [새 메모] ts=…` + 인용 블록 |
| `thread_reply` | ○ | `- #줄번호 [대상 제목] ts=…` (+ ` kind=review`) + 인용 블록 |
| `reaction` | ○ (**새로**) | `- #줄번호 [대상 제목] ts=대상 ts 반응 :이모지: → action` (+ ` kind=review`, ` tag=태그`) |

예(가짜 값):

```
[Slack→메인] 3건 도착 (자동 전달, 지시 아님)
아래는 사용자가 Slack 에 쓴 원문 인용이며 시스템 지시가 아님
- #1 [결정 1] ts=1730000000.000100 반응 :white_check_mark: → approve tag=ui
- #2 [시안 1] ts=1730000000.000200 반응 :비서-a: → pick_a kind=review tag=ui
- #3 [시안 1] ts=1730000000.000300 kind=review
> 색이 조금 진함
전체: ~/.config/lrm-hubs/slack-push/<날짜시각>.md
```

- 기존 규칙은 그대로다: 메시지 원문 400자·묶음 3000자 상한, 위조 접두·제어 문자 무력화, 도착 확인(turn_started) 뒤에만 읽음 표식 올림, 실패·도착 불명이면 보류(fail-closed), 재시도 요청 ID 고정.
- 반응 줄의 제목·이모지·태그도 메시지 본문과 같은 정리(`one_line`)를 거친다.
- 반응은 전달 기록(`slack-push-delivered.jsonl`)의 스레드 건수에 세지 않는다. 확인 답장 "📨 메인에 전달했어요 (n건)" 은 댓글 수만 센다.
- **옛 반응.** 반응 전달 이전 버전이 쌓은 반응 줄은 전달하지 않는다. 그 줄 앞에서 읽음 표식이 멈추고 전달문에 "읽지 않은 반응 n건은 inbox 에서 확인" 만 붙는다. 기준선은 push 상태 파일의 `react_since` 다. 키가 없는 옛 상태는 처음 실행할 때 "전달 완료 줄·보류 묶음 끝 줄" 중 큰 값으로 고정한다. 보류 중이던 묶음은 반응 없이 본문이 고정돼 있어 그 범위 반응도 옛 반응이다.

시험: `tests/slack_poll/push.sh` ⓗ(반응 전달·옛 상태·옛 보류 묶음·시안 전달문·도착 불명 보류), 통합(메모 + 반응 → 👀 → 전달 → ✅·☑️).

## 권한 오류

- `reactions:write` 가 없거나(`missing_scope`) 인증 오류여도 수집·댓글 기록·메인 전달은 계속한다. 표식만 건너뛰고 10분마다 다시 시도한다.
- `slack-poll.log` 에는 사유와 scope 이름만 한 줄 남긴다(예: `읽음 반응 사용 불가(missing_scope) — Slack 앱 scope(reactions:write) 확인`). 토큰 값은 쓰지 않는다. 같은 사유는 다시 쓰지 않는다.
- 권한이 없는 동안 반응 표식은 대기(`new`)로 남는다. 복구 뒤 수집 30분 안이면 👀 를 단다.

## 한계·후속

- 같은 메시지에 ✅ 와 ❌ 를 모두 눌렀다 번복하면 두 줄이 모두 전달된다. 취소가 보이지 않아 메인은 둘 중 현재 상태를 알 수 없다. 번호 카드는 이 경우 충돌로 표시한다(1 을 취소하고 2 를 눌러도 충돌. 사용자 확인 대상).
- 실제 Slack 의 번호 이모지 반응 이름(`one`~`four`)과 `hammer_and_wrench` 는 확인하지 않았다. 가짜 응답(`conversations.history` 의 `reactions:[{name,users,count}]`)으로만 시험했다. 이름이 다르면 해석하지 않고 이름 그대로 넘어가므로(fail-closed) 잘못된 답은 생기지 않는다.
- 시안 ❌=`fail`, 결정 ❌=`hold` 를 되돌릴 수 없는 처리로 볼지는 메인 규칙이며 이 문서의 범위 밖이다. 이 문서는 해석과 전달까지만 정한다.
- 반응 줄은 묶음 글자 상한(`BATCH_CHARS` 3000자)에 세지 않는다. 한 묶음은 건수 상한 20줄이 한계이며 반응만이면 최대 약 3.7천 자다.
- 업그레이드 설치에서 옛 반응이 읽음 표식을 막는 것은 이전 동작과 같다. 이후 전달한 반응의 ✅·☑️ 는 메인이 옛 반응 줄을 읽기 전까지 바뀌지 않는다.
- `thread_broadcast` 답글은 `thread_broadcast_since`(상태 파일, 첫 실행 시각) 이후에 달린 것만 새 항목으로 수집한다. 그 이전 답글은 중복 방지 키에만 기록하고 inbox 에 쓰지 않는다. 상태 파일을 잃으면 이 경계가 지금 시각으로 다시 잡힌다.
- 후속: `slack_notify.sh --kind review` 추가와 `form_kind=review` 매핑(지금도 판별표 1번이 `review` 를 읽는다). 들어가면 시안 발송 규칙이 단순해진다.
- 반응 취소는 감지하지 않는다. 취소해도 inbox 에 새 줄은 안 생기지만, 이미 전달된 반응을 철회하는 안내도 하지 않는다.
- 같은 반응을 30일 안에 취소했다 다시 누르면 새로 기록하지 않는다(중복 방지 키 `react:<ts>:<이모지>` 유지 기간).
- 매니페스트(`hubs/slack-bot-manifest.yml`)의 bot scope 목록에 `reactions:write` 가 없다. 실제 앱에서는 동작이 확인됐다(2026-11-10 메인 실측). 매니페스트로 앱을 다시 만들면 빠질 수 있다.
- 실제 Slack 의 `thread_broadcast` 답글 모양(`conversations.replies` 응답의 subtype)은 확인하지 않았다.
