# 작업 흐름: 7단계와 작업 크기

작성일 2026-11-18. 기능 코디네이터가 일을 받아 끝낼 때까지 밟는 순서와, 그 순서를 건너뛰지 못하게 하는 장치를 적는다.

## 쉬운 말 3줄 요약

- 무엇: 기능 작업은 접수 → 이해 → 설계 → 구현 → 검증 → 검수 → 반영 순서로 간다. 크기가 작은 일은 설계를 건너뛴다.
- 왜: 계획 없이 구현부터 하면 틀린 전제 위에서 만든 것을 전부 버린다. 코드가 바뀌기 전에 한 번 멈추면 버리는 양이 계획서 한 장으로 줄어든다.
- 사용자가 할 일: 목표와 확인 방법을 주고, 계획 승인·검수·병합 승인 세 번만 답한다.

## 단계

| 단계 | 이루려는 것 | 끝났다는 증거 | 사용자가 할 일 |
|---|---|---|---|
| 0 접수 | 만들 것 한 문장과 끝났는지 확인할 방법 한 문장을 정한다. 크기도 정한다 | 기능 카드 설명의 `- 목표:`·`- 확인 방법:`·`- 범위 밖:` 칸, label `size:` | 목표와 확인 방법을 말한다 |
| 1 이해 | 지금 실제 동작과 기획이 말하는 동작을 같은 그림으로 본다 | 기획 대조표, 지금 상태 도식, 기준 캡처나 기준 출력 | 다르면 알려 준다. 큰 일만 "맞다"를 기다린다 |
| 2 설계 | 바뀐 뒤 모습과, 변경을 어떻게 나눠 무엇으로 확인할지 정한다 | 바뀔 상태 도식, 계획서, 계획 승인 답 | ✋ 승인 또는 수정 요청 |
| 3 구현 | 카드 하나씩 만들고 바로 검사한다 | 카드마다 커밋과 증거 로그 | 없다 |
| 4 검증 | 0단계의 확인 방법을 실제로 돌려 본다 | 확인 방법 항목마다 증거, 다른 모델의 검수 판정 | 없다 |
| 5 검수 | 사용자가 결과를 한 번에 판단한다 | 완료 보고 한 건, 사용자의 통과 답 | ✋ 통과 또는 수정 요청 |
| 6 반영 | 계획한 범위만 공유 브랜치에 넣고 뒷정리를 한다 | PR, 병합 커밋, 반영 끝 기록(`--shipped`), 정리된 코디네이터 | ✋ 병합 승인 |

수정 요청은 3단계로 돌아간다. 코디네이터가 스스로 계획을 바꾸면 2단계로 돌아가 다시 승인받는다. 사용자가 코디네이터 창에서 직접 지시한 설계 변경은 다시 승인받지 않는다(아래 「직접 지시」).

## 직접 지시 (11-19)

사용자가 기능 코디네이터 창에 직접 친 글은 계획·검수 모델 지적·티켓 기준보다 우선한다. 11-19 대화 기록에서 지시는 1분 안에 전달됐지만, 진행 중 카드에 코디네이터 자체 수정과 묶이고, 설계가 바뀔 때마다 Slack 재승인을 받고, 작은 조정도 무거운 절차를 타고, 지시가 한곳에 남지 않아 결과와 대조할 수 없었다.

| 장치 | 하는 일 | 막는 것 |
|---|---|---|
| `board-said <기능 카드> <이름> --sync` | 세션 기록에서 사용자가 친 글을 읽어 기능 카드에 `지시 #N` 으로 적는다. 코디네이터가 옮겨 적지 않는다 | 지시 누락, 원문 고쳐 쓰기 |
| `board-said … --mark <번호> 반영\|미반영\|답함\|되물음\|해당없음 "<근거>"` | 지시마다 처리를 적는다 | 처리 없이 넘어가기 |
| `board-done --epic` | 장부에 없는 글이나 처리 안 적힌 지시가 있으면 종료 6(label `said:v1` 인 기능만. `feature_open.sh` 가 새 기능에 붙인다) | 지시를 빠뜨린 채 완료 |
| 코디네이터 창에 `승인`·`스킵`으로 시작하는 글 | 계획 승인으로 인정한다(`board_flow.typed_approval`, 세션 기록에서 읽음). `진행해`·`ㄱㄱ`만으로는 인정하지 않는다 | Slack 버튼을 기다리느라 멈추기 |
| `board-done --epic … --no-capture "<이유>"` | 화면에 보이는 변화가 없으면 캡처·녹화를 생략한다. 기준 브랜치와 견줘 화면 파일(프리팹·씬·재질·셰이더·그림·애니메이션·데이터 에셋·UI 문서)이 하나라도 바뀌었으면 종료 7 | 필요 없는 촬영, 필요한 촬영 건너뛰기 |
| `hub_report.py add … --top` | 결정 카드를 스레드 밖 새 메시지로 올린다 | 스레드 안 카드를 못 보고 지나치기 |

- 직접 지시한 설계 변경은 계획서를 고치고 기능 스레드에 바뀐 점 보고만 올린 뒤 바로 진행한다. 승인 카드를 다시 올리지 않는다. 다시 올리면 받은 승인이 풀린다.
- 지시에 없는 수정을 섞지 않는다. 코디네이터가 찾은 문제는 별도 카드로 만들고, 화면에 보이는 동작을 바꾸는 것이면 먼저 묻는다. 검수 모델 지적이 지시와 부딪히면 스스로 정하지 않고 묻는다.
- 작은 조정은 하던 작업자에게 이어서 맡긴다. 녹화와 다른 모델 검수는 조정마다 하지 않고 기능당 마지막에 한 번만 한다.
- 사용자 글의 정본은 세션 기록(`board/lib/board_said.py`)이다. 입력창에 글을 넣는 명령으로 넣은 줄은 사용자 글과 구분하지 못한다. 일부러 규칙을 피하는 경우라 막지 않았다.

## 급한 일: 준비 건너뛰기 (11-19)

사용자가 급하다고 한 기능은 1 이해와 2 설계(계획서, 계획 승인)를 건너뛰고 접수에서 바로 구현으로 간다. 건너뛸 수 있는 것은 준비뿐이다.

- 왜 준비만인가: 11-19 기능 여섯 건의 단계 시각을 재 보니 보통 크기 일의 준비가 13~18분, 작은 일은 3~5분이었다. 검증까지 열면 3~7분을 더 얻지만 검수 전 코드가 병합될 수 있어 병합 뒤 수정 절차가 새로 든다. 사용자가 준비만 건너뛰는 안을 골랐다. 근거 문서는 `~/Documents/90_정리기록/20261119-건너뛰기-흐름/`.
- 구현 12~35분은 줄지 않는다. "10분 안에"는 건너뛰기로 풀리지 않는다.

| 장치 | 하는 일 |
|---|---|
| `feature_open.sh … --skip 급함` | 새 기능 카드에 label `skip:understand`·`skip:plan` 을 붙인다. `이해`, `계획`만 따로 줄 수도 있다 |
| 코디네이터 창에 `급함` 또는 `스킵 이해`·`스킵 계획` | 코디네이터가 `board-skip <기능 카드> <이름> --sync` 로 세션 기록에서 읽어 적는다. 글 전체가 이 꼴일 때만 읽는다(`급함 아님`은 읽지 않는다) |
| `board-skip <기능 카드> <이름> <항목…> --user-said "<원문>"` | 다른 창에서 받은 사용자 명령(`/orca-feature skip`)을 적는다 |
| `board-skip <기능 카드> <이름> <항목> --undo` | 아직 지나지 않은 항목의 건너뛰기를 취소한다 |
| `board-claim`, `board-stage` | `skip:plan` 이 있으면 계획 승인 없이 구현 카드를 집고 구현 단계로 옮긴다(`board_flow.claim_block`) |
| `board-stage <기능 카드>` | 지금 건너뛴 항목을 보여 준다 |

- 건너뛸 수 없는 것: 접수의 목표·확인 방법과 크기, 카드별 컴파일·관련 시험, 병합할 때 범위 검사, 다른 모델 검수, 캡처·녹화, 사용자 검수, 병합 승인. `스킵 다른모델검수` 같은 글은 건너뛰기로도 계획 승인으로도 읽지 않고, 도구가 건너뛸 수 없다고 알린다.
- 항목 없이 `스킵`만 치면 전과 같이 계획 승인 대기만 넘긴다. `스킵 이해`는 이해만 건너뛰고 계획 승인으로 세지 않는다.
- 이미 지난 단계의 항목은 걸거나 풀어도 바꾸지 않는다(이해는 설계부터, 계획은 구현부터 지난 것).
- 건너뛰기 글은 지시 장부에 지시로 적지 않고 기능 카드의 `건너뛰기:` 코멘트로 남는다.
- 빈틈: `--user-said` 의 원문은 세션 기록과 대조하지 않는다(크기를 낮출 때의 `--user-said` 와 같다). 슬래시 명령이 세션 기록에 남는 꼴을 실제 기록에서 찾지 못해 대조를 만들지 못했다. label 을 `bd` 로 직접 붙이는 것도 막지 않는다.

## 작업 크기

| 크기 | label | 기준 | 밟는 단계 | 사용자가 멈추는 곳 |
|---|---|---|---|---|
| 작음 | `size:small` | 파일 한두 개. 화면 흐름이 안 바뀐다 | 0 → 3 → 4 → 5 → 6 | 검수, 병합 승인 |
| 보통 | `size:normal` | 기능 하나 안에서 화면이나 흐름이 바뀐다 | 전부. 1단계는 올리고 바로 진행한다 | 계획 승인, 검수, 병합 승인 |
| 큼 | `size:large` | 여러 모듈, 구조 변경 | 전부. 구조안 문서가 더해진다 | 지금 상태 확인, 계획 승인, 검수, 병합 승인 |

## 건너뛰지 못하게 하는 장치

규칙은 `board/lib/board_flow.py` 한 곳에 있고 두 도구가 같이 쓴다. 판정 경우는 `tests/board_flow/test_flow.py` 의 표다.

| 장치 | 막는 것 | 종료 코드 |
|---|---|---|
| `board-stage <기능 카드> <단계> <이름>` | 목표·확인 방법·크기 없이 접수를 떠나는 것 | 2 |
| 같은 도구 | 계획 승인 없이 구현·검증 단계로 가는 것(보통·큼) | 15 |
| `board-claim <카드> <이름>` | 계획 승인 없이 그 기능의 구현 카드를 집는 것(보통·큼), 크기를 안 정한 기능의 카드를 집는 것 | 15 |

- 적용 대상은 기능 카드에 label `flow:v1` 이 있는 기능이다. `feature_open.sh` 가 새 기능 카드에 붙인다. 그 전에 연 기능은 막지 않는다.
- `board-stage <기능 카드>` 만 치면 지금 단계, 크기, 계획 승인 여부와 계획 승인 결정 번호를 보여 준다.
- 크기를 낮추는 것(보통·큼 → 작음)은 사용자 원문(`--user-said`)을 함께 줄 때만 된다. 작음은 계획 승인을 건너뛰기 때문이다. 올리는 것은 그냥 된다.
- 집기 검사는 기능 카드 바로 아래 카드뿐 아니라 그 아래의 손자 카드, 상위 없이 `feature:<slug>` label 만 단 카드에도 걸린다.
- 검수(5)와 반영(6)은 손으로 옮기지 않는다. 완료 검사 `board-done --epic` 이 label `stage:review` 를 붙이고, 사용자 검수 답(`--user-ok "<원문>"`)이 `stage:ship` 으로 바꾸고, 병합 뒤 `--shipped "<PR·병합 커밋>"` 이 뗀다.
- 코디네이터는 검수와 반영이 끝날 때까지 남는다(11-19). 완료 검사가 기능 카드를 닫아도 `stage:review`·`stage:ship` 표시가 있는 동안은 살아 있는 기능으로 보고, 검수 답과 스레드 글을 그 코디네이터에게 전달한다(`feedback_route.feature_alive`). 그 전에는 완료 검사가 코디네이터를 바로 정리해서 통과·수정 답이 메인 담당 확인 카드로 떨어졌다. 정리는 `--shipped` 가 한다.
- 답이 세션에 닿았는지는 수신기 로그가 구분한다(11-23). `전달 성공`은 세션에 닿은 때만 찍고, 받을 세션이 없으면 `받을 세션 없음 → 메인 확인 카드`, 세션 전달이 실패하면 `세션에 닿지 않음 → 메인 대리 기록(원인)`으로 적는다.
- 검수 통과 답은 Slack 기록과 대조한다(11-23). 검수 결정 카드는 기능마다 정해진 번호(`D-REVW…`, 계획 승인의 `D-PLAN…`과 같은 방식)로 올리고 1번 선택지를 `통과`로 시작하게 한다. 번호는 `board-stage <기능>` 이 보여 주고 코디네이터가 `--decision-id` 로 넘긴다. `--user-ok` 는 그 번호의 가장 최근 카드에 사용자가 직접 낸 가장 최근 답이 1번일 때만 받는다. 답이 없거나 `고칠 점 있음`이면 거부하고, 카드를 다시 올리면 옛 카드의 답은 쓰지 않는다. 창에 직접 친 통과(`--user-ok-typed`)는 그대로 된다. 카드는 코디네이터가 손으로 올리지 않고 완료 검사가 올린다(11-23: 카드 없이 창에 `통과`를 치라고만 보고한 기능과, 고칠 점을 고친 뒤 카드를 다시 올리지 않은 기능이 있었다). 고칠 점 답을 받아 고친 뒤에는 `board-done --epic <id> <이름> --ask-review [--review-note "<한 줄>"]` 로 다시 올린다. 앞 카드와 제목이 같아 번호 재사용 검사에 걸리지 않고, 답을 기다리는 카드가 있으면 또 올리지 않는다. 올리지 못해도 완료 검사는 성공하고 다시 올리는 명령이 출력된다.
- 전환: 완료 검사가 검수 단계로 넘길 때 `review:v1` 표시를 붙이고, 표시가 있는 기능만 대조한다. 11-23 기준 이미 검수 단계인 기능 9개는 표시가 없어 막히지 않고 경고만 난다.

## 계획 승인

계획 승인은 그 기능의 작업 스레드에 올린 결정 카드의 버튼 답이다. 사용자가 그 기능 코디네이터 창에 `승인`·`스킵`·`전부 추천`·`추천대로`로 시작하는 글을 직접 쳐도 승인이다(첫 문장에 부정·보류·물음이 있으면 아니다. 가장 최근 계획 카드를 올린 뒤에 친 글만 세고, 그 카드에 Slack 으로 수정 요청을 했으면 그 뒤에 친 글만 센다).

- 결정 번호는 기능 카드 id 에서 만든다(`board_flow.plan_id`, 예 `lrm-spn` → `D-PLANLRMSPN`). 손으로 정하지 않으므로 다른 결정의 승인을 끌어다 쓸 수 없다.
- 1번 선택지는 `승인` 으로 시작해야 한다. 사용자가 1번이나 추천대로를 고르면 승인이다.
- Slack 과 문서 사이트에서 사용자가 누른 답만 센다. 터미널에서 남긴 답(`decide-answer`)은 세지 않는다. 코디네이터가 스스로 승인하지 못하게 하려는 것이다. 사용자가 코디네이터 창에 직접 친 글은 여기에 해당하지 않는다(세션 기록에서 읽으며, 코디네이터가 쓸 수 없는 파일이다).
- 검수 통과도 같다. 완료 검사 뒤 사용자가 코디네이터 창에 `통과`로 시작하는 글을 치면 `board-done --epic <id> <이름> --user-ok-typed` 가 그 글을 읽어 통과로 기록한다. 11-19 에 한 코디네이터가 창의 "통과"를 두 번 거절하고 Slack 버튼을 기다린 일이 있어 넣었다.
- 한계: 메인이 입력창에 대신 넣어 준 글과 사용자가 친 글은 세션 기록에서 구분되지 않는다. 그래서 되돌리기 어려운 PR 열기(draft 해제)와 dev 병합은 창 입력으로 풀지 않고 Slack 카드로 남긴다.
- 답은 가장 최근에 올린 카드에 달린 것만 본다. 계획을 고쳐 같은 번호로 다시 올리면 옛 카드의 승인은 새 계획의 승인이 아니다. 새 카드에 다시 승인받아야 한다.
- 한 카드에 답이 여럿이면 가장 최근 것이 기준이다. 승인한 뒤 수정 요청으로 바꾸면 승인이 풀린다.
- 카드에 단 ✅ 반응이나 카드 스레드에 쓴 `1`·`추천` 도 사용자 답이라 승인으로 센다(1번을 가리킬 때만).
- 다시 올릴 때는 첫 줄(제목)을 그대로 둔다. 번호가 기능마다 하나라, 첫 줄이 바뀌면 접수가 "다른 질문에 이미 쓴 번호"로 거부한다.

```
hub_report.py add --kind decide --card <기능 카드> --ws <코디네이터 작업 공간> \
  --decision-id <계획 승인 번호> --recommend 1 \
  --options '1=승인 => 계획대로 구현을 시작한다,2=수정 요청 => 고칠 점을 받아 계획을 고친다' \
  --file <계획서.html> --text $'계획 승인: <기능 이름>\n배경: …\n용어: …'
```

## 코디네이터 자동 압축 (11-20)

- 새로 여는 코디네이터 허브는 대화 약 20만 토큰에서 자동 압축한다(허브 `.claude/settings.local.json` 의 `autoCompactWindow`). 압축 직후 SessionStart 훅이 기능 카드 id·단계·처리 안 된 지시를 다시 넣는다.
- 이유: 호출마다 지난 대화 약 23만 토큰을 다시 읽어 비용이 큰데 기본 기준(약 97만)에서는 거의 압축되지 않았다. 이미 떠 있는 코디네이터와 메인·워커는 그대로다.
- 끄기·바꾸기: 허브 생성 때 `LRM_HUB_AUTOCOMPACT=off`(또는 100000 이상 숫자). 작업판 조회가 2초를 넘기면 훅은 안내 한 줄만 낸다.

## 아직 없는 것

- 계획 승인 한 번이 Jira 상태 전환과 PR 초안 생성까지 승인하는 기록(`plan-approvals/<plan-id>.json`)은 여전히 메인 세션이 쓴다. 구현 착수 판정과는 별개다.
- 옆 패널의 단계 띠와 "다음 할 일" 줄.
- 확인 방법 항목과 증거를 하나씩 대조하는 검사(4단계), 완료 보고 양식 검사(5단계).
- 승인이 계획서 파일의 지문에 묶이지 않는다. 카드를 다시 올리지 않고 계획서 파일만 고치면 승인이 남는다.
- label 을 `bd` 로 직접 떼는 것(`flow:v1`, `size:`)과 `bd update --claim` 으로 직접 집는 것은 막지 않는다. 일부러 규칙을 피하는 경우라 도구 안내와 규칙 글에만 맡겼다.
